# hermes-mcs

### MCSの連絡を、探せる記録と次の確認へ。

**MedicalCareStation（MCS）の記録を、自分のMacで収集・整理・検索。**
**Slack（推奨）**の通知カードから、連絡の確認、担当の記録、タスクの作成までつなげます。
在宅医療・介護のチームで交わされた相談や経過を、あとからたどるためのローカルシステムです。
Slack・DiscordはHermes連携または独立接続、[LINE WORKS](docs/guides/LINEWORKS.md)は独立した独自アダプターを使います。
Hermesを入れない[スタンドアローンモード](docs/guides/STANDALONE.md)では、Slack・Discordの直接接続と共通の操作経路を選べます。接続先SDKと実機運用の受入は別に確認します。
LINE WORKSでは同じ要約・原文・添付をトークルームの連続投稿で配信します。
Slack・Discordでは、元の投稿をチャンネルのカードに、後から届いた返信を1件ずつのカードとして元の会話のスレッドに表示します。

> 秘密値はチャットに書かせず、ユーザーの端末で入力してもらいます。投稿の収集・通知・既読化・サービス起動は、依頼された範囲でだけ行います。

| 収集 | 保存・整理 | 通知・操作 |
|---|---|---|
| 24時間・既定10分間隔 | Mac上のSQLite + ローカルLLM | Slack（推奨） / Discord / LINE WORKS |

MCSサーバーの負荷対策として、自動取得の間隔を5分から10分へ変更しています。サーバーが混雑の応答（HTTP 429）を返した回は、指定の待ち時間を守り、2回受けたら残りの取得を次の定期実行へ回します。

このREADMEはmainの機能を説明します。[任意のローカル支援](#candidate)は機能ごとに適用条件があり、実機・外部の受入条件は分けて記載します。導入する版の変更・更新手順は[CHANGELOG](CHANGELOG.md)と[Releases](https://github.com/yusuketakuma/hermes-mcs/releases)で確認してください。
通知を有効にすると患者名・本文・送信対象の添付が設定先へ送られます。端末のロック画面にも患者名・投稿内容が表示され得るため、通知プレビュー設定と端末の閲覧権限を確認してください。[情報の行き先と安全境界](#data)を導入前に確認してください。

## 画面イメージ — Slack

**通知先とカード操作はSlackを推奨します。** 要点の確認からタスクの確定・再確認候補まで、8画面で紹介します。
掲載画像の名前・投稿・数値はすべて架空です。実データや実投稿の匿名化例は使用していません。現行実装に基づく説明図で、実画面のキャプチャではありません。
[導入前に資格情報なしで画面をたどる](docs/screenshots/slack-gallery/README.md#導入前に画面をたどる)案内では、原文・返信・添付・スタンプと、配送保留の文章シナリオを確認できます。

![Slackの全体像：チャンネルの元の投稿のカードと、スレッドに届いた返信のカード・添付を並べた画面例](docs/screenshots/slack-gallery/01-overview.png)

元の投稿のカードでは、要約と折りたたんだ原文を読み、押した人を含むスタンプを同じエリアで確認・送信できます。後から届いた返信は、1件ずつのカードとして元の会話のスレッドに届きます。元の投稿のカードには返信の件数だけを表示し、画像やPDFの添付もスレッドに届きます。この表示は更新後に新しく始まる会話から使い、以前からあるカードは返信をまとめる従来の表示のままです。従来の表示に戻すには`notify.reply_cards`を`false`にします。

![通知から確認・タスクまで：新しい投稿がカードとスレッドで届き、職員の確認・担当・タスク作成が記録されてカード表示に戻る流れ](docs/assets/notification-flow.svg)

スマートフォンの通知には、患者名・発信者・所属・投稿時間・短い要約を含む通知文を送ります。要約が未完成なら原文の一部と処理状態を示し、取得できない項目は推測しません。実際の表示・省略は端末とアプリの通知プレビュー設定に従います。既存のDiscordカードとLINE WORKSのファイル通知では、同じプレビュー表示にならない場合があります。
画像を開くと拡大できます。画像内のボタンは説明用で、実際の操作はSlackの許可ユーザーが行います。

### 確認・担当を、カードから共有

![Slack通知カード：元の投稿のカードとスレッド内の返信カードに、それぞれの要約・原文・スタンプ・操作を表示する画面例](docs/screenshots/slack-gallery/02-notification.png)

`確認する`・`担当する`の結果を、カードの状態欄に名前で表示します。確認と担当はカードごとに記録し、返信のカードで選んだ操作は、その返信だけが対象です。
MCSのスタンプは、カードと未確認一覧に `スタンプ 👀2` のような絵文字と件数で表示します。
操作する本人とMCSアカウントを指定すると送信が既定で有効になり、そのカードに表示している投稿へスタンプを送れます。Slackはスタンプ表示と`スタンプを押す…`メニューを同じエリアにまとめ、メニューを開いて種類を選ぶ2段階です。自分の種類は`✓（取消）`、Discord・LINE WORKSは従来の直接ボタンで示します。`別の投稿`（メニューにまとめるカードでは`MCSスタンプ`）のフォームからは投稿・返信を選んで追加・変更・取消できます。画像・PDFは添付が属する投稿が対象です。`stamps.enabled=false`で無効にできます。[操作と設定](docs/specs/stamp-management.md)を確認してください。
押下者取得を有効にすると、Slackの新形式カード、DiscordやSlackの本文スレッド、LINE WORKSの投稿見出しに、スタンプの件数と押した人の氏名を1行で表示し、古い一覧・再取得失敗を区別します。投稿ごとの観測日時は、押した時刻ではありません。
**カードの確認済み表示やMCSの「完了」スタンプは、正式なタスク完了を意味しません。**

### 必要な操作を、メニューから選ぶ

![Slackの操作メニュー：患者の記録まとめ・検索などの画面例](docs/screenshots/slack-gallery/03-actions.png)

Slack・Discord・LINE WORKSとも、`確認する`・`担当する`・`タスク作成`を含む通常操作を`操作を選ぶ…`にまとめています。スタンプと`別の投稿`はメニューを開かずに押せます。
`タスク一覧`などの表示は、カードの状態や設定で変わります。
`患者の記録まとめ`は本人だけに背景・療養情報の原記録抜粋を表示します。全患者の詳細情報を根拠付きで保存し、全文と以前の記載は[患者別の詳細読取り](docs/guides/USER_GUIDE.md#c-患者ごとのまとめrollup)から確認できます。

<a name="slack-summary"></a>

### 訪問前に、患者の記録まとめで記録をたどる

![Slackの本人向け患者の記録まとめ：薬・次回予定・未完了タスク・履歴取得状況の画面例](docs/screenshots/slack-gallery/07-patient-summary.png)

`患者の記録まとめ`から、取得済み投稿の薬・最新バイタル・次回予定・未完了タスク・履歴取得状況を本人に表示します。

住所・連絡先・キーパーソン・駐車場・家族構成・現病名など、保存された投稿の明示情報も背景としてたどれます。
各記録は原文の後ろに出典を短く添えます（例: 「残薬3日分。（10/03 薬剤師 #3）」）。Slack・Discordでは日付から患者のMCSチャットを開けます。Slackでは見出し・出典・区切り線を使ったBlock Kitで表示します。病名・既往など重要な分類が先頭に並び、関係者は冒頭の1行にまとまります。関係者・事業者は投稿者の職種・氏名・事業所から部屋ごとに一覧にします。利用中の契約や主担当は推定しません。訪問看護・介護・診療・薬局・リハ・栄養・歯科・相談員などの記録を共通の分類で扱い、職種を選ぶと表示順だけが変わります。

[患者コンテキスト作成](docs/guides/USER_GUIDE.md#患者コンテキスト作成既定は有効)は、過去の記録を24時間少しずつ点検し、保存済みの投稿がすべて現行のLLM抽出世代で解析済みの患者から患者コンテキストを作ります。本人向け画面で背景、前回からの変化、連絡・返答、訪問前の確認事項、経過、記載の食い違い、引継ぎ、退院前後の記録を原文付きでたどれます。生成・限定閲覧とも既定で有効です。既存環境も設定を省略して更新すると有効になり、明示した `false` は維持します。
患者の記録まとめを読み込めない場合は、その旨を示して基本のまとめを表示します。自分のタスク・未確認一覧・集計ではアーカイブ済み患者を末尾に示し、通常の解析もアクティブ患者を優先します。
**暫定集約であり、確定した処方一覧ではありません。未取得の記録も「無い」とは扱いません。**

### 該当スレッドで、対象と根拠を確認する

![本人の緊急度再確認候補を元スレッドに追加する完全合成の画面例](docs/screenshots/slack-gallery/08-urgent-notice.png)

本人・家族・他者と、現在・過去・予定を原文から区別します。再確認候補と薬剤シグナルは元投稿の既存スレッドに追加し、原文根拠・投稿日・確認先を短く示します。解析が続いている投稿には「解析更新中」を表示し、既存の投稿を更新します。

新しいカードは患者名の下に緊急度・投稿数・解析中の件数をまとめ、投稿ごとの要約を項目順に表示します。薬剤の確認と辞書検索は押した本人だけに表示し、Slack・Discordでは同じスレッド、LINE WORKSでは1:1トークで確認します。辞書の検索は承認済み辞書が有効な場合だけ使えます。

## できること

| したいこと | hermes-mcsでできること |
|---|---|
| 新しい連絡を確認する | 要約カードで通知。Slack・Discordは元の投稿と返信を1件ずつのカードで表示し、返信のカードと添付は元の会話のスレッドへ。Slackは原文を折りたたんで表示。LINE WORKSは連続投稿で確認 |
| 過去のやり取りを探す | 履歴の保存・全文検索・患者ごとのタイムライン。全角・半角や英字の大小を揃えて検索し、途中で止まった履歴取得は再開 |
| 長い連絡の要点を読む | 薬・症状・依頼・バイタル・検査値などをローカルLLMとルールで抽出 |
| 患者の記録をまとめて見る | 薬・最新バイタル・次回予定・未完了タスク・服薬管理の報告・MCS連携サマリーを暫定集約 |
| 次に確認する記録を見つける | 処方期間の候補の終了前・終了後や、後続の記録が見つからない状態などをアラートとして提示 |
| 確認・担当・依頼を共有する | カードの確認・担当を記録。タスクは内容と理由を確認してから確定 |
| 全体の傾向を把握する | 投稿量・職種別内訳・未解決依頼などの読み取り専用統計。任意の日次ダイジェスト |

Slack・Discordでは通知カードと操作メニューに加え、`/mcs`コマンドから閲覧・依頼管理・運用承認を行えます。
LINE WORKSではカードのボタンと本人との1:1トークの `mcs JSON` を使います。Hermesあり・なしで共通の機能と人承認条件を使い、LINE WORKSの接続はどちらも独立アダプターが所有します。
`全体の新着集計`から全体・施設・患者・記録上の担当で絞り込めます。Slackは`/mcs-summary`、Discordは`/mcs`の`summary`、LINE WORKSは本人DMの「サマリー」でも呼び出せます。元データは読取り専用スナップショットです。

要約の項目別の短い文字数・件数制限は外し、作成待ちと再試行上限に達した失敗を区別します。通知先の表示上限は維持し、長いカードはページに分け、単一投稿が上限を超える場合は省略して本文表示や原本へ案内します。抽出の保存後に表示を更新し、押下者取得を有効にした環境では取得完了後に氏名も反映します。

服薬管理のうち薬の保管状況・保管場所・管理者、疑義照会・処方提案の結果、重複・相互作用の確認は、原文の値を引用した1行でカードにも表示します。以前の報告を抽出の参考にする設定（`extract.patient_state_context`）は既定offです。

原文の測定値・薬剤・確認や連絡の候補が欠けている場合は、既存の時間枠で一度だけ再確認します。初回に読み取れた内容を保持し、補完待ちや確認できなかった箇所は「要確認」と区別します。意味解析では取りこぼしを補完した後も再監査を行い、不完全な結果を公開しません。

履歴取得・抽出・統計の重複走査とメモリ使用を抑え、一時的な障害からの再試行を改善しています。抽出やカード配送の停滞は稼働状態へ記録します。記録が多い環境でも、モデル・取得間隔・任意機能の既定値は変えません。

収集エラーの警報は、18の原因分類ごとに何が起きたかと利用者の対処を示します。時間切れ・通信・取得未完了などの自然に回復しやすい異常は同じ異常が3回続いたときに通知し、ログイン切れ・保存できないなどの重い異常はすぐ通知します。health.jsonではDB本体の使用量・空きページ量、バックアップの種類別容量、日次・週次保守の経過時間も確認でき、日次保守が2日以上完了しないと警告します（[判定の説明図](docs/releases/v1.1.0/README.md)）。

AIが緊急度を高と判定した投稿で元の本文を取得できていない場合は、「緊急度: 要確認」と表示し、本文で裏付けられない「高」の表示や緊急通知はしません。

ローカルLLMはMCS専用の3レーンです。レーン1は新着、レーン2・3は過去分を担当し、2・3はGPUを順番に使います。患者コンテキストはレーン3で24時間作成し、解析済みのアクティブ患者から処理します（再試行上限に達した投稿は対象判定から除外）。既存の閲覧・公開条件を維持します。[処理の説明図](docs/releases/v1.0.27/README.md)で役割を確認できます。

薬剤辞書が未設定の対話初期設定では、追加照合を既定「はい」で提案します。利用条件と採用方針の確認後に有効化し、既存辞書や非対話設定を自動変更しません。

詳細は[利用者ガイド](docs/guides/USER_GUIDE.md)と[プラグインガイド](hermes_plugin/README.md)を参照してください。

**AIの抽出は候補です。患者サマリーは確定した処方一覧ではなく、カードの確認済み表示もタスク完了を意味しません。**

## クイックスタート

**導入前提:** macOS 13以降、普段のユーザー（sudo不要）、Xcode Command Line Tools、Homebrew、空き約12GB、利用権限のあるMCSアカウント。Pythonはインストーラーが用意します。
今回の初回受入候補はmacOS・Apple silicon・Slackのstandaloneです。下の例はこの方式を明示します。正式対応・実機受入は別途確認し、既存環境の方式は維持します。
[能力・既定条件・確認済み範囲・残る受入](docs/guides/INSTALLATION.md#capabilities-acceptance)は導入ガイドの単一表で確認してください。

```bash
git clone https://github.com/yusuketakuma/hermes-mcs.git
cd hermes-mcs
./install.sh --mode standalone --preflight   # 読み取り専用の事前チェック
./install.sh --mode standalone               # 依存一式を導入。途中で止まったら修正して再実行
```

事前チェックの「要対処」に表示される`対処:`を確認し、`導入を妨げる問題 0件`になってから導入します。
方式を省略した初回の`./install.sh`は、Hermes経由かHermesなし（[スタンドアローン](docs/guides/STANDALONE.md)）かを尋ねます。Enterの既定は従来どおりHermesです。Hermes連携を選ぶ場合は、上の2コマンドを`--mode hermes`で実行します。
導入後は、そのまま初期設定へ進むか、後で行うかを選べます。後で行う場合は、完了画面に表示される設定コマンドを使います。
初期設定の推奨コースは必要な項目を順番に案内し、詳細コースでは全項目を確認できます。分からない必須情報は中止して確認できます。HermesモードのSlack/DiscordではHermesとの同期も行います。[初めての導入・更新・復旧](docs/guides/EASY_SETUP.md)に操作の流れをまとめています。
本体の初回設定後は、ブラウザーの準備など診断に残った項目を解消します。LINE WORKSの認証・Callback・常駐設定と再診断は[接続ガイド](docs/guides/LINEWORKS.md)で続けます。
既存環境を更新する場合は[更新エージェント手順](docs/guides/UPGRADE_AGENT.md)を使います。移行先版の更新コードで計画・バックアップ・適用を行い、再導入は必要な場合に明示指定します。

**AIに導入を任せる場合**は、リポジトリを開いたエージェントに次のように依頼できます。デスクトップ版のClaude・Codexが一時フォルダへ取得した場合は、`python3 scripts/install_local.py` で恒久的な置き場所へ導入します（[手順](docs/guides/LOCAL_AGENT_INSTALL.md)）。

```text
docs/guides/SETUP_AGENT.md に従って、このMacへhermes-mcsを導入してください。
既存設定と回答を再利用し、まず通知先を選んで進めてください。
認証情報は私が端末へ直接入力します。投稿の収集・通知・既読化は開始前に範囲を確認してください。
```

|---|---|
| [standaloneのSlackを設定する](docs/guides/STANDALONE.md#slackとdiscordの接続準備) | Slack app・接続・許可範囲。Hermes連携は[導入ガイド](docs/guides/INSTALLATION.md)へ |

困ったときは、表示された同じインタープリターで`mcs_setup.py doctor`を実行します。
1.0.13の統一入口は`mcs doctor`です。既定はローカル診断で、LLM通信やサービス状態のprobeは明示指定します。診断が成功しても、SDKの通信・カード操作や配備済みworkerの反映まで検証したとは扱いません。

処理が進んでいるかを確認するときは、doctorで運用記録の鮮度、待ち件数、中断検出、日次バックアップの状態を確認できます。`--probe data` を付けると、収集エラーの原因分類と件数、未取得の本文の最長経過時間も表示します（[収集の診断](docs/guides/COLLECTION_DIAGNOSTICS.md)）。サポートへ状況を伝えるときは `doctor --share` で、患者件数・設定値・パスを含めない共有用のJSONを確認してから渡せます（自動送信はしません）。詳しい工程別の残数・実測速度・条件付きの見通しは、[処理の残数・停滞の確認](docs/guides/USER_GUIDE.md#cli--処理の残数停滞の確認)へ進んでください。未確認の値は0件と区別し、工程間の件数は合算しません。

### 人が確認して判断するための境界

- **記録がない ≠ 対応していない。** アラートは記録上の候補で、対応漏れを断定しません。
- **人承認を記録。** 依頼登録・更新、アラートの却下、閾値変更は所定の承認とreceiptの記録を伴います。MCSへの依頼送信を自動化しません。
- **保存完了後に既読化。** 患者単位の既読化は、取得完了・DBへのcommit・snapshot timestampを条件にします。本文を取得できていない親投稿がある患者は既読にせず、後続の収集で補完します。既読化を指定した定期収集（`--mark-read`）では、直近7日以内に保存した返信のスレッドを1回最大10件確認します。返信は未保存・抜粋のみの内容を先に補完します。ただし、保存済みの抜粋が取得の再試行上限に達した場合は、補完を諦めてスレッドの既読化を進めます。未保存の返信が残る場合は既読にしません。返信の既読化は収集時点に限定できないため、確認後に届いた返信も既読になる場合があります。読取り時に見つかった追加返信は取得ジョブへ登録します。
- **スタンプは観測情報。** 件数・本人反応・観測日時を本文と分けて保存し、未取得と0件を区別します。取得日時は押下時刻ではありません。スタンプだけで確認・担当・業務完了を変更しません。専用の再取得は既定で無効です。有効化すると直近30日活動スレッドの先頭・返信を対象に、活動時期に応じた間隔で最大8件/回を再取得します。押下者取得も既定で無効で、有効化すると直近7日活動スレッドの全投稿について氏名・所属・職種を取得し、氏名・職種をSlackの新形式カード、本文スレッド、LINE WORKSの投稿見出しに表示します。押下者ごとの最後の観測状態を無期限に保持し、取消を観測した時刻を残します。再押下時には取消状態を解除し、過去の全操作履歴は復元しません。未読保持の実証後に定期shadowを有効化できます。既定では反応値を通常表示へ反映せず、公開を別途有効化した場合だけ正常な取得値を表示へ反映します。本人の承知・完了を未応答候補の判定に使う設定も既定で無効で、正式タスクの完了とは別です。
- **スタンプ操作の権限。** 設定した1人の操作者だけが、MCS収集アカウント名義で追加・変更・取消を依頼できます。操作時点の投稿・本人の状態を再確認し、送信前の記録を保持します。結果不明の操作は自動では再送しません。
- **添付の送信範囲。** 通知で送るファイルはMCSのデータ保存先の`attachments`内に限定します。保存先の外を指すファイルは送信しません。
- **認証とログの境界。** no-redirect / no-proxy。定期実行のログへ本文・氏名を出しません。明示的な閲覧出力は別に扱います。
- **説明用の架空データだけをリポジトリへ。** 患者データ・秘密情報・実投稿の匿名化例を入れません。

## よくある質問

<details>
<summary><strong>AIが処方や医療判断を確定する？</strong></summary>

抽出・要約・アラートは候補です。原文と取得範囲を確認して人が判断します。
投稿から抽出した「完了」と、人がタスク操作で確認した完了も区別します。

</details>

<details>
<summary><strong>添付画像やPDFも解析する？</strong></summary>

添付は保存・通知とメタ情報の管理までで、内容の意味解析は行いません。
長文の要約も全件完了を保証せず、入力上限を超える記録は要確認として扱います。
[解析の限界](SECURITY.md)

</details>

<details>
<summary><strong>バックアップがあれば端末故障にも対応できる？</strong></summary>

日次SQLiteバックアップは同じMac上の保存です。端末喪失時の復旧保証にはなりません。
1.0.13の暗号化backup・escrow-key drill・新規配置restoreはローカル支援であり、原本上書きや通知再開の許可ではありません。別媒体・鍵・独立SHA receipt・保持の承認と復元訓練は運用側で行います。[鍵・同意待ちの条件](docs/guides/BACKUP.md)と[復旧の限界](docs/specs/lifecycle-spec.md)を確認してください。

</details>

- **新機能 · DB容量とバックアップの内訳、保守の遅れを確認**
  health.jsonの早期警告に、DB本体の使用量と空きページ量、バックアップの種類別容量、日次・週次保守の経過時間を追加しました。日次保守が2日以上完了していない場合は `db_maintenance_overdue` を表示します。表示を追加しただけで、削除・保持期間・VACUUM・全体の判定は変わりません。

  Slackの添付説明を更新する前に止まった記録が複数ある場合も、全対象の証拠が揃えば、まとめて未送信と確定し、現在の内容への編集計画を作れます。いずれかの照合に失敗した場合は全件を保留します。人が配送先と証拠を確認したカード本体の復旧も、SlackとLINE WORKSで版の不一致により拒否されなくなりました。自動の解除・再送はせず、人の承認付きの既存の復旧コマンドで行います。

  Slack・Discordで、同じ内容の返信が別の投稿の本文を再利用する問題を直しました。Slackの返信カードの薬剤詳細・返信の保存済み件数・タスク一覧・誤りの報告・スタンプメニューも、そのカードの投稿に合わせます。Slackの返信履歴に別のスレッドが記録されている場合や、添付サイズが整数でない場合は、配送済みとの照合や更新に使わず保留します。投稿別カードの更新先が確認後に消えた場合も、配送完了とは記録しません。

- **動作・設定の変更 · 収集エラーを細かく分類し、一時的な異常は3回続いたときに通知**
  監視の警報では、ログイン・認証、時間切れ、通信、保存など18の分類ごとに、何が起きたかと利用者の対処を表示します。時間切れ・通信・取得未完了・取得制限・通知の待ちなど自然に回復しやすい異常は、別々の収集結果で同じ異常が3回続いたときに通知し、観測回数と初回からの経過時間を添えます。収集は通常10分ごとなので、通知は初回からおよそ20分後になります。ログイン切れ・保存できない・設定の誤り・空き容量不足などの重い異常と、一時的でない分類を含む場合は、従来どおりすぐ通知します。分類ごとの対処は[収集の診断](https://github.com/yusuketakuma/hermes-mcs/blob/v1.1.0/docs/guides/COLLECTION_DIAGNOSTICS.md)にまとめています。

**更新時の注意**

- 抽出・意味チェックのコードが変わるため、候補識別値と抽出の更新契約が1回変わります。以前の候補の承認・保留の記録は現行の候補との再照合が必要になる場合があり、旧契約で保留された記録は更新後に1回再試行されます。保存済みの抽出・判定の結果を書き換えたり、全投稿を再解析したりはしません。設定・臨床閾値・抽出世代は変わりません。

- 更新の直後は回数を数え直すため、一時的な異常の最初の通知は更新後に3回観測されてからになります。

- CSDCについて：すでに `sdc.enabled=true` を設定している環境を、この更新が自動で停止・変更することはありません（停止は別の明示操作です）。`optional_features.csdc` は案内の表示だけを決める設定で、通信を止める設定ではありません。すでに送信を始めたHTTP要求をすぐに回収できるとは限りません。登録案内を表示したい場合は、更新後に `mcs setup features`（PATHが未設定なら `~/.local/bin/mcs setup features`）で「案内を表示する」を選んでください。

- 公開医薬品情報の照会でExaへ接続するのは、TinyFishのトークンファイルがない場合だけです。トークンが不正・権限不足・認証拒否・無料枠の上限・一時的な通信障害の場合はExaへ切り替えません。Exaでは強制再取得とETagの確認ができないため、添付文書の定期的な更新確認は未取得として止まります。定期確認は従来どおり `drug_info_watch: false` で止められます。

- 導入済みのAIモデルが固定版と一致しない場合、導入・更新は既存のモデル・取得途中のファイル・起動設定を残して停止します。出典と内容を確認し、固定版のモデルを準備して再実行してください。自動の削除・上書き・再取得はしません。自分で管理するAIサーバーは従来どおり `--no-llm` を指定します。

- 対話での初期設定では、保存の確認に「はい」または1を選んでください。通知先の準備に失敗した場合は、保存済みの設定を残して接続サービスの起動に進まずに止まります。保存先の権限と空き容量を確認して `mcs setup` を再実行してください。

- Slackの長い本文は、最新の計画で長さの超過が確定し、新しい上限も超えると保存記録から確認できる本文だけを通常の巡回で計画し直します。本文の分割数が増える場合があります。他の部品に送信結果不明が残るカードは、その確認が済むまで保留します。結果不明の配送の自動再送や、過去の投稿の一括再配信はしません。
