**通知カードを操作優先に整理し、クラウドAIを用途別のモデルと施設の確認記録で管理**

v1.2.0は、通知カードの確認・担当をボタンにし、処理状況は問題があるときだけ表示する版です。クラウドAIは用途ごとのモデルで送り、新規導入では施設の責任者が確認を記録したサービスにだけ送信します。抽出・添付OCR・患者コンテキスト・更新と復旧の不具合も多数修正しました。DBへの自動追加、作り直しの範囲、再起動と手動操作が必要な条件は「更新時の注意」にまとめています。

| 変更 | 以前（1.1.2） | 今回（1.2.0） | 利用者への効果 |
|---|---|---|---|
| 通知カード | 確認・担当はメニューの中。処理状況を常に表示 | 確認・担当はボタン、依頼・薬剤を先頭に表示。処理状況は問題があるときだけ表示 | 必要な操作と状態がすぐ分かる |
| クラウドAIの使い分け | Anthropicはprofileを設定しないと出力上限が1600トークン | 用途別にHaiku 5.5 mediumとSonnet 5.5 high。5xxはすぐローカルへ回す | 長い応答が切れにくい。患者コンテキストと品質修復の単価は上がる |
| 外部AIの開始条件と記録 | 設定だけで送信を開始 | 新規導入は施設の確認記録に含めたサービスだけへ送信。`/mcs`の閲覧・操作は改ざんを検知できる記録に残す | 送信の範囲と閲覧の経緯を説明できる |

### 新機能

- **担当者宛ての訪問前メモ配送経路を追加**
  この変更だけでは訪問前メモは送信されません。将来、所有者承認と既定OFFの明示ゲートを満たした環境で、訪問日・担当者・原文の状態を夜間に固定し、JST 08:00以降の既存通知tickでLINE WORKSの明示した個人宛てに限り配送できる経路を追加します。共有カードや共有チャンネルへのフォールバックはありません。

- **患者情報の閲覧・操作記録と、新規導入時の外部AI送信の施設確認を追加**
  Slack・Discord・LINE WORKSの /mcs 操作とサマリーは、操作者・操作・患者ID・結果を改ざんを検知できる記録として data/access_log/ に残してから回答します。記録できない場合は、閲覧の回答も患者情報を含む失敗の応答も返しません。新しく導入する環境では、Anthropic・OpenAI・Jevへの送信は、施設の責任者が確認を記録し、その確認に含めたサービスにだけ始まります（mode を明示した設定も同じです）。確認記録の無い既存の環境の動作は変わりません。

- **Anthropic で用途ごとのモデル（Haiku 5.5 medium・Sonnet 5.5 high）を選べるようにする**
  クラウド推論の提供元が Anthropic のとき、用途ごとのモデルを設定で選べるようにしました。再抽出と意味解析は Haiku 5.5 の medium、品質修復と患者コンテキストは Sonnet 5.5 の high が既定です。Sonnet 5.5 の料金（入力100万トークンあたり2ドル、出力10ドル、キャッシュ書込み5分2.5ドル・1時間4ドル、読取り0.10ドル）を追加しました。

- **v3自動更新の実行入口ロック（Q）を業務プロセスへ適用**
  v3へ移行した端末では、常駐・定期の業務プロセスが起動時にruntime-entry.lockの共有ロックをプロセス寿命中保持します。これによりコード切替の排他制御が業務プロセスへ及びます。v3未移行の既存端末では制御ルートが存在しないため何も変わりません。

- **v3自動更新の同意撤回コマンド `mcs update auto-disable` を追加**
  v3自動更新のstanding consentを本人の操作で撤回できる `auto-disable` サブコマンドを追加しました。consentを無効化しlocal_consent_epochを増分してowner stateへ先に耐久保存するため、通信なしでも撤回は確定します。v3状態が未作成の環境では unavailable を返し、既存の更新・監視動作には影響しません。

- **v3 standing consentの人間確認付き確定コマンドを追加**
  `mcs update consent-preview --proposal-id ID --output FILE` でConsentPreviewを取得し、`mcs update consent-confirm --preview-file FILE` で人間確認のうえ同意を確定します。確認証拠はpreview内容へ紐付けてローカルに保存され、再試行時も同じ証拠を使います。

- **v3自動更新の起動fence整合検査と適格性評価**
  v3管理下の業務プロセス起動時に、owner状態とstart-intent記録の相互整合を検査し、不整合なら起動を拒否します。また自動更新の適格性を明示測定値だけで評価する判定関数を追加しました。v3未移行の既存端末では従来どおり起動します。

- **v3自動更新の端末transport基盤（未配線）**
  v3自動更新が中央と通信するための固定path限定transportを追加しました。現時点では呼び出し側（owner orchestration）が未実装のため実行経路には未接続で、既存の更新・監視通信には影響しません。

- **明示設定による定期保存後の隔離復元訓練**
  定期保存の成功後に、明示した周期でDBを隔離復元し、検証と同意待ち配置を行う機能を追加します。作業途中も含めて平文保持を1枠に制限し、失敗や占有を成功扱いにしません。

- **過去世代の抽出結果を作り直す範囲を絞る設定 extract.upgrade_scope を追加**
  config.json の extract.upgrade_scope で、更新後に以前の世代・識別値の抽出結果（LLM抽出、規則抽出、添付OCRページの解析）を作り直す範囲を選べます。未指定と "all" は従来どおりすべて作り直し、"none" は作り直さず、{"project_ids": [...]} はその患者だけを作り直します。新着、本文の編集、同じ世代の品質再試行、人の修正報告はどの値でも止めません。

- **回答の保存されていない支払い済み再抽出を、人が束で承認してローカルで作り直す**
  保存済み投稿の再抽出のうち、支払いは済んでいるのに回答の本文が保存されていないものを対象に、ローカルで作り直してよい単位を確認する cloud-llm local-rebuild-plan と、確認した束を人が承認する cloud-llm local-rebuild-approve を追加します。承認しても、クラウドへの送信・予約・費用の記録は変わりません。承認した単位は、承認した時点からクラウドの再抽出の対象から外れ、次の再抽出からローカルの推論だけで作り直します。承認が使えなくなっても、クラウドの対象には戻りません。

- **介護・介入イベントの正規抽出結果を監査済み証拠で表示**
  canonical抽出が監査を通過した投稿では、これまで未確認扱いだった介護イベントを、出典・証拠範囲・ポリシーが一致する場合に限りタイムラインへ表示します。証明が一つでも欠ける場合は従来どおり未確認のままにし、ローカル抽出への黙った代替は行いません。

- **介入記録を参加者名簿・患者コンテキスト・経過表示へ接続**
  介入記録を発言者IDと種別で過去の参加者名簿へ結び付け、患者さんの全体像・経過タイムライン・訪問前確認へ表示します。発言者の名簿情報と実際のサービス提供者を区別し、対象不明の記録は根拠を残して別に示します。

- **介護介入イベントへ固定detail契約を追加**
  介護イベントに17種の介入・会議・入退所などの区分と、根拠に結び付いた日付・サービス主体を追加しました。同じ出来事の述語と属性を確認し、別の出来事や記録日の混入を防ぎます。タイムラインでは年を推測せず、訂正・否定・第三者の文脈も照合します。公開推論エンジンv1.0と従来のイベント種別は維持します。

- **クラウド履歴の確認失敗に理由コードを追加**
  クラウド履歴の確認に失敗したとき、会計や要求契約の固定エラーコードをログで区別できます。

- **未精算の外部AI利用記録を全件確認するオプションを追加**
  `cloud-llm outstanding --full` で、読取り上限を広げて会計履歴の全件を確認できます。会計履歴が増えると、既定の上限（5秒・10万件）では常に `unknown` になり、未精算の要求を確認する手段がなくなっていました。

- **患者コンテキスト品質状態の件数をヘルス観測へ追加**
  患者コンテキストのレーン別結果と公開件数は10分毎のヘルス収集で観測されていましたが、原典品質監査（lane C）の状態別件数は含まれず、held・failed・unavailable などの滞留をヘルス監視から検知できませんでした。lane_metrics に quality カウントを追加し、quality_state を状態別に集計して health.json の patient_context 節へ載せるようにしました。患者・ソース・本文は一切含まれません。

- **収集の段ごとの所要時間を実行結果に記録**
  収集が遅いときに、未読取得・最新確認・履歴補完のどこで時間がかかったかを実行結果の collect_s で確かめられます。収集の範囲・順序・既読化の条件は変わりません。

- **通知の未完了部品の観測が上限で止まったとき、停止検知時の処理を記録に残す**
  health.json の notify.incomplete_parts が観測上限で不明になったとき、停止を検知した時点の処理を示す observation 項目（phase・stop・budget_s・elapsed_s・remaining_s）を記録に含めます。時間窓が読み取り前に尽きたのか集計途中で超過したのかを区別できます。件数の判定・警告の条件・再送の扱いは変わりません。

- **長時間の書込み取引が内部のどの処理に時間を使ったかを観測できるようにしました**
  患者・メッセージ保存で書込みロックを長く保持した場合、従来の合計保持時間に加えて、意味スナップショット・患者情報読み書き・メッセージ保存・変更検出・通知登録の区間別時間をログへ記録するようになりました。長時間保持（実測43〜71秒）の原因切り分けができ、今後の短縮改修の判断材料になります。動作自体の変更はありません。

- **日次バックアップの一覧・完全検査・保留付き復元と、更新が止まったときの警告を追加**
  手元の日次バックアップと更新前のコピーを mcs_local_backup.py で一覧し、--verify で整合性・スキーマ・SHA-256 を読取り専用で確かめられます。restore は1世代を検証して新しい私有ディレクトリへ通知保留付きで置き、稼働中の DB とバックアップは変えません。採用は mcs_restore.py の承認で行い、配送は保留のままです。日次バックアップが2日以上古いと健康状態が要確認（backup_local_overdue）になります。

- **患者別の時系列チャットをMac内で閲覧**
  公開済みスナップショットの患者一覧・投稿・返信・要約・スタンプ・添付の取得状態と文字記録を、外部チャットを使わず閲覧できます。患者名の右には選択中の患者のコンテキストと根拠を表示します。患者名と本文の検索、以前の記録のページ送りに対応します。

- **過去の確定未送信を証拠付きで運用追跡から分離**
  Slackで長文を拒否された過去の本文部品について、同じ配送先の後続カードが配送済みと確認できる場合に、人承認で運用追跡を終了できます。未配送の事実は保持し、監視の対象件数と運用終了・未回収の件数を分けます。結果不明は全件集計を続けます。

- **未完了partの内訳で復旧作業の順序を決められるように**
  health.jsonのnotify.incomplete_parts.recovery_breakdownとmcs_view recovery_partsのsummaryで、監視対象の未完了partを固定エラー・送信先・種別・使える復旧計画・まとめて承認できる件数で確認できます。送信・確定・承認・警報の判定は変わりません。

- **上限に達した添付OCRを日次で再処理**
  添付OCRが3回失敗した後も、前回の結果保存から24時間以上空けて再処理します。過去の失敗と元資料を保持し、検証に通った新結果を採用します。

- **過去のOCR警報の受付と未回収の資料を分離して記録**
  自動再試行の上限に達した表セル重複のOCR警報を、人承認で受付記録へ残せるようにします。同じ警報だけの反復通知を停止し、OCRの失敗・未回収件数・原資料への参照は保持します。新しい失敗や照合不能な状態は引き続き警報対象です。

- **不確かな表のOCR除外と失敗の明示再処理**
  表構造を検証できない添付を、明示設定によりOCR採用対象から除外できます。原本未評価の参照と失敗履歴を残し、設定を戻すと未完了扱いへ戻します。失敗資料を待機時間にかかわらず再評価するコマンドも追加します。

- **患者コンテキストを消去して作り直す人承認コマンドを追加**
  患者コンテキストの公開版・調査結果・品質判定・生成枠と、その外部AIの会計記録を、人の確認と記録を伴って消去できるようにしました（cloud-llm context-reset-plan・context-reset）。消去の前にバックアップを取ります。使った額は引き継ぎ、上限判定と使用額の表示は消去の前と同じ額を数え続けます。

- **旧契約世代の抽出checkpointをsupersededとして識別**
  過去の契約世代で書かれた抽出checkpointが現在の契約と一致しない場合、未知の破損と区別して prepare_context_load_superseded として分類します。現時点では引き続き保留され、旧行は変更されません。

- **試行記録がない保留中のファイル共有を承認付きで復旧可能に**
  配送が途中で止まりfile_groupがpendingのまま試行記録を持たない場合、journalがそのpartを開始していないことを証明し、人の承認があれば未送信として確定できます。滞留していたカードの更新が再開し、後続の通知でファイルを再利用できます。

- **保存済み保護属性を単回修復へ渡す内部受付を追加**
  抽出器の内部受付に保存済みの保護対象を渡すと、原文で再確認できる属性の欠落を既存の単回修復で扱います。通常ジョブへの修復入力の接続と、修復属性の出所を照合する採用経路は未実装です。この変更だけで既存の保留は解消しません。

- **提供元設定の保存の最後で止まったときの保留を、人の確認で解除できるようにする**
  提供元別設定の保存中に電源断や強制終了が起きると、保存中の記録（.provider-settings-pending.json）が残り、書込み処理がすべて保留されたまま解除できませんでした。今後は mcs_setup.py provider-pending-finalize を --confirm-human と理由付きで実行すると、保存後の状態を確かめたうえで記録を退避し、解除できます。

- **保存済み投稿の再抽出に限り、期間と上限額を付けてクラウド送信を再開できる**
  過去の投稿を現行の抽出世代へ上書きする処理を、所有者が指定した終了日時と期間予算の範囲でクラウドへ送れます。既定はOFFで、指定しない限り送信先と費用は変わりません。再開中は、患者名を含む投稿本文を外部APIへ送ります。

- **リリース動画をリポジトリの素材から自動生成する開発ツールを追加**
  docs/screenshots/release-video.json のシーン定義（タイトルカード・Slack/LINE WORKS ギャラリー・Discord 静止画）と macOS の say 音声合成、ffmpeg から、縦型 1080x1920 のナレーション付き mp4 をローカルで生成できます。MCS 本体の動作への影響はありません。

- **DB 復元の承認を端末からも送れるようにする**
  スキーマ変更を伴う更新の巻戻しで、DB 復元の承認を端末から送れるようになりました。これまで承認はチャットの /mcs からだけで、独立実行（runtime_mode=standalone）では承認待ちの間 /mcs が使えず、承認する手段がありませんでした。今後は mcs_update.py restore-approve で、/mcs と同じ承認（ops.restore_approve）を命令の受付場所（data/cmd）へ送れます。承認の検証と処理の経路は /mcs と同じです。

- **患者集計の持ち越しを調べるための時間と人数を記録**
  定期収集の結果に rollup_timing を追加し、患者集計の走査時間、再構築時間、再構築に残された秒数、完了人数、未完了人数、患者ごとの最大処理秒数を記録します。

- **semantic drain の run.lock 保持区間を計測するログ項目を追加**
  バックログ semantic drain が run.lock を保持したままモデル通信の合間に費やした時間を、cloud_backlog_pass イベントの lock_hold 項目（hold_max_s・hold_sum_s・hold_count）で記録するようになりました。処理結果や通知内容に変更はありません。

- **収集が止まったとき、止まった処理と原因・対処を表示**
  収集の実行全体が失敗したとき、すぐ届く「収集処理の失敗」通知と監視警報に、どの処理で止まったか（例: 未読投稿の取得、通知の送信）と、原因の分類に応じた対処を表示します。これまでは「mcs_setup.py check で確認」「data/mcs.log の末尾を確認」だけで、ログを読めないと原因が分かりませんでした。ログイン切れの通知にも止まった処理を添えます。

- **CSDCへの固定テレメトリ送信を別同意で追加**
  mcs telemetry enableで明示的に許可した場合だけ、ハードウェア・稼働状態・実行ログのイベント名・ヘルス状態の固定項目を1時間間隔でCSDCへ送信します。患者情報・秘密値・ホスト名・パス・シリアル・MACアドレス・ログ本文は送りません。状態監視の接続・別の送信同意・state_rootがない環境では送信されません。中央側の受信設定（TELEMETRY_ENABLED）が無効な間はサーバーが拒否します。

- **専用ChromeでのMCSログインを1つのコマンドで案内**

### 動作・設定の変更

- **AIの受付制御を有効にしていると診断がエラーになり、この版への更新が完了しない**
