## [1.3.0] — 2026-11-26

**患者コンテキストと在宅ケアを拡張し、Jev 1.14.0へ更新**

v1.3.0は在宅ケア台帳・訪問/処方記録、医薬品検索と患者横断検索を追加します。患者コンテキストの品質確認と患者選定の競合を修正し、Jev 1.14.0への更新、抽出・添付・通知・スタンプ・クラウド処理の改善も含みます。更新時は各記録に示す適用条件を確認してください。

**この版は初めて外部へ公開するリリースです。** 社内運用で検証してきた内容を、外部の事業所でも導入できる形に整えたものとして公開します。

| 以前 | v1.3.0 | 利用者のメリット |
| --- | --- | --- |
| 在宅ケアの患者台帳・職員・訪問・処方歴をローカルで一元管理する画面がない | 患者画面に台帳と訪問・処方歴を追加 | 患者ごとの在宅ケア情報をまとめて確認・記録できます |
| 医薬品辞書からの共通検索と、患者の言及を横断して探す入口がない | 検索・照会の共通入口と患者横断検索を追加 | マスター差分や添付文書改訂に関連する患者を探せます |
| 常駐処理の状態不明時の誤起動、上限超過辞書の再走査、クラウド行の再選定が起こり得る | 状態不明時の起動を抑止し、辞書上限結果と条件不変の行を保持 | 不確かな状態での起動や同じ対象の繰り返し処理を抑えます |
| 患者コンテキストの品質確認と患者選定が競合時に不整合を起こし得る | 入力の再照合と選定ロックの処理を修正 | 対象患者の情報を確かめながら品質確認を続けられます |

### 新機能

- **日次サマリーに処方期限の近い患者の一覧を追加**
  朝の日次サマリーに「処方期限の記録」の節を追加し、終了日まで期限アラートの検出範囲（expiry_ahead_days、既定3日）以内か終了日を過ぎた期間表現を、終了日の順に患者ごとに並べます。調剤・配達・訪問の段取りを1通で確認できます。抽出した期間表現の終了日であり、処方期間の確定ではありません。

- **在宅記録などから使う医薬品の検索・照会の共通入口を追加**
  在宅記録などの機能から使う、医薬品の検索・照会の共通入口（drug_catalog）を追加しました。設定した承認済みの薬剤辞書から、名称・別名・公式コードの部分一致で製品を探します。別名の一致は件数で打ち切らず、製品名の順に返します。未設定・未承認の辞書では推測せず何も返しません。ローカルのチャット表示の処方薬の入力欄は、この入口で薬を検索します。

- **薬剤名・マスター差分・添付文書改訂から、言及のある在宅患者を一覧にする**
  出荷調整・回収・販売中止・添付文書の改訂を受けたとき、mcs drug patients で該当する薬の言及がある患者を横断して確認できます。薬剤名、master-impact の出力、まだ受け入れていない添付文書の改訂のいずれかで探し、患者ごとに言及件数と最新の言及（投稿日時・投稿ID）を新しい順に示します。添付ファイル（OCR）の言及は元の投稿の日時で並べます。言及は服用中の確定ではなく、未抽出・未取得（返信の取得漏れを含む）・取得失敗（失敗した取得ジョブを含む）の件数も表示します。

- **在宅記録の台帳をローカルバックアップの対象に追加**
  在宅記録の台帳が $MCS_ROOT/data/homecare.db にあると、原本 DB と同じく毎日検証したコピー（homecare-YYYYMMDD.db、3世代）と更新を適用する前のコピー（homecare-preupdate-*.db、新しい3つ）が data/backups に作られます。台帳は手入力の記録で MCS から取り直せないためです。mcs_local_backup.py の list --verify で検査し、restore で新しいディレクトリへ戻せます。台帳のコピーが作れないときは、適用先の版へ進まずに更新を止めます。

- **ローカルの患者画面に在宅ケアの患者台帳・職員・ケアチームを追加**
  Mac内の患者タイムライン画面を --homecare-db 付きで起動すると、事業所の患者台帳（連絡先・キーパーソン・訪問先の注意・利用状態）、資格付きの職員名簿、患者ごとのケアチーム（担当者と役割）を登録・編集でき、患者を MCS の患者と人の確認で対応付けられます。職種に共通の機能の上に職種別モジュールを載せる作りで、今は薬局モジュール（薬剤師の資格と担当薬剤師の役割）があります。旧 zaitaku-calender の機能をこのMacへ移す最初の段階です。

- **在宅ケアの患者画面を事業所のスマホから使える常駐モードを追加**
  Mac mini 以外の端末（スマホなど）から使う Mac だけ、install.sh --with-tailscale で Tailscale を入れ、mcs setup remote で tailnet の中だけに公開し、患者画面と在宅ケア台帳を常駐させます。誰が使っているかは Tailscale のログインで見分け、職員として登録したログインの人だけが使えます。訪問薬剤管理の実施の記録・変更・中止は薬剤師だけです。

- **在宅ケアの台帳に訪問歴・処方歴・訪問時の情報・訪問ルートを追加**
  --homecare-db 付きで起動したローカルの患者画面で、訪問の予定と実施、薬局の処方（薬剤・用量・用法・日数）を記録でき、訪問時に必要な連絡先・注意事項・ケアチーム・次の予定・最近の処方を1画面で見られます。日付ごとの訪問予定の一覧も追加しました。--route-settings を指定したときだけ、その日の訪問を回る順番を作れます。この機能は「ルートを作る」を押したときに、患者の住所を国土地理院の住所検索へ、位置を openrouteservice へ送ります。氏名などは送りません。

- **Jevへの要求と回答の内訳を処理状況の確認で表示**
  semantic_observe.py の出力に jev_effect を追加しました。指定期間（--days、既定14日）について、保存済みの記録から次の件数を表示します。Jev要求数（処理・ジョブ種別ごと。要求記録の保持期間7日の範囲）、投稿ごとの判定、抽出監査の判定と緊急度の組（投稿ごとに最新の記録）、患者コンテキスト品質確認の記録数。読み取り専用で、送信・設定・既読化は変わりません。

- **Jevの新しいモデルを知らせ、確認に合格したときだけコマンドで切り替える**
  Jevを使う環境（意味解析がoff以外、キーあり、日次予算が1以上、施設確認でJevが許可済み）では、mcs_setup.py check が1日1回までモデル一覧を取得し、新しい固定版があれば情報として表示します。自動では切り替えません。mcs_setup.py jev-model --to で、合成データの確認に合格したときだけ人の確認と承認記録を伴って切り替えられ、完了済みの意味解析は新しいモデルでやり直されます。

- **ローカルの患者画面へMCSから取得した情報を漏れなく渡す**
  ローカルの患者ワークスペースで、MCSから取得している情報（緊急度、要約の状態、スタンプを押した人、添付とOCRの状態、取得状態、連携サマリー全文、MCS登録データなど）をもれなく表示します。未取得・取得失敗・判定中は「なし」や0件と区別します。検索は添付OCRの文字も対象です。通知のまとめ（🧾）には「他N件」の行が増え、「Loop候補（semantic shadow）あり」を「未完了のやり取りの候補あり」に改めます。画面は起動し直し、通知側は gateway と LINE WORKS アダプターの再起動で反映されます。

- **ローカルの患者画面で訪問前の確認ノートや経過などを表示**
  Mac内の患者タイムライン画面で、通知カードから開いていた患者別の画面（記録のまとめ、全体像、前回から変わったこと、連絡・返答の確認、訪問前の確認ノート、経過タイムライン、出来事・検査・観測の記録、記録の食い違い、引継ぎ用の記録、退院・移行時の経過）と未解消のシグナル、投稿ごとの薬剤を選んで表示できます。外部チャットを使わずに同じ内容を確認できます。

- **薬局から医師への照会・提案の返答待ちをアラートで知らせる**
  自局から医師へ出した処方・薬の照会や処方提案に、スレッド内の他の人の返信もルーム内の医師の投稿も見つからないまま3日（request_response_days）を過ぎると、アラート「照会の返答未記録」の候補にします。返事待ちの照会を覚えておく負担を減らします。電話・FAXなど記録外の返答は判定に含みません。自局の照会は「処方依頼」（rx_request_visibility）には出なくなります。

- **Macの性能に応じて導入するローカルAIモデルを自動選択**
  新規導入時、32GB以上のMacではQwen3.8-27B、48GB以上ではQwen3.6-35B-A3B、128GB以上のMax/UltraチップではQwen3.5-122B-A10B、512GB以上のUltraチップではQwen3.5-397B-A17Bを選びます。低スペックや検出不能のMacでも下限は従来のQwen3.5-9Bです。すでに対応済みのQwenモデルが導入されているMacでは、そのモデルを維持します。

- **v3自動更新のownerを定期観測する**
  v3自動更新に移行済みの端末では、10分ごとの定期処理がownerを1回だけ観測し、届いている作業の再開・証拠送付・health報告を行います。未移行の端末では何もせず終了し、従来の自動更新経路へ fallback しません。


- **費用上限などの変更を設定の保存ごとに記録**
  提供元別設定の環境では、設定を保存するたびに、保存した入口と、費用上限・期間予算・終了日時・API別上限・Jevの件数と期限の保存前後の値を小さな私有の記録に残します。cloud-llm budget・providers に最後の上限変更と、現在の設定が記録された保存の結果と一致するかを表示し、budget --history N で記録を確認できます。上限の判定・費用の集計・承認条件・設定内容は変わりません。

### 改善

- **クラウド4モデルの料金を再確認し、確認期限を12月24日に更新**
  Claude Haiku 5.5、Claude Sonnet 5.5、GPT-6 Luna、GPT-6.1 Sol の公式料金を2026年11月24日に確認しました。入力・出力・キャッシュ・長文の単価と適用条件は前回と同じです。新しい送信には11月24日版の料金表を使い、すでに予約した処理は予約時の料金表で精算します。

- **外部AIの提供元ごとの判定を提供元の定義に集約**
  外部AIへの送信内容・費用見積り・予算判定・保存済み記録の扱いは変わりません。設定の保存前確認では、Anthropic を選んだときも患者コンテキストと品質修復に使うモデルと推論の強さを表示するようになりました（これまでは OpenAI のときだけ表示）。

- **mcs/core/ の補助モジュールを役割別のフォルダへ移動**
  利用者から見える動作・設定・既定値・通知・既読化・承認条件は変わりません。開発者向けに、mcs/core/ 直下の補助モジュール13個を ledger/・runtime/・records/ の3フォルダへ移しました。import 名は変わりません。

- **収集の派生処理の内訳時間を記録する**
  収集の derive 段の中で、リアルタイム抽出（derive_llm）と見守り候補の判定（derive_signals）にかかった秒数も、段別の経過時間に記録します。health.json と実行ログで、derive の時間がどこで使われているかを確認できます。処理の内容と順序は変えていません。

- **閲覧権限を失った患者はexportから除外し、権限のあるarchiveはarchived行を付ける**
  日次export（brain_export）で、取得が拒否された患者（fetch_state=forbidden または権限系の fetch_reason）は患者ページを生成せず既存ページを削除し、その未解決シグナルも出力から除外するようになりました。除外した患者数は実行結果とmeta.mdに出ます。権限が戻れば再生成されます。権限のあるアーカイブは従来どおり出力で先頭に archived: true の1行が付きます。

- **意味解析・抽出監査に使う Jev のモデルを jev-1.14.0 に更新**
  Jev（TypeSafe）のモデルを jev-1.13.0 から jev-1.14.0 に変えます。料金・文脈上限・要求と応答の形式は公式資料上同じで、多言語の扱いが改善された版です。モデルが変わるため、更新後は意味解析が有効で処理対象のプロジェクト（一時停止中や対象外を除く）について、完了済みの意味解析も定期処理が少しずつ登録し直し、患者コンテキスト品質の判定とあわせて新しいモデルで一度やり直されます（日次の要求上限の範囲内）。抽出監査は、抽出が変わるまで既存の監査結果をそのまま使い、新しい監査から jev-1.14.0 を使います。

- **通知部品の遠隔確認スクリプトが、実行したユーザー名を操作者として記録**
  開発用の診断スクリプト scripts/diagnostics/notify_remote_verify.py が --emit で書く確認コマンドの操作者を、固定の名前ではなく実行した OS ユーザー名にしました。理由欄から特定の作業日時の記述を除きました。通常の収集・通知・既読化には影響しません。

- **権限の弱い .env ファイルは読み込まなくなりました**
  ログインの予備パスワード（MCS_PASSWORD）や初期設定のBotトークンを読む .env ファイルが、所有者以外から読める権限（例: 644）・他者所有・シンボリックリンク・上限超過の大きさだった場合、そのファイルからは値を読まず、従来の未設定と同じ扱いになります。初回の読取りで警告（local_file_permissions_weak）をパスごとに1回だけ stderr に出します（値は出力しません）。config.json の警告だけで読む挙動は変わりません。

- **患者画面のレイアウトを見直し（患者台帳は読む画面が先、訪問予定はカード表示、スマホは下のタブバー）**
  ローカルの患者画面で、上の見出しが1行になり、患者を開くと最初に読むための「訪問時の情報」が出ます（編集は2つ目のタブ「台帳を編集」）。「訪問予定」は、状態・住所・注意事項が分かるカードと7日分の件数の帯、職員での絞り込みになりました。MCS では、投稿を開いていない間は右の欄に「いまの状況」（未解消のシグナルと連絡・返答の確認）を表示します。スマホでは画面の切替が下のタブバーになり、患者一覧は「患者」ボタンで開く全画面の一覧になりました。記録の内容・権限・保存の条件は変わりません。

- **抽出監査の指摘が残る投稿を、再抽出の再開期間中にクラウドで1回だけ再抽出**
  抽出監査の指摘がローカルの再抽出後も残る投稿を、再抽出の再開期間（cloud_llm.reextract_backlog_until）中だけ、直近60日に限りクラウドでもう1回再抽出します。本文に加えて監査が指摘した項目名・緊急度の指摘も送ります。上限はAPI要求1回ではなく本文1つにつき1回（分割・修正の要求を含む）で、同じ本文へ2回目は送りません。なお残る投稿は mcs view qc の確認候補に出ます。ローカルの再抽出を済ませた投稿は通常の再抽出としては送りません（人の ⚠ 報告と世代更新は従来どおり）。

- **未読の意味解析jobを止め抽出QCだけをまとめて処理**
  意味解析は有効だが要約・ループの結果readerがない設定では、意味解析jobを実行せず、extract_qc=annotateの抽出QCだけを常駐workerが最大8件、約5分の新規ジョブ開始時間内に開始します。開始済みjobは各自の予算内で続き、全体を5分で打ち切るものではありません。readerがある設定では意味解析jobは1件ずつ処理し、Jev上限時にbacklogで待機するのは抽出QCだけです。新着用realtimeレーンの扱いは変更しません。

- **送信から1時間後も自分のスタンプが操作どおりの状態にないと確認できた場合に操作を終了**
  送信から1時間以上たった時点で、MCS上の自分のスタンプが操作どおりの状態になっていないと確認できた場合は、その操作を終了します。自動では再送しません。終了後は同じ投稿で新しい操作ができます。自分のスタンプの状態を取得できない間は「確認中」が続きます。

- **使われない意味解析の判定を作らない**
  要約（summary_mode）とループ（loop_mode）がともに off の設定では、通常の取込・再処理で意味解析ジョブを作らず、待機中のものも実行しません。人が確認した保留解除は既存の解除契約どおり置換jobを保留状態で残し、患者コンテキストは保留解除後にそのjobを待たずに進みます。


- **cloud処理を初回送信と5回までの再試行に統一し、課金済み応答を安全に再利用**
  個別チャット抽出・意味解析・患者コンテキスト管理・Jevのcloud処理で、失敗時に初回送信へ最大5回の再試行を行う上限へ統一しました。入力束縛の一部だけが変わっても論理的に同じpromptの課金済み応答は、追加送信せず再利用します。HTTP状態・request id・固定の失敗区分に加え、課金済み応答がローカル検証で不合格になった場合は固定の失敗理由を会計artifactへ記録し、その応答を再利用せず上限内で再試行します。患者データ本文やprovider応答本文は失敗理由へ記録しません。

- **遠隔接続の患者画面で、MCS の記録の閲覧を閲覧記録に残す**
  Tailscale 経由の常駐モードで患者一覧・投稿・検索・記録のまとめを開くと、表示の前に Tailscale のログイン名・患者ID・時刻を `data/access_log/` へ記録します。検索語・本文・患者名は記録しません。記録できないときは表示しません。この Mac だけで開く秘密URLのモードと、在宅ケア台帳の表示は対象外です。

- **患者コンテキストの品質確認が止まった箇所を記録**
  患者コンテキストの品質確認（資料と概況の Jev による確認と修復）が通らずに終わったとき、クラウド処理の記録（patient_context_pass）に、止まった確認の種類を固定の短いコード（quality_detail）で残します。処理期限、設定・鍵・判定方針の変更、確認中の別の書込み、修復の予算や送信の見送り、保存直前の再確認などを区別できます。記録は観察のためだけで、判定・保存される値・再試行の間隔は変わりません。本文・患者を特定する情報・設定値は含めず、一覧にない値は unclassified とします。

- **意味解析の要約・loopの既定をassistに変更**
  意味解析の mode が有効な環境で summary_mode・loop_mode を設定していない場合も、既定で assist モード（補助表示）として要約・loop の意味解析が動くようになります。これまで既定は off で意味解析 job は実行されず pending に残るだけでしたが、この変更で未設定の環境でも job が実行され、補助結果が蓄積されます。ローカルLLMの処理量と Jev の要求数が増えます。明示的に off を設定すれば従来どおり無効にできます。extract_qc の既定は off のままです。

- **意味解析backlogの要約生成を非専用workerでもcloudへoffload**
  semantic backlogを非専用workerの常駐処理が拾った場合でも、要約生成stageはownerが開いたsemantic backlog window内でcloud推論を使うようになりました。facts抽出stageは従来どおり専用backlog workerだけがcloudへ送り、realtime laneと新着10分以内の対象はcloudへ送りません。loop候補生成はもともとfactsからの決定的変換で、関係評価はJev APIのため、今回のlocal LLM offload対象ではありません。

- **独立接続の SDK を SHA256 と照合して導入**
  `install.sh` は Slack・Discord の SDK とその依存（合わせて13個）を、ハッシュ付きの一覧 `deployment/requirements-standalone.lock` から `--require-hashes` で導入します。記録と中身が違う配布物は導入しません。版は従来の `requirements-standalone.txt` と同じです。

### 不具合修正

- **測定したことが明記された検査値を読み取る**
  「Cr 1.2mg/dLを測定しました」のように、数値・単位に続けて測定したと明記した引用を検査値として表示します。比較・否定・測定予定や、そのまま投薬の説明に続く記述は未確認の候補にとどめます。

- **添付ページのローカル解析の保留理由が「原因未特定」になる問題を修正**
  添付ページのローカル解析が処理期限の超過などで保留されたとき、健康レポートでは原因が「未特定」と表示されていました。そのページの解析処理自体が保留を返したときは、その処理が記録した固定の理由（処理期限の超過、処理枠の空き待ち、ローカルLLMの未到達など）を保留の原因として表示するようにしました。結果を返したのに保存できなかった場合と、理由が記録されなかった場合は、従来どおり「未特定」と表示します。解析・保存・既読化の条件は変わりません。

- **クラウド意味解析のロック保持時間の記録を正す**
  クラウド意味解析は、ロックを手放して対象を選んでいる時間とロックの取り直しを待つ時間も、ロックを持ち続けた時間として記録していました。この時間を選定の時間として分けて記録します。選定の後にロックを取り直せなかった回は、記録を残して常駐処理が次の回へ進みます（従来は記録なしで終了）。health.json には直近の収集の段別の経過時間も載せます。

- **クラウド費用チェックの照合を軽くして、クラウド抽出が進むようにする**
  クラウド抽出とクラウド意味解析の送信前の費用上限チェックが速くなり、クラウド抽出が送信まで進むようになります。これまでは DB への書込みのたびに期間内の利用記録をすべて照合し直し、1回に十数秒かかっていました。今回からは既存の書込み時ガードの回数が前回と同じなら、増えた記録だけを読み直します。ガードが無い場合や回数が変わった場合は従来通りすべてを照合します。費用上限と二重送信防止の条件は変えていません。

- **ほかの表への書込みで温めた費用集計を捨てないようにする**
  稼働中の DB で、ローカル作り直しの承認が費用集計の作り直しで時間切れになりにくくなります。これまでは集計中にほかの表への書込みがあると温めた集計を捨て、承認の書込みロックの中で今月分を作り直していました。今回からは集計を残し、次に使う前に照合し直します。費用関係の記録が変わった場合やガードの無い DB では従来通り全件を照合します。費用上限と二重送信防止の条件は変えていません。

- **クラウド再抽出が同じ持ち越し投稿を繰り返し選定する問題を修正**
  クラウド再抽出で、支払い済み結果の確定できない投稿と、旧世代の保留記録しか持たない投稿が、パスごとに再選定されて重い準備処理を繰り返していました。条件が変わっていないと証明できる間は、これらの投稿が既存の復帰間隔（6時間）の有界な claim を保持するようになり、その間に後続の投稿が処理されます。条件が変われば従来どおり通常の選定経路で見直され、支払い済み履歴・旧チェックポイント・再送防止の条件は変わりません。

- **別名数が上限を超える薬名辞書でヒント生成が毎回全走査する問題を修正**
  別名が上限（20万件）を超える辞書では、薬剤言及ヒントの生成のたびに別名表を最初から数え直していました。上限超過の結果をキャッシュするようにしたため、2回目以降は再走査せず即座に判定が返ります。結果の status=incomplete という扱いは変わりません。

- **薬剤辞書照合の期限打ち切りで健康レポートが低下扱いになる問題を修正**
  薬剤辞書との照合が実行時間の期限で途中まで進んだ場合、要約や通知の後回しと同じく次回に続きを処理する延期として記録し、健康レポートを低下扱いにしなくなりました。1件も進まずに打ち切られた場合は、従来どおり要確認のエラーとして残します。照合の結果と対象は変わりません。

- **人が確認して実行する保存操作が、定期処理の合間に書込みロックを取れるようにする**
  クラウドの停止・再開、ローカル作り直しの承認、取得ジョブの操作、外部送信の確認など、人が確認して実行するコマンドが稼働中でも通りやすくなります。これまでは書込みロックを5秒しか待たず、定期処理や常駐処理が交代で握っている間はほぼ必ず「ほかの保存処理が終わってから再試行」で終わっていました。今回から最大180秒待ち、待つ間はその旨を表示します。

- **新規導入が設定の保存前に止まっても、同じコマンドの再実行で続きから導入できるように修正**
  新しい Mac の初回導入が、通信の失敗、Homebrew・Python 環境・Hermes の導入失敗、Ctrl+C などで設定ファイルを作る前に止まった場合、原因を直して同じコマンドを再実行すれば初回導入を再開します。これまでは「初回導入が中断された記録があります。担当者に確認してください」で止まり続け、利用者が自分で復旧できませんでした。止まったときの表示も、再実行で再開できることを案内するようにしました。

- **Hermes 経由の新規導入が、Hermes の初回起動に時間がかかって必ず止まる問題を修正**
  新しい Mac に Hermes 経由で導入すると、Hermes の最初のコマンドが同梱スキルの準備などで1分以上かかり、導入の安全確認（30秒以内に Hermes の定期実行一覧を確かめる）が間に合わず「初回導入の安全性を確認できません」で止まっていました。導入の段階2で Hermes の初回準備を時間制限なしで済ませてから確認するようにしました。

- **単発のカード通知が、ファイル公開の一時的な失敗で保留に止まる問題を修正**
  緊急通知など1件ずつ配信するカードで、配信の記録を確定したあとにファイル公開だけが失敗しても、失敗回数に数えなくなりました。これまでは一時的なディスク障害などが数回続くと、確定済みの通知が保留に入り再配信されませんでした。公開されなかった分は、まとめて配信するカードと同じく既存の復旧処理が公開し直します。

- **手動のJev操作が背景処理の実行中にすぐ失敗する問題を修正**
  Jevの疎通確認やjev-valueなどの手動コマンドは、背景処理が保存の排他を持っている間も最大30秒（要求のタイムアウトが短ければその長さ）待ってから利用枠を予約します。これまでは1回だけ試して usage_lock_busy で止まっていました。待機中に更新が始まった場合やコードが入れ替わった場合は usage_code_changed で送信せずに止まり、台帳のSQLite書込み待ちが長引いた場合は異常終了の代わりに再試行可能な usage_ledger_busy を返します。

- **Jev を導入していない環境と Jev の対象外の患者で、外部AIの患者コンテキストが公開待ちのまま止まる問題を修正**
  Jev が未導入または対象外の患者でも、外部AIの患者コンテキストを確認未実施として安全に公開できるようになります。v1.3.0 では QA_VERSION を1から2へ更新するため、旧PASSは新しい版の確認として再利用されず、背景再確認まで概要が一時的に非表示になります。

- **カルテ更新時の依存確認で読み込む記録を削減**
  カルテの更新時は、対象患者の記録と患者を指定しない共通の記録を索引で読みます。他の患者の記録が増えても、その全件を走査せずに変更の有無を確認できます。

- **検査値の判定で、検体の節・続く検査値の単位・長い行での停止を修正**
  尿・髄液・胸水・腹水・便・喀痰の見出しの下に書かれた白血球・総蛋白・総ビリルビン・Ca・Mgは、間に別の結果や改行・句点があっても、血液の見出しか結果のあとの空行までは裏付け済みにせず、未確認の候補として値を残します。K・Na・Caなどの値のあとに空白を挟んで「Cr 0.9」「Cr:0.9」のような既知の検査値が続く場合は、再び裏付け済みと判定します。長い行で判定が止まることもなくなります。

- **launchctl の状態を確認できない常駐処理を未読込として起動する問題を修正**
  `mcs_setup.py services` で launchctl の状態確認がタイムアウトした常駐処理を未導入とみなして起動しようとする問題を修正しました。読み込み状態を確認できない場合は起動・再読込を行わず、状態不明として問題に報告します。

- **承認済みのローカル作り直しが背景抽出に埋もれず進むように修正**
  人が承認したローカル再抽出が、新着や未処理の抽出に埋もれて進まない問題を修正しました。通常の背景処理では承認を再確認して先に選び、新着限定の処理では空き枠を使います。新着が続く場合も一定間隔で承認済みの処理に枠を割り当てます。最古・アーカイブ専用の処理、新着・対話の優先、意味解析の進行、対象の照合、二重課金防止は従来どおりです。一時的な読取失敗は再検証し、採用済み・承認条件が変わった対象は通常順のローカル処理に戻します。

- **手動の規則抽出と修復診断で過去の抽出を作り直す範囲を指定できる**
  手動の規則抽出も extract.upgrade_scope に従います。添付OCRは、処理開始後に対象を絞った場合も範囲外の過去世代を作り直しません。新着や訂正依頼は従来どおり処理します。

- **通知の検索・日時・記録の状態の文言を実際の状態に合わせる**
  Slack・Discord・LINE WORKSの🔎検索で、アーカイブ済みや閲覧権限のない患者は理由を表示し、一致なしは「調べた範囲の取得済み原資料には見つかりませんでした」と表示します。日時のない行は「日時未取得」等と表示し、グループのルームにはMCSリンクを付けません。反映にはHermes gateway（またはstandalone）とLINE WORKSアダプターの再起動が必要です。

- **再起動で添付OCRの受付と再抽出の承認が無効になる問題と、待ち合わせで添付OCRの健康状態が揺れる問題を修正**
  Mac を再起動すると、DBを置き換えていなくても、人が受け付けた添付OCRの失敗とローカル再抽出の承認がすべて無効と判定されていました。DB の同一性を inode で確かめるように直し、復元・置換・複製したときだけ無効になります。修正前に受け付けたOCRの失敗は受付のやり直しが必要です。また、書込みロック待ちで始まらなかった添付OCRの実行が前回の結果を上書きしなくなり、健康状態が誤って処理保留に変わらなくなりました。

- **別の患者の更新で患者コンテキストの品質確認が止まる問題を修正**
  品質確認の途中で別の患者の記録が更新されても、確認に使った原文や回答がそのままであることを確かめて処理を続けます。対象の原文や回答が変わった場合は、古い結果の保存を見送ります。

- **ほかの患者の更新が重なっても品質確認済みの原文や概況を保存**
  クラウドで作った患者コンテキストの品質確認後、ほかの患者の記録が更新されても、確認に使った原文・回答・調査結果が一致すれば公開へ進みます。対象の記録が変わった場合や照合できない場合は保存を見送ります。

- **患者コンテキストの候補確認中に別の患者の処理を進める**
  ある患者の原文や解析結果の確認に時間がかかっていても、別のワーカーが次の患者を選んで処理できます。

- **抽出・意味解析の待ちが溜まり続ける問題を軽減**
  意味解析とクラウド再抽出が、書込みロックの待ちと重い選定処理に時間を取られてほとんど進まなくなっていた問題を直しました。常駐の意味解析は前処理を10分に1回に減らし、抽出結果の保存とクラウド意味解析の書込み待ちは0.2秒間隔でロックを確認します。再抽出の選定SQLは作り直さなくなり、再処理の見直しで試行回数が0に戻らなくなりました。既読化・二重送信防止・人の承認の条件は変わりません。

- **同じ内容の投稿判定を Jev に繰り返し送る問題を修正**
  添付の保存や返信件数の更新だけでスレッドの識別値が変わり、Jev に送る内容が同じなのに投稿判定をやり直して有料リクエストを使っていました。送信内容が同じ場合は保存済みの判定を引き継ぎ、Jev を呼びません。返信の追加・本文の編集では従来どおり判定し直します。

- **Jevの日次上限で待機した抽出QCを、保存した回答の続きから再開**
  バックグラウンドの抽出QCは、処理中にJevの日次上限に達すると、得た回答を保存して待機します。次の枠では同じ抽出結果の未回答の質問だけを送ります。常駐workerがまとめて処理する場合の約5分は新しいジョブを始められる時間です。開始済みのジョブは各自の予算内で保存まで続けます。

- **意味チェックの再修復待ちで監視が劣化しないようにし、決定的な保留で再処理が止まる問題を修正**
  実行世代が古い意味チェックを1回に1件ずつ修復する順番待ちは「延期」に分類され、それだけでは監視状態が劣化しなくなりました（実行記録は partial のまま）。複数投稿を対象とするジョブが、全対象とも入力の変化を待つ決定的な理由で保留されたときは、単一対象と同じく1時間待ってから再選択します。これまでは1分ごとに戻って枠を埋め、再処理ジョブが何日も進まないことがありました。

- **ほかの項目が不正でもスタンプを押した人の一覧を更新**
  メンション、ブックマーク、ピン留めのいずれかの値が不正でも、スタンプを正しく取得できた投稿は、押した人の再取得と一覧の更新判定に使います。

- **適用済みの通知の追跡終了が監視件数に反映されない問題を修正**
  2026-11-21 の更新で通知部品の表に列が増えてから、人の承認で適用済みだった通知の追跡終了がすべて無効と判定され、未完了の通知部品が再び監視件数に数えられていました。追跡終了の証明が、証明を作った時点の列だけを使うように直しました。既存の承認記録はそのまま有効に戻り、再送や再承認は発生しません。新しい承認や送信の条件は変わりません。

- **抽出QCでJevの回復を確認したときに古い障害警告を解除**
  意味解析がJevの障害を記録した後、抽出結果の品質確認（抽出QC）がJevに問い合わせて完了すると、以前の障害を示す警告が消えます。要約とループがともにoffで意味解析が止まっている間も、抽出QCによる回復を反映します。

- **収集診断の対処案内を統一CLIに修正**
  収集エラーの対処案内で、環境によっては存在しない素のpython3実行ではなく、導入方式に対応した`~/.local/bin/mcs`コマンドを案内します。

- **LINE WORKS文章通知の設定不足を初期設定で検出**
  LINE WORKSの文章だけの送信先を設定した場合も、接続設定・操作範囲の入力を求め、送信先トークルームの不一致を初期設定と設定確認で検出します。これまで設定を保存できても送信時に失敗する組み合わせがありました。

  MCS単独（standalone）でSlackカード用のチャンネルを新規作成または再開したとき、通知経路の公開ファイルがまだ無くても準備完了と判定される場合がありました。完了前に通知経路を公開し、その記録まで終わったときだけ完了として扱うように修正しました。チャンネル作成の条件、操作者の招待範囲、送信許可の範囲は変わりません。

  リポジトリ内の `sh scripts/mcs telemetry ...` が操作名エラーで拒否されず、導入後の `mcs telemetry` と同じ固定テレメトリ設定入口へ進めます。

  cloud処理の有界再試行統一（初回送信へ最大5回）で追加された固定エラー区分 cloud_validation_failure_invalid / cloud_validation_failure_transaction_required が error code 登録から漏れていたため補完しました。利用者向けの動作変更はありません。

- **cloud意味解析backlogがrun lockを取得できず送信されない問題を修正**
  cloud意味解析backlogがrun lockを取得できるよう、lock待機を連続ウィンドウに延長します。

- **クラウドの背景ワーカー数を抑え、患者コンテキストの走査の時間切れを正しく記録**
  クラウドを有効にした環境で、常駐処理が起動するクラウドの背景ワーカーを減らします。患者コンテキスト専用は最大2本、再開期間のワーカーと合わせた合計は空きメモリ（1本256MiB換算）と max_concurrency の小さい方までで、1回の判断で起動するのは最大2本です。また、患者コンテキストの走査が時間上限で止まった周回を読取り失敗ではなく走査の中断として記録し、読取り失敗には SQLite のエラー名を残します。

- **外部AI送信の確認記録が消えても送信を再開しない**
  施設の確認が必要な環境で `external_transfer.json` が見つからないときは、読めないときと同じく Anthropic・OpenAI・Jev への送信を止め、`external_transfer_unreadable` の警報を出します。これまでは、確認記録が消えると確認の無い既存環境と同じ扱いになり、キーがあれば送信していました。

- **抽出の自動再試行で既存コンテキストを誤って無効扱いしないように修正**
  クラウド抽出の自動再試行で、初回実行時に保存されたコンテキストが試行番号の違いだけで無効と判定され、以後の再試行が進まなくなる問題を修正しました。同一原文・同一経路の過去試行は履歴として再利用できます。

- **Homebrew導入済みでPATH未設定の場合の導入案内を改善**
  HomebrewがPATHに見つからない場合の導入エラーで、導入済みならインストーラのNext stepsにあるshellenvコマンドを確認する案内が表示されます。

- **通知カード掃除の台帳走査を索引で限定**
  通知カードの残骸掃除が通知履歴を広く走査してrun lockを長く占有する問題を修正しました。対象となる状態と更新時刻を既存の開設時索引で限定し、掃除に要する読取りを減らします。

- **患者コンテキストの健全性観測が大きな台帳で観測上限に達する問題を修正**
  doctor の患者コンテキスト観測が observation_limit（unknown）になりにくくなりました。最新行の照合を、患者の新しい履歴を候補ごとに辿る相関副問合せから、同じ種別の現行行を一回だけ集計する方式に変えました。集計結果・表示は変わりません。

- **患者コンテキスト走査の中断理由を待機と読取障害に分けて記録**
  患者コンテキストの候補選定が台帳の書込みロック待ちや走査期限で止まったとき、記録上の理由がすべて read_sqlite（読取障害）に集約されていたため、実際には候補の読取りまで到達していない停止を読取障害と区別できませんでした。ロック待ち・期限による中断は既存の scan_interrupted として記録し、本当の読取障害だけが read_sqlite になります。待機の扱いは従来どおりで、いずれの場合も後で再試行します。

- **患者コンテキストの状態が件数のある環境でも「不明」になる問題を修正**
  健康状態の記録（health.json）の患者コンテキストは、1時間ごとの再集計が2秒の上限に収まらなかった場合や読み取りに失敗した場合でも、直前に集計できた件数を失わず、元の集計時刻と経過秒数を付けた前回値（stale_measurement）として残します。前回値は元の集計から3時間までで、その後や台帳・抽出世代が変わった場合は従来どおり unknown です。doctor --probe data の作業待ちの件数は、1秒の上限で全員を確認できなかった場合に「患者N人のうちM人まで確認」と確認した範囲の件数を示し、合計としては扱いません。

- **再取得で時刻だけが更新されても品質照合が偽の競合で止まらないよう修正**
  同じ投稿を再取得して閲覧時刻だけが更新された場合に、患者要約の品質照合が「出所が変わった」と誤判定して要約生成が止まる問題を修正しました。本文・署名・版・権限など実際の入力が変わった場合は従来どおり拒否します。

- **添付の依存captureが患者の全artifactsを走査して収集を停止させていた問題を修正**
  患者コンテキストのscan選択が既存索引を使わず患者の全artifactsを走査していたため、添付依存captureが重くなり収集runが時間切れになることがありました。索引を明示して走査範囲を絞ります。返す行は変わりません。適用後は添付解析の指紋が失効し、既存の添付解析の一部を再処理します。

- **semantic projection候補が無い環境で収集runが長くなる問題を修正**
  semantic projectionの無効化確認は、対象kindが1件も無いとき全artifactsを走査していました。対象kindの有無を既存索引で先に確認し、無い場合は走査を省きます。対象がある場合の判定と更新は変わりません。

- **旧形式のsemantic cloud receiptでbacklog再処理が止まる問題を修正**
  member binding導入前のsemantic cloud receiptが、現在のinterpretation generationで必要な再処理送信を永久に拒否しなくなります。旧receiptの会計記録は保持したまま、現在generationの送信は論理unitごとに通常どおり予約・記録されます。

- **同一内容の要約の再判定で推論元の記録が失われなくなりました**
  公開の証跡が古い形式（文書ハッシュなし）のとき、意味解析の要約を再判定すると内容がまったく同じでも推論元の記録が空の複写が新たに作られ、どのモデルが作った要約かの情報が失われていました。内容が同一の再判定では、保存済みの行の推論元の記録を引き継いで再利用するようになりました。

- **スナップショット複製の間も他の処理が書込みを続けられるように修正**
  定期処理が台帳スナップショットを複製している間、run lockを保持し続けて患者コンテキストや抽出が待機する問題を修正しました。オンラインバックエップの一貫性を利用し、複製と検証の間だけロックを離して再取得します。

- クラウドの lookahead で prepare_context_load_superseded（複数片の旧世代保留行）にも _prepare_hold_s 経由の有界 claim を置く。従来は保持対象外で、パスごとに context の読み直しを繰り返していた。保留集合が引き続き旧世代だけと証明できる間は6時間、変われば短い準備待ち（60秒）で見直される。その他の準備拒否コードには従来どおり claim を置かない（次パスで即座に再選定される main の挙動を維持）。必須クラウド契約が付かない旧世代保留の経路では、v4採用済み投稿は _source_writable の契約条件により claim を取得できず、従来どおり解放され次パスで見直される（契約付きの経路では採用済み投稿にも保持を許容する従来の判定は変わらない）。
- _release の _commit_hold は真偽値のほか保持秒数を値として受け取るようになった。真偽値は従来どおり短い準備待ち（_PREPARE_HOLD_S、60秒）を意味する。

#### 手動のJev操作が背景処理の実行中にすぐ失敗する問題を修正

- _reserve_live_usage が run.lock を1回だけ試す代わりに既存の wait_run_lock で待つ。
- 待機の上限は LIVE_LOCK_WAIT_S（30秒）と要求のタイムアウトの短い方。
- 予約中の sqlite3.OperationalError を JevError('budget_exceeded', 'usage_ledger_busy', retryable=True) に変換する。
- 日次上限・予算・復元中の確認は従来どおり排他の中で行い、Jevへの通信は排他を外してから行います。
- 台帳エラーのうち再試行可能な usage_ledger_busy にするのは SQLITE_BUSY・SQLITE_LOCKED だけで、読取り専用などそれ以外は usage_ledger_unavailable（再試行なし）。
- 共通の wait_run_lock は最後の試行を期限ちょうどに行い、固定間隔ぶん期限を過ぎてから取ることはない。手動の Jev 予約は、待ち時間（30秒と要求のタイムアウトの短い方）を過ぎてロックを取れた場合、台帳を開かず usage_lock_busy で止まり、送らない要求を利用枠に数えない。

#### Jevの新しいモデルを知らせ、確認に合格したときだけコマンドで切り替える

#### 検査値の判定で、検体の節・続く検査値の単位・長い行での停止を修正

- 検体の見出しは、検体の語（尿・検尿・カテ尿・導尿・随時尿・早朝尿・中間尿・蓄尿・沈渣・髄液・胸水・腹水・便・検便・喀痰）に、決まった続き（検査・検査結果・検査の結果・の検査結果・定性・一般・生化学・穿刺・の性状・所見・データ・検体など）か括弧が付いたもので、前の語に続けて書かれていても見出しです（本日尿検査、入院時尿検査：、外来尿検査結果：）。続きのない検体の語（尿、沈渣、髄液など）は、句の始まり（行の先頭、空白・読点・句点・「・」「/」「;」・助詞のあと）または日付や時を表す語のあと（本日尿）にあり、その行で結果が続くときに見出しです（蛋白(1+)、沈渣 WBC 30/μL、潜血(-)。尿：WBC 30/μL、入院中の尿：WBC 30/μL）。行の終わりで終わる続きのない検体の語は、単独の行（記号・数字・括弧・【結果】のあとを含む）、空白や「：」のあと、日付や時を表す語のあと（11/20 尿、本日の尿、本日、尿）のときだけ見出しにします。排尿・血尿・軟便のように前の語に続いたもの、「多量の便」「夜間に尿」「食事良好、便」で行が終わるもの、「尿、便」「多量の便、WBC」のように読点が続くものは見出しにしません。見出しは、その行の終わりで終わるか、区切り・括弧・空白のあとに結果が続くか、「で」「は」などのあとに検査項目名が続くものです。続きのない検体の語や、性状・所見・データ・検体のような記述の見出しのあとは、登録された検査項目の値（尿 WBC 30/μL、尿所見：WBC 30/μL）だけを結果とし、「尿：淡黄色 6回」「便の性状：泥状 3回」「便所見：普通便 1回」「尿 量 500ml」のような記録は見出しにしません。検査・定性・一般などの見出しのあとは、どの結果（pH 6.0、蛋白(1+)）でもかまいません。見出しは改行・句点・読点・セミコロンをまたいで、血液側の見出し（血液検査・血液・血液一般・血液データ・採血・本日採血・定期採血の結果・血算・CBC・末梢血・静脈血・血清・生化学。「血液検査では」も含む）、別の検体の見出し、または節の結果を読んだあとの空行まで、その節の結果すべてに及びます。見出しのすぐ後の空行では終わりません。空行の前の結果には、薬の量や回数（抗菌薬 1錠、排尿 6回、10 mg）は数えず、視野あたりの数（赤血球 5個/HPF）、文末の句点のついた値（pH 6.0.）、文がそこで終わる陰性・陽性・正常・異常なし（潜血 陰性、陰性です）は数えます（陰性疑い、陰性か確認中、陰性かもは数えません）。結果のあとの項目（pH 6.0 Mg:2.0mg/dL）は数値の単位と読みません。行の先頭（記号・日付・時を表す語だけが前にあるもの: 11/20 尿検査：pH 6.0、11月20日 尿検査：、11/20の尿検査：、※尿検査：）の見出しは次の行へ及び、文の途中で結果が続く見出し（発熱あり、尿検査：蛋白(1+)）はその行の終わりまでです。日付や時を表す語に続く血液の見出し（本日血液検査、入院時血液検査）も節を終えます。「尿検査は異常なし」のように結果が続かないもの、再検査・外注検査・検査値・本日測定・【看護師より】のような語は、見出しにも節の終わりにもなりません。項目に直接付いた検体の語（尿TP、尿中Ca、髄液TP）は従来どおりその項目だけを未確認にします。

- 判定は抽出結果の引用（evidence）の中だけで見出しを探します。投稿本文で見出しが引用の外にある場合（本文が「尿検査」「pH 6.0」「WBC 30/μL」の3行で引用が最後の行だけ）は、検体の節と分からず従来どおり血液の値と同じに判定します（既知の限界）。

- 裏付け済みにしない例（従来どおり）: 単位が空白なしで次の語に続くもの（4.0mEq/LCr 0.9）、数値の直後の mg などの単位を次の項目（Mg）と読まない（「カルシウム 10 mg 2」「カリウム 4 Mg 2」）、登録されていない項目名（Cl など）が続くもの。同じ行で同じ項目の値が2つ読めるもの（血小板数 15万と PLT 15万）は、単位を正しく切るようになったぶん2つの読みとして見つかり、未確認になることがあります。

- 原資料検索で検索語が無いとき（日付などの条件だけのとき）は search_query_empty、開始日が終了日以降のときは bad_search_filter を返します。グループルームの検索結果の見出しには、MCSの患者ページへのリンクを付けません。
- 要約の状態に「要確認」（チャットのまとめと同じ判定）を加え、設定ファイルが壊れているなど判定に使う設定を読めないときは「状況不明」と表示し、添付のOCR件数も返しません。投稿の行には添付のOCRの状態ごとの件数を返し、失敗・未処理の添付があることを示せるようにします。
- 患者一覧の各行に返答確認の件数を加えます。件数は同じスナップショットと同じ設定の間は一度だけ集計して使い回し（設定を変えると判定し直し、連絡・返答の確認の表示と一致させます）、一度の一覧表示で集計するのは12件までです。まだ集計していない行は「未集計」と返し、0件とは区別します。
- MCS登録データの観測値は、観測項目の一覧にある項目すべてを表示し、値をまだ取得していない項目は「未取得・未確認」として項目名とともに示します。

- 原資料検索の「ここまでの範囲で」の件数は、件数が報告されなかった範囲を0件として足さず、その範囲を除いた件数に「（件数の報告がない範囲を除く）」を付けます。どの範囲でも報告がない種類（添付OCRが設定で無効、または設定を読み取れず調べなかったOCR未完了など）は表示しません。

#### 抽出監査の指摘が残る投稿を、再抽出の再開期間中にクラウドで1回だけ再抽出

- 送信条件は既存の再開期間と同じ（費用上限、cloud-llm stop、施設の確認、project_ids・exclude_project_ids の範囲、cloud-llm resume で記録した履歴の範囲、旧抽出の保留なし）。新しい設定項目や送信経路はなく、再開期間外には送らない。

- クラウドの再抽出後も指摘が残る投稿と、すでにクラウドで再抽出した投稿は確認候補（needs_confirmation）、まだの投稿はクラウド再抽出待ち（followup_state）に表示し、確認候補はそれ以上自動では再抽出しない。チャットのカード表示は変わらない。
- 現在の抽出世代で qc_fix の記録がある投稿を通常の再抽出として送らないのは、監査と再抽出を繰り返すたびに有料の送信が重なるおそれがあったため。
- 抽出の qc_fix に attempt を追加し、採用したクラウドの2回目だけ attempt: 2 を記録する。送信後の既知の失敗ではローカルで再実行せず、抽出も書き直さないので、現在の監査がその抽出を指したまま確認候補に出る。
- 1回の記録として artifacts に新しい種類 extract_cloud_attempt_v1 を加える。2回目は有料の要求ごとに、その送信予約と同じ transaction で開いた記録（監査された抽出・source の revision・契約・予約の id に束縛）を残し、記録を含めて2回目の条件（最新の監査が1回目の結果を指摘し続け、人の誤り報告がなく、本文が送信済みでない）・現在の本文 hash・QC の60日範囲・契約の一致を満たさなければ予約ごと取り消す（保留・error retry 等のレーンの他の条件は selection と claim の cloud_lane_sql だけが判定する）。最初の予約の前に上限等で止まった場合は記録が残らず、後で別のモデルでも送る。採用・保留は抽出の書込みと同じ transaction で、送信後の既知の失敗は単独で閉じた記録を追記する。通常の再抽出も終了時に閉じた記録を残す。この記録は送信の会計記録（cloud_usage_*、62日で整理）と違って削除されない。記録が指さない reextract 送信予約も、予約した時点の本文がいまの本文なら（本文を編集して元に戻した場合の以前の期間を含む）送信済みとみなす。
- 途中まで送った回は開いたまま残り、次の機会に、最初の予約時の契約（送信先と、分割・修正の各要求のモデル）で保存済みの分割結果と修正結果を再利用して残りだけを送る。契約の可否は cloud_policy.resolve_contract が決め、client の作成・送信前の確認・予約のすべてがその送信先の設定と鍵を使う。その送信先が上限の間は優先順位を変えて別の送信先が使えても待つ。読み取れた設定・記録した施設の確認・鍵がその契約を提供しなくなった場合は別のモデルで送り直さず、抽出の処理（クラウドの on/off に関係なく毎回）がその回を終えて確認候補にする。契約の profile は、自動で選ばれた送信先に関係なく、その送信先自身の検証済み設定（分割した provider 設定ではその送信先のファイル）で判定する。設定・確認記録・鍵を読めない・確認待ち・一時停止・費用上限が未設定の間は終えずに待ち、送らない（契約を提供しなくなった場合はそちらを優先して終える）。待つ間に投稿がQCの60日範囲を出た場合は、残りを送らずにその回を終えて確認候補にする。閉じる書込みは stale GC と同じ短い待ち時間で区切り、混んでいれば次の処理で行う。修正要求は開始を保存してから送り、再開時に送り直さない（保存直後に中断した修正の応答は採用せず、最初の応答を要確認で確定する）。送信済み・結果不明の要求は既存の会計の重複防止で送り直さない。この契約を持たない送信の送信先の選択は従来どおり。
- claim 時もレーンの絞り込み（extract_llm_selection.cloud_lane_sql、QC の60日範囲と qc_fix 済みの除外を含む）と qc_cloud 列を再照合する。cloud-llm estimate も同じ絞り込みを使う。
- mcs view qc の一覧に qc_attempts（0・1・2）、needs_confirmation、followup_state（local_reextract_pending・cloud_reextract_pending・needs_confirmation）を追加し、集計に followup 別の件数を加えた。--needs-confirmation は --message-id と同時に指定できない。
- 2回目の各記録は監査の指摘内容の digest も束縛し、途中で新しい監査が指摘内容を変えた回は何も送らずに抽出の処理が終えて確認候補にする（保存済みの有料応答は送った prompt で確かめるため）。同じ指摘内容の再監査では続ける。契約の判定は auto がいま選ぶ送信先ではなく設定自体の誤りと契約の送信先の設定で行う。記録の hash が読めない記録は送信済みとみなし、抽出・revision の束縛は整数だけを受け付ける。終了の判定は設定の更新中に待たず次の処理へ回し、書込み transaction の中では設定や確認記録を読まない。記録を残す前の版で送った投稿は62日残る送信予約で判定するため、整理後は mcs view qc で cloud_reextract_pending に戻ることがあるが、対象は直近60日なので再送しない。

#### Jevの日次上限で待機した抽出QCを、保存した回答の続きから再開

- まとめ処理の約300秒は新しいジョブを始める期限にだけ使う。開始前の確認（ジョブのロック・予算・長時間出力の予約）の間にこの期限を過ぎたジョブは始めず、予約を戻し、試行回数を数えずに次回へ残す。各ジョブの実行期限（job_budget_seconds まで）は開始時に1回決め、Jev通信と保存前の確認に使う。通信後の run.lock の取り直しは、呼び出し元（定期処理・まとめ処理）の期限と、レーンごとの取り直し待ちの上限（定期処理は150秒、backlog は660秒）の早い方まで待つ。ジョブの期限内に取り直せば回答を保存する。通信は期限内に終わったが取り直しがジョブの期限を過ぎた場合は、回答もエラー（HTTP 400 など）もジョブの処理に渡さず、評価の記録を書かず、試行回数も数えずにジョブを次回へ残し、呼び出し元の処理はそのまま続ける。上限までに取り直せなければ従来どおりその回の処理を止める。送った問い合わせは、送信前に台帳へ記録する日次使用量の予約に数えたまま残る。
- 抽出QCの開始に必要な残り時間は通常15秒。要約かループが有効なbacklogでジョブ予算（job_budget_seconds）が680秒を超えると、超えた分を最大540秒まで保存用に加える。既定の45秒では加算しない。意味解析でJevの送信前に時間が足りず、送信も途中結果の保存もなかった場合は、ジョブ予算が1回の試行時間（attempt_timeout_seconds）と5秒の余裕を賄えれば、試行回数を数えずに次回へ残す。
- backlog レーンのQCは、設定によらずJevの日次上限・予備枠・Jevの回路遮断に当たると評価を省略した完了にせず、試行回数を数えずに待機する。途中で日次上限に達したときは、得た回答を対象の抽出結果と質問の組に結び付けて保存し（extract_qc_wait）、次の枠では残りだけを問い合わせる。QCの結果はすべての回答がそろってから書く。ローカルLLMを使う意味解析がある設定では、その回の残りのジョブは続ける。判定は semantic_policy.waits_for_jev_quota（ジョブの種類を含む）に集約する。
- backlog レーンでローカルLLMを使う意味解析がある設定では、Jevの日次上限などで待機したQCを、その回の残りの選択から外す。待機中のQCが選択の範囲を埋めて、アーカイブ済み患者などの意味解析ジョブが選ばれなくなることを防ぐ。外したQCの状態と試行回数は変えない。
- 要約とループがともにoffの場合、10分ごとの定期処理（新着用realtimeレーン）でも、抽出QCには同じ15秒の開始条件を使い、ローカルLLMの回路遮断で止めない。定期処理がこの段階に進む条件は、残り60秒超でローカルLLMの新着用の枠が空いていること。
- 新着用 realtime レーンでは従来どおり、日次上限に達したジョブも評価を省略した結果で完了し、新着の処理を止めない。待機して次の枠を待つのは backlog レーンだけ。
- 根拠: mcs/extract/llm/extract_llm_resident.py、mcs/semantic/semantic_drain.py、mcs/semantic/semantic_qc.py、mcs/semantic/semantic_runtime.py

#### 未読の意味解析jobを止め抽出QCだけをまとめて処理

#### クラウドの背景ワーカー数を抑え、患者コンテキストの走査の時間切れを正しく記録

- これまでは患者コンテキスト専用と再開期間の2つの組が、それぞれ空きメモリと max_concurrency の小さい方まで一度に起動していました。
- 既定値の変更: 患者コンテキスト専用ワーカーの上限 CONTEXT_WORKERS_MAX=2、1回の判断（約10秒ごと）で起動する上限 SPAWN_PER_DECISION=2（いずれも cloud_backlog.py の定数で、設定項目はありません）。
- 患者コンテキストを優先します。再開期間のワーカーは、空きメモリの本数から患者コンテキストの分（動いている本数、患者コンテキストが有効な間は再起動待ちでも少なくとも患者コンテキストの上限本数）を引いた範囲で起動します。患者コンテキストが無効な間は全体を使えます。再開期間が開いている間、患者コンテキスト専用は max_concurrency から1を引いた本数まで（max_concurrency が1なら1本）とし、再開期間のワーカーに少なくとも1本の枠を残します。患者コンテキストを無効にすると専用のワーカーは処理中の1単位を終えてから終了し、空いた枠は次の判断で再開期間のワーカーが使えます。再開期間のワーカーは、予算の上限・鍵・接続先の設定などで新たに起動できない状態になると、持ち越した支払済みの結果を精算（保存、または元の投稿が変わっていれば保留）してから次の確認（60秒おき）で終了し（理由 cloud_blocked。mode が on でない場合は従来どおり cloud_mode_off）、枠を空けます。終了するまでの間は、その分だけ患者コンテキスト専用の起動を控えます。患者コンテキストを無効にしている間に起動した再開期間のワーカーは、患者コンテキストを有効にすると、その分を超えた本数が次の確認（60秒おき）で終了します。空きメモリが減ったときは（前景用の予約を下回った場合はすぐに終了します）、超えた分のワーカーが次の確認で終了するまで合計が上回り、確認の後も最大2本上回ることがあります。あとから再開期間が開いたときも、枠を超えた専用のワーカーは処理中の1単位を終えた後の確認（60秒おき）で終了します。1回の判断で起動する2本は2つの組で共有します。
- max_concurrency は従来どおり同時に送るクラウド要求の上限です。送信枠・予算・鍵・承認の判定と、従来の終了・再起動の判定（メモリ不足・mode・経路の閉鎖、短時間で終了した子の再起動待ち）は変わりません。追加した終了条件は、患者コンテキスト専用のワーカーの2つと、再開期間のワーカーの2つ（患者コンテキストの分を超えたとき capacity_reduced、そうでなく起動できない状態になったとき cloud_blocked）だけです。
- 候補の読取りが SQLite の中断で止まったとき、その読取りの時間上限を過ぎている場合だけ走査の中断（scan_interrupted、理由 patient_context_scan_incomplete）とします。上限より前の中断とそのほかの SQLite の失敗は read_sqlite ですが、busy/locked の待ち切れは読取障害ではなく scan_interrupted として記録します。時間上限を過ぎた中断は、上限を過ぎた後の行の取得と同じく周回を打ち切り、これまでのように読取り中だった確認を未準備として扱って走査を続けることはしません。
- read_sqlite と busy/locked の周回は、クラウド処理の記録（patient_context_pass）に SQLite の標準のエラー名（SQLITE_BUSY など）を scan_sqlite_error として残します。その形でない値は unclassified とし、エラーの本文・患者を特定する情報は残さず、DB にも保存しません。エラー名の記録は走査・選択・保存・再試行間隔の判定を変えません。
- 根拠: mcs/llm/cloud_backlog.py、mcs/patients/patient_context_refresh_sources.py、mcs/patients/patient_context_refresh.py
