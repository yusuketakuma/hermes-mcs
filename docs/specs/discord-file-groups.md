# Discordの原文と添付の一括配信

`chat_format_version=1` のスレッドカードは、各投稿の原文の直下に添付を表示します。カード面に原文がある投稿はカード本体、長文がスレッドにある投稿はその原文の最終本文部品へ添付します。画像はMediaGallery、PDFなどはFileを使います。画像の折り畳みを維持します。

同じ表示先の複数ファイルは、本文・操作ボタンと同じ1回の送信または更新に含めます。`file_group:<surface>` とその添付部品は独立したHTTP要求を持たず、本文の受領結果から同じDBトランザクションで確定します。

## 上限と保留

1つの表示先は10ファイルまで、1ファイルは20MiBまでです。ファイル合計は25MiBから64KiBの余裕を引いた値を上限とします。表示は40部品・4000文字の制限も確認します。元投稿の表示位置が定まらない場合や上限を超える場合は通知全体を保留し、ファイルを黙って省略しません。

## 再利用と受領証拠

DB形式12は、Discordの投稿IDとファイルIDを別々に保存します。添付の再利用では、以前の配信で確認したファイルID、表示先の投稿ID、原本のhash・サイズ・名称が一致する必要があります。仕様を整理しても、この証拠は保持します。受領結果には、部品ID・送信名・サイズ・ファイルIDの全件を含めます。欠落・余分な添付・重複IDは成功扱いしません。

既存の投稿に未確認のファイルがある場合は、更新前に処理を止めます。送信の成否が不明な場合は自動で再送しません。同じ配送・同じ試行の後から届いた受領結果だけが、対応する部品状態を確定できます。

## 人による復旧

既存の `ops.card_part_resolve` を使います。操作者、理由、人による承認、停止済みworkerの証拠、対象配送と部品のhashが必要です。Discordの添付グループを配信済みと確定する場合は、`evidence.files` に当該表示先の全添付の `part_id`・`wire_name`・`bytes`・`remote_file_id` を記録します。投稿IDだけでは添付の配信を証明できません。

過去の送信結果が不明な記録は、承認だけで自動再送へ変えません。送信済みの部品を別の試行で書き換えたり、取り消された配送を復活させたりしません。

## 更新

旧形式の仕様は既存の配信経路を維持します。新しい仕様は未対応の旧workerが拒否します。DB更新前のバックアップを保持し、導入時にすべてのworkerを新版へ切り替えてください。コードの変更だけでは稼働中workerへ反映されません。
