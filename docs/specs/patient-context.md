# 患者背景情報の構造化契約（1.0.16）

既存の `extract_v1` / `extract_llm` artifact に `patient_context` 配列を追加する。患者テーブルやDB schemaを変更せず、保管済み本文・連携サマリーと同じ患者スコープで扱う。

| 属性 | 契約 |
|---|---|
| `category` | 基本情報、診断、既往、経過、実施したケア・訪問、事故・ヒヤリハット、ADL・リハ、生活・家族・制度、介護度、サービス、担当者、連絡先、アレルギー、機器・処置、意向・看取り、服薬管理、栄養、排泄、皮膚・褥瘡、口腔、認知・行動、副作用経過、検査・観測、計画・目標・会議、指示・連携文書、フォローの26分類（1.0.25で7分類追加）。列挙正本は `patient_context.CATEGORIES` |
| `text` | 根拠引用に含まれる原文値。否定・過去・予定・条件・未確認を残し、推測や臨床的な確定値への変換をしない |
| `evidence` | 対象本文の一意に照合できる引用。別投稿・参考コンテキストの引用は拒否 |
| `subject` | LLMは `patient` / `family` / `other` を必須にする。見出しルールは対象者を推測せず `unspecified` |
| `details` | 35属性の `{key,value,evidence}` 配列（1.0.25で `valid_period`＝指示/認定/計画の期間、`body_site`＝部位、`food_texture`＝食形態・とろみを追加。期間は期限 `due_text` や観測日と別）。値は原文文字列、引用は同じ親引用内で一意に照合できること。キー正本は `patient_context.DETAIL_KEYS` |
| `origin` | 見出しルールの場合 `explicit_heading`。LLMの生成文字列をコードや指示として実行しない |

ルールは明示された見出しから次の見出しまで複数行を保持する。対応外の装飾見出しやコロン見出しは境界として区切り、前項目に取り込まない。全ての自由文から網羅的に情報を得られるルールではない。見出しがない文章の追加抽出は既存ローカルLLM経路で行う。入力全体を既存の長文分割で処理し、一部の失敗を完全な抽出結果と扱わない。

LLMのJSON grammar・項目検証・修復・chunk統合・batch・checkpointに同じ契約を適用する。LLM世代6・詳細契約2へ進め、既定1600 tokensは維持する。旧世代の成功・失敗結果を通常pendingへ戻し、新しい失敗予算・lease・chunk・QCの境界で再抽出する。ルール世代12への更新で既存本文の明示情報を通常のrun_pendingで補完する。

## 職種別の見出し語彙（1.0.25）

薬局以外の職種（訪問看護、訪問診療、ケアマネ、訪問介護、施設・通所、リハ、栄養、歯科、相談員）が日々書く定型見出しを `patient_context.LABELS` に持つ。1ラベルは1分類にだけ属し、長い見出しが接頭の短い見出しより先に一致する。「排泄」は状態として排泄分類に移り、動作は「トイレ動作」「排泄介助」で保持する。専用の分類は探しやすさのためで、見出しのない文章はLLM経路が同じ分類へ投影する。評価尺度（BI、FIM、MMSE、NRS、DESIGN-R、BMI等）は観測の見出しとして原文のまま残し、尺度名・版・部位・時点を結合して比較しない。訪問や会議の時点はcanonicalの `event_time` と原文で保持し、観測日と混ぜない。算定可否・正式文書の交付・提出の成立は表示も推定もしない。

`--role` と通知カードの表示順は `patient_context_view.ROLE_ORDER` / `ROLE_LABELS` を正本とし、nurse / physician / pharmacy / care に helper（訪問介護）、facility（施設・通所）、rehab、nutrition、dental、msw を加えた並び順だけを変える。閲覧範囲・認可は変えない。

関係者・事業者の一覧は、投稿に記録された投稿者の職種・氏名・事業所名（`messages.profession` / `sender_name` / `organization`）から `patient_context_view.participants` が患者の部屋ごとに自動生成し、CLI `--view participants` と「患者さんの全体像」の末尾に投稿件数・最終投稿日時付きで出す。投稿者であることと、利用中の契約・主担当・現在も関与していることは同じではなく、判定しない。本文からの事業者名の見出し（事業者名・関係事業所など）は care_team の記載として別に保持する。
この一覧の利用先（1.0.25）: (1) タスク作成フォームの担当者候補は名簿のうちその患者の部屋に投稿した人を先頭に並べる（名簿の範囲は変えない）。(2) 「連絡・返答の確認」「訪問前の確認ノート」「引継ぎ用の記録」の依頼行に、依頼を書いた投稿者の職種・氏名・事業所と最終投稿日時を添える。(3) 「記録の食い違い」に、care_team の記載が事業所名を含み、その事業所の投稿者がいない場合を「投稿者に見当たらない事業者の記載」として候補表示する（投稿がないことと関与がないことは同じではない）。(4) 統計 `poster_gaps` は部屋×事業所ごとの最終投稿からの日数を候補として出す。(5) 「患者さんの全体像」の標準表示では、投稿者の職種から表示順の候補を1行で示すだけで、自動では切り替えない。

1.0.25ではルール世代23・LLM世代9・患者背景契約4へ進み、1.0.26でルール世代24へ更新した。現行のルール世代は `mcs/extract/rules/extract.py` の `RULE_VERSION`（現在29）、LLMの内部世代は `mcs/core/inference_version.py` の `LLM_EXTRACT_VERSION`（現在11）、患者背景契約は `extract_llm.PATIENT_CONTEXT_VERSION`（現在4）を正本とする。公開engine版1.0は内部世代と別に扱う。更新後は既存投稿のルール再抽出が通常の処理で順次行われる。抽出の世代は走査契約に含めず、走査が読む項目が変わった資料だけを再走査する（下の「資料ごとの束縛」）。

## 読取りと要約

既存 `evidence` / `timeline` / `search` / `thread` に根拠付きの項目を付ける。`read_model` の各投稿は最新のhash一致したv1とLLMを選び、canonical projectionがLLMを覆っていても追加情報を保持する。削除・不完全本文・古いhash・別患者・壊れた項目は採用しない。既存のlimit/cursor/total/truncated契約を維持する。

`read_model --scope detail` は原文値・引用・出典を返す。`aggregate` は分類と件数だけを返し、原文値・引用・記入者名を含めない。`project_metadata` は連携サマリーの `reported` / `fetched_empty` / `not_fetched` / `unknown` を区別し、別の出典として保持する。旧schemaのkarte_id欠落は未確認として扱う。

rollupの `patient_context` は `memo` と `chat` を別々に持つ。チャットの分類ごとに最新の報告投稿から全項目を集約するが、現在の確定した患者状態を意味しない。全文と以前の報告は詳細読取りに残る。本人限定の患者まとめには原記録の短い抜粋を追加し、基本情報・連絡先の分類は抜粋に出さない。共有カードには、所有者決定（2026-10-14）により服薬管理の `storage_status` / `storage_place` / `medication_manager` / `inquiry_result` / `interaction_check` だけを、現在の本文hashに一致する抽出から原文の値を短く引用した1行（本人以外は対象を併記）で載せる。同じ親項目の他の属性・基本情報・連絡先・服薬支援などは共有カードへ出さず、`events` の `prescription_inquiry` は区分「処方の照会・提案の記載」とし、照会の完了や結果の確定を表さない。

連携サマリーは既存GET・認証・保存経路を使う。deep runは未取得を優先し、24時間経過したサマリーを再取得する。背景対象10件・段全体12GET・deadline余裕60秒・失敗後6時間の待機を維持し、保管済み患者は除外する。失敗しても最後の成功内容を保持する。

## 服薬管理の報告の集約と参照（1.0.21、抽出世代8への更新と同時に一貫させる）

本節は実装済みの契約で、抽出世代8（ルール世代21）で適用する。配備後は通常の抽出workerが旧世代の結果を順次再抽出し、保存済みの結果を直接書き換えない。本番への配備と、参照情報（`patient_state_context`、既定false）の有効化は別の判断で、まだ行っていない。

- **集約**: `patient_context.pharmacy_state_items` は現在の抽出から、`inquiry_result`・`storage_status`・`storage_place`・`medication_manager`・`interaction_check`・`support_method`・`residual_quantity`・`missed_doses`・`followup` の根拠付き detail を1件ずつの list で返す。同じ親の `drug_name` を全件付け、値を薬剤ごとに分配しない。親の引用・text・主体、親と項目の fingerprint、project・message・本文hash・投稿時刻を持つ。rollup の `pharmacy_state` は `{items, total, truncated, source}` で新しい投稿順に最大100報告。最新の報告は現在の確定状態ではなく、否定・予定・過去の原文を保つ。
- **本人向け表示**: 患者の記録まとめは最大8件と残り件数・集約上限を示し、表示前に現在の本文と抽出から再計算した fingerprint と一致する報告だけを出す。共有カードには上記の限定5属性と区分だけを出す。
- **参照情報（`extract.patient_state_context`、bool、既定false）**: 有効時だけ、同じ患者・対象より厳密に前・最大200投稿の現在の抽出（`current_fact_pred` の現行1件、品質確認済み、保持中の旧結果を除く）から、本人で否定・予定・過去・不確実でなく、同じ投稿で値や薬剤が一意な報告だけを日付付きの参照（最大600文字、既存の文脈と合わせて1200文字）にする。より新しい同じ薬剤・項目の報告が使えない場合は古い値へ戻らない。集約済みの現在値から逆生成しない。無効時の文脈は従来と同一。
- **試行への固定**: 初回推論前に、投稿・本文hash・時点・モデル・実装契約・試行・設定へ結び付けた参照本文と参照表（digest付き）を保存し、chunk・分割の再開と完了後の進捗は保存済みの内容だけを使う。他投稿の更新では作り直さず、破損した保存内容は推論せず保留する。
- **refers_to**: 抽出の値と引用は対象本文だけから取る。供給した参照番号だけを解決した参照として保存し、未知・型不正・別薬剤/別主体の参照は破棄して数える。
- **表示時の再照合**: 詳細読取り・本人向け表示・共有カードの許可行は、参照元の本文hash・時刻・主体・薬剤・項目 fingerprint を現在の抽出と照合し、一致するときだけ保存した値と日付を `（参照: MM-DD「値」）` で示す。変わっていれば `（参照先は更新済み）` とし、別の値へ差し替えない。参照の連鎖は辿らない。

## 定期取得の有効化と再開

`clinical_metadata` はbool・既定false。`mcs setup init --yes --set clinical_metadata=true` で明示選択した環境では、既存deep runがキャッシュ済みsessionだけで登録薬剤・観測項目・各項目値を巡回する。GETのみ・no_extend_session・名前保持なし・medical/現在karte mapping限定・archived除外。相談groupの関連付けは推測しない。

各deepはHTTPの内部再試行・session probeも含め12GET、25秒、親deadlineの60秒前まで。予算による保留は次回再開し、未完を登録0行・失敗・完了と扱わない。患者ごとに全観測項目を巡回し、1項目のHTTP失敗で後続を止めない。薬剤登録／項目発見／session失効は6時間待機。成功した一巡後24時間、失敗を含む一巡後6時間で再試行する。

観測定義と値をkarte ID・項目ID・成功定義世代・定義fingerprintへ束縛する。同じ定義の再取得時刻だけで旧値を無効化せず、正規化した旧pinと新しい全定義が同値であることを証明する。実差分・破損・別mappingは旧値を現在値へ出さない。失敗時の最後成功内容は履歴として保持する。

初回入力は共通の `clinical_chunking.plan_chunks` で見出し・段落・文・関連する連続行を優先して分割する。薬剤の用量、観測項目、変更・支援・予定、明示フィールドなどの密度と原文長から出力量の目安を算出する。これは実token数や処理時間の保証ではなく、未知の自由文も全て処理対象に残す。短い高密度投稿も事前分割し、低密度の短文は1単位のままにする。連結は空白・改行を含め原文と完全一致し、各単位は既存入力上限以下にする。

出力が実際にlength打切りされた場合は失敗した区間だけをさらに細分化し、既存checkpointへlayoutを保存する。完了済み区間を同じ実行中と中断後の再開で再利用する。分割履歴と結果を本文hash・投稿日時・実モデル・prompt・分割契約・参考文脈に束縛し、全文が完了するまで本抽出を完了保存しない。各区間へ渡すルール候補も当該本文の範囲へ限定する。参考コンテキストだけの値を対象投稿からの値と扱わない。

canonicalのmanifestは共通分割と同じ原文境界にatom所有を割り当て、見出し・隣接atomを参照専用に保持する。分割契約をchunk世代とbundle fingerprintへ含め、古いlayoutと新しい証拠所有を混ぜない。category_presence等の必須判定、subject・否定・時制・根拠を維持し、任意の空欄・重複説明のみ省く。

本人限定の患者まとめは最新20投稿の処理中・完了・要確認と完了区間数を表示する。現在の原文・モデル・prompt・分割契約・設定に合う検証済み結果だけを採用し、途中結果や古いPASSを完了扱いしない。以前の投稿はこの進捗表示の対象外と明記する。抽出処理の完了は臨床情報の完全性や臨床対応の完了を意味しない。共有通知に進捗行を追加しない。

v6のprefilterは完全一致の短い挨拶3種だけを省き、語彙netで臨床情報の不存在を判定しない。了解・承知・ありがとうなどの返信、見出しなしの嚥下・支援情報もLLMへ送る。稼働枠・token予算・timeout・admission・認可を維持するため、旧履歴の再抽出と対象拡大は通常workerで順次処理される。

canonical v3/v4の既存事実にもoptional patient_contextを同じ事実引用・対象へ拘束して保存し、属性の意味づけも既存監査へ含める。新promptでbundle/chunk世代を更新し、投影世代3へ進める。source/doc_hash・PASS・公開fence・人承認・admissionを維持する。legacy書込みの制限を解除して同時書込みさせない。

登録データ・チャット・連携メモは別出典で読取り、原文・属性・以前の記載はdetailに保持する。自由文メモで見出し抽出できない部分はdetailのcomment/unclassified_textで原文と未分類状態を示す。aggregateでは値・引用・氏名・具体日時を返さない。候補・未取得・古い情報を現在の確定患者状態と推測しない。

### 処理契約と出所（P0-2a・P0-2b）

- 走査契約（`snapshot["contract"]`、`patient_context_refresh_state._contract()`）は、資料の分割・引用検証と走査の処理（`patient_context_plan.py`・`patient_context_scan.py` のファイルhash）と各版だけを持つ。処理系の名前（ローカルのモデル名・クラウドの処理先）は含めない。走査で保存する事実には読取り時の解釈（`temporal`）を保存せず、読むときに要約側で `patient_context_projection.with_temporal` が付ける。原典の品質確認は保存した事実をそのまま使う。抽出の世代（`RULE_VERSION`・`EXTRACT_VERSION`）と添付の項目変換（`patient_context_projection.py`）は走査契約に含めない。走査契約の `context`（`PATIENT_CONTEXT_VERSION`）は、保存した項目から走査入力を作る処理（`patient_context.py` の引用照合・見出し抽出）の版として残す。この処理のコードは資料の署名に入らないため、出力が変わる変更ではこの版を上げる。`tests/patients/test_patient_context_version_pin.py` は完全合成の資料でこの処理の出力を版ごとに固定し、版を上げずに出力が変わると失敗する。この固定は合成の資料が通る経路だけを確かめるため、版を上げ忘れた変更は、保存済みの `extract_v1` が作り直されるまで走査入力の変化が署名に表れない。
- 資料ごとの束縛（P0-2b）：資料の署名（`patient_context_plan.source_signature`）は、原文の識別値に加えて、走査が読む入力だけを束縛する。`extraction_sig` は走査が読む項目の分類・本文・引用・主体・見出し由来・属性（属性は順番を保つ）のhash（`mcs_queries.context_items_signature`）で、成果物のid・モデル・抽出の世代・再試行の記録・項目の余分な欄を含めない。チャットは採用した `extract_v1`・`extract_llm`・追加の監査済み文脈（`semantic_facts_v4` または `canonical_projection`）に保存された項目を読む順に束縛し、本文は `content_hash` が束縛する。このため、浅い読取り（`hydrate=False`）でも本文の再照合や見出しの再抽出をせず、全文の読取りと同じ署名を作る。採用判定の証明は投稿ごとに成果物1件につき1回だけ行い、補助要約と項目の読取りで共有する。添付OCRは添付解析から作った最終の項目を束縛する。添付の項目は保存されず読取り時に作られるため、浅い読取りでも解析済みの頁ごとに1回だけ項目を作る（本文は浅い読取りでも読む。解析待ちの頁では作らない）。連携サマリーの項目は本文と `context` だけで決まるため `extraction_sig` を持たない。`derived_summary_sig` は補助要約の種類と本文のhash（`mcs_queries.derived_summaries_signature`）で、走査に送る補助要約にも成果物のidを含めない。種類は走査に送るため、添付解析の段階（ローカル・クラウド）が変わると同じ本文でも別の入力として扱う。`extraction_ready` は独立した欄として署名し、項目のない解析済みと解析待ちを区別する。
- この束縛により、再抽出・再解析で走査が読む項目と補助要約が同じ場合は、保存済みの走査を再利用し、走査をやり直さない。項目か補助要約が変わった資料だけが走査をやり直す。抽出の世代を上げた直後は、旧い抽出結果の採用判定が成り立たなくなり、その補助要約を読まないため、資料の署名が一時的に変わる。この間は `patient_context_refresh_readiness._eligible_source_keys`（`extract_llm.pending_pred` と採用判定の証明）がその投稿を走査対象から外し、劣化した入力での走査は行わない。概況の表示は再抽出が済むまで出さない。再抽出で同じ入力が戻れば、保存済みの走査が再び一致する。
- `original_source_sig` を持たない旧い成果物の照合（`source_signature(..., legacy=True)`）は、その時点の欄の集合（`derived_summary_sig`・`extraction_ready` を含めない）を保つ。ただし `extraction_sig` の意味が変わったため、旧い署名で保存した成果物は一致しなくなり、安全側に不採用になる。
- 要約契約（`snapshot["summary_contract"]`、`_summary_contract()`）は、根拠の選択・読取り時の時点解釈・依存喪失（`patient_context_selection.py`・`patient_context_projection.py`・`inference_dependency_loss.py`）を持つ。入力署名 `source_sig` は要約契約を含むので、概況の同一判定・公開判定・生成枠は要約契約に結び付く。走査レーンのクラウド入力の束縛は要約契約を含まない署名（`scan_source_sig`）を使い、要約側だけの変更で有料の走査単位を捨てない。レーン巡回と一患者scanの予定組み（`patient_context_schedule.py`）は出力に影響しないため、どちらの契約にも含めない。再試行の上限の印（`_checks()`）は走査と要約の処理hashから作る。
- 出所：調査結果・保存片・概況の各成果物は `provenance {backend, model, profile}` を保存する。照合は `patient_context_artifacts.route_accepts` が、設定から決まる「受け入れる出所」（`_route(cfg, pid)`：走査契約・対象のクラウド処理先・ローカルのモデル）と行う。クラウドの成果物は処理先の契約だけで照合し、ローカルのモデルを変えてもクラウドの成果物は失効しない。ローカルで作った成果物（クラウドの経路でのローカル代替 `local_fallback` を含む）は設定のローカルのモデルと一致する場合だけ採用する。このため、ローカルのモデルを変えると、クラウドで作った概況でもローカル代替の資料を含む場合は、その資料を作り直すまで表示しない。設定を持たない閲覧（スナップショットの読取り）は保存された出所を受け入れ、走査の署名が読む行を固定する。原典の品質確認と修復の識別値は走査契約と処理先（クラウド、またはローカル代替の経路の処理先）から作り、ローカルのモデル名を含めない。保存片の単位識別値（`unit_key`）は入力・区間・走査契約・処理先（ローカル代替は経路のクラウド処理先）・ローカルのモデルから作る。ローカル代替の単位は通常のローカル単位と別になり、ローカル経路へ戻ったときの再走査は過去の同一入力の再送として保留しない。
- 補助要約（意味解析の要約）と添付の解析結果も、ローカルのモデルを入力の識別値に含めない。意味解析の要約はクラウドだけで作った完全な出所なら設定のローカルのモデルに関係なく現在の結果で（`semantic.fact_source` が `legacy` の場合。`shadow`・`canonical` では下の未決項目のとおり方針の識別値が変わり、クラウドの要約も1回作り直す）、それ以外は行のモデルが設定のローカルのモデルと同じときだけ現在の結果とする（`semantic_store.producer_current`）。添付の結果はローカル段なら行のモデル、クラウド段なら参照先のローカル行（同じ原本・同じ契約）で照合する。どちらも閲覧時に設定のローカルのモデルで照合する（設定を渡す読取りはその設定のモデル、渡さない読取りはホストの設定を1回だけ読む）ため、設定を持たない閲覧が保存された出所をそのまま受け入れる走査・概況（`route_accepts` の `local_model_pinned=False`）とは非対称になる。ローカルのモデルを変えると、作り直した要約の文面が変わった資料だけ、走査が再実行される。
- 添付抽出の契約は、患者コンテキスト専用のモジュール（`attachment_extraction._CONTEXT_ONLY_SOURCES`）を除いたコードの識別値から作る。ローカルの接続先とモデルは含めない（互換のため出荷時の既定の組を固定値として残す）。抽出の入力として使う `patient_context` と `patient_state_context` は残す。資料を読む `mcs_queries.py` は除外の対象ではないため、その変更は添付の抽出を1回やり直させる。走査契約と要約契約は `mcs_queries.py` を含まず、再解析で同じ入力が戻れば走査は再利用する。

### 品質確認の識別値（P0-2c）

- 品質確認（概況の要約QA・原典の source-QA）の `assessment` は `{code, policy}` で、`code` は `patient_context_quality_identity.patient_quality_assessment_code()`＝`payload_hash(["patient-context-quality/1", QA_VERSION, patient_quality_code()])` とする。状態側（`patient_context_refresh_state._quality_assessment`・`_source_quality_hold_key`・`quality_schedule_key`・読取りの証明）と PASS の記録の照合（`semantic_usage_receipts.patient_source_pass_content`）は同じ関数を呼ぶ。走査契約と要約契約は、それぞれ `source_input_key`（`quality_binding` の契約）と `input_key`（`source_sig`）を通じて識別値に入っているため、`code` には含めない。
- `patient_quality_code()` は、質問を作り答えを判定するコードだけを hash する。対象は `QUALITY_FUNCTIONS`（`semantic_audit` の `_probability`・`_patient_quality_sources`・`_patient_quality_facts`・`patient_source_question_keys`・`patient_source_quality_pages`・`patient_source_quality_identity`・`audit_patient_quality_page`・`audit_patient_summary_chunk`、`semantic_jev` の `choice_question`・`evaluate_once_more`・`validate_answers`・`_validate_usage`（応答の usage の検証）・`_validate_answer`・`finite_value`（数値の検証）・`is_answer_defect`・`failure_class`、`patient_quality_expected`）と `QUALITY_CONSTANTS`（選択肢・`_PATIENT_SUMMARY_CHUNK_LIMIT`・`_PATIENT_SOURCE_CONTEXT_FIELDS`・`JEV_MODEL`・`DATA_NOTE`・`patient_context.CATEGORIES`）。関数は呼出し時にモジュールの名前から引き、`semantic_candidate.code_identity` でファイル名・行番号・行表を除いた bytecode（入れ子の関数・lambda・内包表記を含む）と既定値を hash する。closure を持つ関数と包まれた関数は拒否する。集合は `tests/patients/test_context_quality_identity.py` が固定し、`semantic_audit` に患者品質の補助関数を足すと分類するまで失敗する。`semantic_jev._merge_partial_answers` は `evaluate_once_more` が答えの保存先（callback）なしで呼ばれたときだけ使われ、`audit_patient_quality_page` は常に callback を渡すため対象外とする。
- 意図して範囲を狭めた。以前の識別値は読み込んだほぼ全コード（`extract_llm._LOADED_SOURCE_DIGESTS` と `semantic_candidate.loaded_source_contract()`）を含み、関係のないリリースのたびに全資料の品質確認が失効し、Jev の再確認が終わるまで公開版が非表示になっていた。
- `QA_VERSION` を手で上げる場合：hash の外にある受入れ規則を変えるとき。品質確認の制御・記録（`patient_context_quality_controller.py`・`patient_context_quality_receipts.py`）と `semantic_usage_receipts.py` の PASS 判定、答えの解釈、同じモデル名のまま Jev の振る舞いが変わるとき、送受信の補助（`mcs_util`・Jev の通信）や資料キーの解析が判定に影響する変更をしたとき。上げると全資料の品質確認が1回失効し、公開版は「再確認待ち」（未完了）として表示を止める。「問題なし」とは扱わず、以前の判定記録は削除しない。
- docstring は bytecode の定数に入るので、対象関数の docstring の変更でも識別値が変わる。bytecode は Python のマイナー版と `-O` の段階で変わるため、識別値はこの2つを明示的に含む。Python を更新したとき、または別の `-O` 段階で起動した worker があるときは、品質確認が1回失効し、異なる段階の process 同士は互いの PASS を採用しない。
- このモジュールは患者コンテキスト専用（`_CONTEXT_ONLY_SOURCES`）なので、`QA_VERSION` を上げても添付の抽出契約は変わらない。`semantic_audit.py`・`semantic_jev.py`・`semantic_candidate.py`・`semantic_usage_receipts.py` は専用ではなく、その変更は従来どおり添付の抽出を1回やり直させる。
- 計算は1回あたり約0.2ms（関数の hash は、関数・コード・既定値の各オブジェクトが同じ間だけ再利用する）。以前の約0.08msとの差は、資料数×呼出し回数でも無視できる大きさ（合成環境で計測）。
- 未決（所有者の決定待ち）：`semantic.fact_source` が `legacy` 以外（`shadow`・`canonical`）の場合、`assessment.policy` が `candidate_fingerprint` を含み、それは読み込んだ全コードと、ローカルのモデル（`local_llm.resolve(cfg)`）・`local_llm` の設定全体を hash する。このため、その設定では関係のないコード変更でも品質確認が失効し、P0-2c の効果はない。既定は `legacy`。現在の挙動はテストで固定している。

### 要約に使う根拠の選択（P0-3a）

`patient_context_selection.select_facts` は、要約へ渡す根拠を最大256件（`MAX_FACTS`）選ぶ。返す総数は5区分の事実の全件数で、上限で切っても総数は変えない。

- 区分の重み：12枠の周期「現在・不一致・予定・現在・未確認・不一致・現在・予定・未確認・不一致・現在・履歴」（現在4・不一致3・予定2・未確認2・履歴1）で順に取る。
- 空の枠：その区分が尽きたら、現在・不一致・予定・未確認の順で最初の空でない区分から取る。履歴の枠も履歴が尽きたら同じ順で取る。履歴以外が尽きたら残りを履歴で埋める。このため、履歴以外が残る間、先頭n件の履歴は12件に1件を超えない。
- 区分内の順：分類（`CATEGORIES` の名前順）を交互に取り、分類内は新しい順とする。新しさは `temporal.state_day`、なければ `temporal.posted_day`、どちらも読めなければ投稿時刻の日本時間の日付（`YYYY-MM-DD` の厳密な形だけを読む）、次に投稿時刻（有限の数値だけ）、最後に根拠IDの降順で決める。読めない値は最も古い扱いにし、例外にしない。
- 5区分（現在・不一致・予定・未確認・履歴）以外の区分や `CATEGORIES` 外の分類の事実は、従来どおり選択にも総数にも含めない。
- 臨床日付が投稿日より未来の場合（誤記の可能性）の上限は設けていない（未決事項）。

### 処理と原文の保持

時間帯を限定せず処理する。クラウドを有効にした設定では既存の `CloudBacklogPool` の患者コンテキスト専用子から `run_due` を呼び、個別ローカル解析の枠を待たずに進める。ローカルだけの設定では従来のレーン3から一単位ずつ処理する。新規送信、費用、ローカルへの切替と旧予約の回収は既存の実行経路が判断する。作成対象は現在の原文、個別の解析、必要な品質確認と依存資料を照合できた資料の集合とする。患者内の別資料が未処理でも、この集合から部分的な概況を作成できる。legacy方式は現行のLLM内部世代（`EXTRACT_VERSION`＝`inference_version.LLM_EXTRACT_VERSION`、現在11）、canonical方式は現在の原文に対応する検証済み投影を資料ごとに確認する（`patient_context_refresh_readiness._inference_ready`）。添付の処理待ち、再試行上限到達、保留中の資料は集合に含めず、全患者の完了とは区別する。ローカルの空き枠待ちで期限が切れた呼出しは送信前の先送りとして次の周回へ回し、患者の失敗回数に数えない。処理日のidは日本時間00:00で切り替える（`workday_window`）。日付をまたぐ処理単位は開始時のidを保ち、日付変更だけで中断や点検のやり直しをしない。A（差分）、B（未点検の履歴）、C（根拠照合）を6:3:1の順番で巡回し、空の区分は飛ばす。これは処理単位の配分で、実推論秒数や完了件数の保証ではない。患者間は未保管・最新の活動順を優先する走査と、開始時の患者ID上限を固定した公平な巡回を3:1で組み合わせる。走査位置は既存の進捗に保存し、高コストな候補確認より前に進める。活動順SQLが期限で中断しても公平な巡回の機会を残す。A・B・Cの配分位置と試行順序（`last_attempt_unit`）は候補の確認だけでは進めず、実際に処理単位を選んだときだけ更新する。1周回は最大8候補とし、未走査や期限中断を解析完了とは扱わない。全患者の確認は同じ読取スナップショット内で行い、選択後は保存用トランザクションで原文・公開版・進捗・処理権を再確認する。選んだ患者の未完了区分をA・B・Cの順番配分へ渡す。失敗時は待機時間を増やす。同じ入力・現行の確認条件で5回以上失敗した対象は、保存済みの次回予定と失敗時刻から24時間後の両方を満たした時点で日次の再評価を行う。失敗時刻がない旧記録は、保存済みの次回予定から24時間後を下限とする。品質保留・その他の保留は解除せず、不正な再試行記録は採用しない。確認条件が変わった場合は、既存の次回予定と保留の条件で再評価する。Aの失敗は患者の文章生成、B/Cの失敗は該当投稿だけを待機させ、ほかの履歴調査は続ける。B/Cで対象の投稿を確定する前の失敗では調査記録を書かず（進捗の試行記録だけを更新する）、ある投稿の記録を別の投稿へ書かない。この失敗は投稿の待機時間・失敗回数・`failed` の件数に入らず、その周回の結果（`failed` と理由コード）にだけ残る。確定前の読取りは候補の確認と同じ保存記録を読むため、続く誤りは次の周回の候補の確認で下記の `skip_patient_invalid` になり、同じ単位を選び直し続けない。一時的な誤りは次の周回で再試行する。候補の確認で1人の保存記録が値・型の誤りで読めない場合（ValueError・TypeError・KeyError）はその患者だけを飛ばして `skip_patient_invalid` に数え、最初の理由を `skip_patient_code`（登録済みコードか型名）に残す。作成対象外（`_out_of_scope`）の患者は数えない。飛ばした周回は待機として扱い、ほかに選べる作業がなければ `patient_context_patient_invalid` で先送りし、complete を返さない。同じ周回が走査中断で終わった場合は中断を優先して `patient_context_scan_incomplete` とする。周回で確認した患者が2人以上で全員が読めず、例外の型と理由コードがすべて同じ場合は、患者ごとの記録ではなく設定・コードの不具合とみなして飛ばさずに例外を上げる（患者が1人だけのときは区別できないため飛ばす）。SQLite・I/O の失敗と走査中断は従来どおり周回全体を打ち切る。

要約が有効な非空投稿は、既存の `semantic_store.reprocess_target_state` により、原資料と要約・監査の証拠を投稿単位で検証する。返り値が `current` または `current_skipped` の場合だけ採用でき、同じスレッドの別投稿に処理待ちがあっても、その非空投稿を一律には除外しない。`current_skipped` は既存方針に基づく省略の証拠を確認した状態であり、監査合格への置換ではない。

要約OFF・空本文・削除済み投稿では、semanticが有効な場合にスレッド全体の処理完了を待つ従来の条件を維持する。スレッドの取込み保留（`semantic_intake_hold`）や未保存の原資料がある場合、原文・添付OCR・抽出QC・取得範囲・権限・出典を確認できない場合も採用しない。canonicalは検証済み投影を要求し、legacyの証拠で代用しない。新しい原資料や監査失効で証拠が現在の入力と一致しなくなった場合は、処理待ちだけを理由に採用を許可しない。

選択後の保存前照合では、最新の共有進捗にある `patient_scan` の形式を検証する。走査位置以外の内容とメタ情報が選択時と一致する場合だけ、別患者の走査位置の更新を許容し、最新位置を残して選択済みのB/Cを進める。処理段階の順番（cursor）、処理単位数（units）、その他の内容・メタ情報の変更は拒否する。患者ごとの原資料、公開版、品質確認、処理世代と書込み権限の照合およびA・B・Cの6:3:1の配分は維持する。

入力はMCSの保存済みチャット原文、現在対応する連携サマリーと保存済みの過去版、現行の添付OCR原文。現在の原文に結び付く投稿要約と、検証済みの意味解析・添付解析の要約も、原文と区別した補助入力として渡す。以前の患者コンテキストは再入力せず、補助要約を事実の根拠にしない。既存26分類・35属性と引用検査を再利用する。原文と補助要約は入力上限内の区間に分け、出典・署名・区間を付けて全文を確認する。引用と属性は原文だけで検証し、全文が取得できていない資料を点検完了に数えない。クラウドを再開するときは、通常のローカル処理の途中位置や完了をクラウドの確認済み区間とは扱わない。一方、クラウドの確定的な利用不可を受けて代替処理し、`local_fallback`が厳密な`true`として保存・検証された資料は、確認済みのローカル成果物を利用し、クラウドで再走査しない。この免除は通常のローカル設定からクラウド設定への切替には適用しない。

要約の推論結果は根拠IDの選択・順序に限定し、表示文は原文の引用から復元する。推論入力では短いIDを使い、返答を元の根拠IDへ厳密に対応付ける。提示していないIDや原文にない生成文を採用しない。否定・家族・予定などを落とした部分文字列にせず、周囲の段落を保持する。人物や時点を原文以上に確定しない。Cは保存済みの引用・属性・出典を再構成して照合する。引用一致は医学的な正確性や分類の正しさの証明ではなく、人手評価の結果を自動的に引き上げない。

調査結果は投稿単位 `patient_context_scan_v1`、患者のまとめは `patient_context_v1`、進捗は `patient_context_progress_v1` に保存する。同一対象の古い状態を置き換え、再試行ごとに行を増やさない。1保存片128根拠、表示するまとめ256根拠・12引用、1回の推論入力18,000文字を上限とする。資料の全文と根拠は複数の区間・保存片に分けて扱い、表示の上限を入力全体の上限にはしない。上限超過で本文を黙って切って完了にはせず、失敗・未点検として残す。まとめの選択外にも原文と投稿単位の根拠を残し、元の履歴は削除しない。

確認済みの範囲が空本文と削除済み投稿だけで、未反映資料（`unreflected > 0`）または取得未完了が残る場合は、空の部分概況をA候補にしない。B/Cの資料解析・品質確認は続け、有用な事実を確認した範囲からの部分作成は維持する。未反映・未取得の資料がなく、全資料が空本文と削除済み投稿だけで過去の品質不合格もない場合は、既存のローカル経路で確認結果を保存し、モデル通信・クラウド処理単位・生成枠を使わない。

概況の品質確認は、受け入れる出所に処理先（provider）が指定され、利用できる本文を持つ資料が1件以上ある場合、または過去の品質不合格がある場合に必要とする。本文があるのに抽出項目が0件の場合も、必要な品質確認と生成枠の扱いを維持する。原資料・概況の不合格を、空の本文を理由に確認対象から外さない。

### 概況の作成回数と処理権

概況の新規作成は患者ごとに日本時間の1日4回、原則3時間間隔とする。原文・採用事実・処理契約と生成する処理系（クラウドの経路では処理先、ローカルの経路ではローカルのモデル）に対応する入力の識別値を使い、同じ入力の再開・有限回の品質修復を同じ1回にまとめる。日付や再起動だけでは数え直さない。全資料の処理完了を初めて反映するときは間隔だけを省き、1日4回は超えない。B/Cの資料調査・品質確認、検索、既存結果の閲覧には適用しない。

既存artifactsの `patient_context_generation_v1` へ、短い書込みトランザクションで予約と開始を記録してから推論する。保存時も処理権を照合し、概況と完了状態を同じトランザクションで保存する。終了または期限切れとなった担当の遅延結果で、新しい概況を上書きしない。送信結果不明の記録と消費回数は保持し、作業を再開するときも従来の課金証跡と再送防止を確認する。初回の未送信を実際の送信前拒否で確認できた場合だけ回数を返す。回数待ちはAの候補選択で扱い、別患者やB/Cを止めない。

消去と作り直し（下記）を除き、過去の空の概況作成で使用した生成枠・会計・送信結果の履歴は変更しない。使用済みの枠を自動で取り消さず、残っている3時間の待機と日次4回の制限を保つ。

確かめられない生成枠の記録（読めない記録・同じ入力の重複・現在より後の時刻を持つ記録）は次のとおり扱う。

- 数え方: 書き換えず、使用済みの1回として数える。同じ入力の重複は2回と数え、再開には最も古い記録を使う。読めない記録は入力を特定できないので、同じ入力でも再開ではなく新しい1回とする。期限切れの同時予約は通常どおり解放または送信結果不明へ移す。
- 時刻: その記録が持つ現在以前の時刻と、その記録より後に保存された任意のartifacts行（別患者・別種類を含む）のうち現在以前で最も早い保存時刻の、遅い方で数える。後の行がなければ、記録の時刻がすべて現在以前の場合だけその最大値を使う。
- 停止と復旧: 時刻を決められない間は、数え済みの入力の再開を除いて、その患者のAの新規作成だけを固定の理由 `patient_context_generation_unverified`（読めない記録）または `patient_context_generation_clock_changed`（未来の時刻の記録）で止める。別患者とB/Cは止めない。その記録より後に現在以前の保存時刻を持つ行が1件でも書かれると自動で再開する。それまでの明示的な復旧は消去と作り直しとする。消去は読めない記録・未来の時刻の記録では拒否せず、会計記録の不備（`accounting_unverified`）とも扱わずに、件数だけを表示して消す（下記）。
- 返す情報: 判定結果（`inspect`・`reserve_tx`）は理由と件数 `unverified_records` だけを返し、名前や本文を含めない。現行のAの候補選択はこの理由と件数を読まず、待ちを観測値 `wait_generation_quota` の件数としてだけ数えるため、状態表示・診断にはまだ理由が出ない。読めない記録・未来の時刻の記録は処理権を持たない。

### 消去と作り直し（2026-11-15 所有者決定）

`cloud-llm context-reset-plan` は、消去で消える件数・引き継ぐ使用額・今は実行できない理由を、本文や識別子を出さずに表示する（変更しない）。
`cloud-llm context-reset --preview-hash <表示された値> --confirm-human --reason ...` は、人の確認と記録（receipt）を伴って消去する（`mcs/patients/patient_context_reset.py`）。

- 前提：設定で `extract.patient_context.enabled=false`、`cloud-llm stop` で外部AIの送信が停止中、品質確認の担当が有効でない、生成枠に有効な処理権がない（読める記録で、状態が予約または開始中、記録の時刻がすべて現在以前、期限が現在より後のもの。担当の照合 `owns` が受け付ける記録と同じ判定 `patient_context_quota._live` で、`patient_context_quota.census` が数える）、作成から10分以内で結果のない patient_context の予約と Jev の品質確認がない、会計記録が読める。満たさない場合は固定の理由で拒否し、何も変えない。
- 生成枠で消去を止めるのは上の有効な処理権（`generation_active`）だけとする。読めない記録（JSONでない・オブジェクトでない・項目や型が違う・時刻が範囲外（浮動小数で表せない大きな整数を含む）・行の列が本文と合わないもの）と、現在より後の時刻を持つ記録は処理権を持たないので止めず、ほかの生成枠と一緒に消す。`context-reset-plan` はその件数だけを `generation_records`（`unreadable`・`future`）に表示し、receipt の `erased` にも残す。この件数も `preview_hash` に含めるので、確認の後に記録が読めなくなった場合や、この件数を含まない以前の形式の値では `preview_changed` で拒否する。`future` の件数は時計に依存するため、確認と実行の間に記録の時刻が現在に追いつくと、記録が変わらなくても `preview_changed` になる（その時点で期限が残る予約・開始中の記録は有効な処理権となり `generation_active` で拒否する）。会計記録（予約・結果・処分）の確認はこれと別に行い、従来どおり厳格に拒否する。
- 消去の前に、同じ書込みロックの下でデータベースのバックアップ（`patient-context-reset-*.db`。自動では削除しない）を取り、名前・大きさ・SHA-256 を receipt に残す。消去の時点で、この名前で更新時刻が直前1時間以内（時計のずれは5分まで）のバックアップが同じ大きさで残っていなければ拒否する。拒否された消去のバックアップは削除し、例外で止まったときは残して名前を表示する。同じ `--command-id` の再実行は、保存済みの消去の receipt を表示するだけでバックアップを取らない。ほかの操作の receipt なら `command_id_conflict` で拒否する。
- 確認の読取りは専用の読取り上限の中で行い、上限に達したときは `refusal: "read_incomplete"` と `stop_reason` を表示する（会計記録の不備とは区別する）。`read_deadline` は時間をおけば通ることがあるが、`reset_budget_exceeded` と `value_too_large` は再実行しても通らない。この経路の会計記録は1回の走査で読み、ほかの経路の予約を指す結果・処分があれば `accounting_inconsistent` で拒否する。
- 消すもの：患者コンテキストの公開版・調査結果・進捗・生成枠・品質判定（要約・原典）・修復とその候補、品質確認の担当（`fetch_jobs`）、route=patient_context の予約・結果・処分の会計記録（予約が整理済みで残っていない結果・処分を含む）。公開版はすぐ表示されなくなる。生成枠は引き継がないので、消去の後は全患者の1日4回・3時間間隔の数えが0から始まる（読めない記録しかなかった患者も、読める記録の患者と同じ）。使用額は次の引き継ぎで数え続ける。
- 残すもの（「前回」位置を残すので、作り直しで消去の前からある記録に再び見つかった事実は「過去記録から追加発見」に出さない。消去の時刻を `patient_context_reset_mark_v1` に、患者ごとに消去前の公開版が持っていた事実の識別値（記録・版・分類のハッシュ。本文は含めない）を `patient_context_reset_prior_v1` に残す。消去前の記録でも、公開版になかった分類の事実は追加発見として出す）：閲覧者ごとの「前回」位置、通知カードの封印済み表示、依存喪失の記録、ほかの route（再抽出・意味解析・添付OCR）の会計記録。
- 使用額：消す会計記録の額を、日・期間予算の開始時刻の前か後か・提供元・精算の別に合計し、各合計をその中で最後の予約の時刻に置いた引き継ぎ記録（`cloud_usage_carryover_v1`）に残す。消去の後で期間の開始を動かした場合や、消去の時に期間予算が設定されていなかった場合は多めに数えることがあり、少なく数えることはない。1日・1か月・期間の上限判定と使用額の表示はこれを数え続け、精算できていない分は最大額のまま未解決として数える。消去の前後で使用額の報告が一致しなければ取り消す。
- Jev：患者コンテキストの品質確認の使用記録は消し、今日の分は使用数だけを残して Jev の1日の上限に数え続ける。
- 消去の後に `enabled` を戻し、`cloud-llm resume --confirm-human` で送信を再開すると、通常の処理で作り直す。消去後は患者コンテキストの較正の標本がなくなるので、作り直しの見積り（`cloud-llm estimate`）は消去の前に取る。

### 公開と失効

生成・限定閲覧は `extract.patient_context.enabled` / `publication` の省略時にともにtrue。既存環境でも省略したまま更新すると有効になり、明示falseは尊重する。不正な型・未知キーは両方falseとして設定診断で拒否する。原文hash、抽出の内容・世代、取得状態、患者対応、走査契約・要約契約と受け入れるクラウドの処理先を入力署名へ含め、処理系のモデル名は入力署名に入れず成果物ごとの出所で照合する（ローカルのモデルを変えてもクラウドの成果物は失効しない）。通常の再取得時刻や日付の変更だけでは作り直さない。原文・補助要約・添付OCRの追加や訂正で入力署名が変われば、同じ日でも再確認する。抽出項目が同じでも、入力署名や処理先が変わったまとめは再評価する。推論前後に署名と調査状態を照合する。推論中に書込みトランザクションやrun lockを保持せず、保存時だけ短い排他区間でdata_versionも再確認する。原文の区間調査や必要な品質確認が終わっていない資料は概況に含めない。作成時の対象キー・出典・署名と件数を固定し、選択から品質監査、保存、表示まで同じ集合を照合する。取得途中や未反映の資料があっても、確認済みの集合は部分的な概況として利用できる。

閲覧時にも同じ署名と引用を検証する。採用済み資料の削除・訂正・対応変更・観測済みの権限失効がある場合は古い文章を返さない。新着の追加だけでは以前の集合を失効させず、現在観測している集合外の資料を未反映件数として区別する。この数は未処理や医学的な欠落の件数とは限らない。対象外の資料に由来する中止・訂正情報の喪失も、同じ臨床項目への採用制限として保持する。未取得の上流変更まで検出できるという保証ではない。閲覧者・患者・チャネルの許可は既存通知の認可経路を使い、職種は欄の順番だけを変える。

前回からの変化は、閲覧者と通知先の識別値をhash化したキーと表示依頼時刻で比較する。これは送信成功・既読・臨床上の確認完了の記録ではない。新着・遡及取得はfirst_seen、訂正・削除は既存改訂履歴、過去記録の追加発見はfound_atを使う。削除した本文は表示しない。共有チャットへの自動配信は追加しない。

### 状態別件数と表示の文言

`doctor --probe data` の `patient_context.states`（`patient_context_status.state_counts`）は、保存済みの最後の結果（`basis: "last_stored_outcome"`）を数える。現在の `_inference_coverage` の再計算ではなく、作業待ちの件数 `counts`（患者ごとの走査、1秒で打ち切り）とは別に、1秒の上限で読む。アーカイブしていない患者を `invalid`（読めない記録あり）→`held`→`failed`→`dependency_gap`（依存の不足が未解消。依存喪失の記録を持つ患者について `inference_dependency_loss.read` が未完了と返す場合で、監査済みの coverage 行で解消した gap は含まない）→`published`→`in_progress`（記録あり・未公開）→`no_record`（未着手）の優先順でちょうど1区分へ入れ、合計を `patients_total` と一致させる。gap でも coverage でもない依存喪失の記録（恒久的な否定利用の障壁）を持つ患者は `dependency_loss.patients` に別に数え、解除可否は `unclassified` とし、区分にも注意にも使わない。読み手は `sqlite3.Row` で列名参照するため、`state_counts` は呼出し中だけ接続の row factory を `sqlite3.Row` にして元へ戻す。読めない行・型の誤り・不正な原典キーは `invalid_rows` に数え、完了側へは数えない。資料の保留・失敗は、投稿が削除・空本文になった場合と、保存時の `source_binding` が現在の原文と異なる場合は数えない（その患者は `in_progress` に残る）。`source_binding` を持たない旧行は保存された結果のまま数える。失敗コードは登録済みの `patient_context_*`（旧 `nightly_*` は読み替え）だけを出し、ほかは `other` にまとめる。照合の保留は `quality_held` とする。患者名・本文・個別の患者IDは出さない。読取りに失敗した場合は `states` を `null` とし0件とは扱わない。`counts`・`lanes`・`states` はどの経路（未確認・失敗・設定不正）でも同じキーを持つ。`counts` は記録が値・型の誤りで読めない作成対象の患者を `invalid` に数え、ほかの患者の集計を続ける。`lane_metrics`（doctor の `lanes`・health.json の `patient_context`）は JSON オブジェクトでない最新行を例外にせず `invalid_rows` に数え、レーン別・照合状態（none を含む）の件数へ入れない。`lane_metrics` の `invalid_rows` は health.json にだけ出す。doctor は同じ最新行（`invalidated` の調査記録を除く）を `states.invalid_rows`（読めない行）として表示し注意にするため、二重には出さない。保留・失敗・未解消の依存不足・読めない記録（`states` の区分・行、`counts.invalid`）が1件以上あれば注意、`states` か `counts` のどちらかが得られなければ確認できません、両方が得られて問題がなければ正常とする（`lanes` は状態判定に使わない）。

🧾 の状態行は `_inference_coverage` の全状態（`patient_context_status.COVERAGE_STATES`）に日本語を持ち、未知の値は「解析状況を確認できません」と表示して省かない。保留・失敗は事実だけを示し、再開・再試行の予告は付けない。`dependency_gap` で依存の内訳（`terminal`・`repairable` の整数）がある場合だけ「復元できない記録／原本の再点検待ち」の件数を添え、内訳がない場合は0件と表示しない。復元できない記録がある間は再点検だけでは解消しない（`_inference_ready` は `terminal` が0の場合だけ再点検を許す）。

### 段階的な評価（生成だけの評価はpublication=falseを明示）

- R0: 一時DBと完全合成の本文・応答で、境界時刻、次の周回での再開、競合、失敗、失効、表示・認可を検証する。実患者DB・Keychain・実LLM・通知先へ接続しない。
- R1: 運用者が許可した私有snapshotと隔離した評価先で、従来の抽出と根拠IDを比較する。追加情報・不一致・臨床的に重要な項目は別の評価者が原文を確認する。評価用の実データをrepo・fixture・外部レビューへ含めない。
- R2: 明示した本番設定でenabled=true/publication=falseとし、数日の未生成件数、進捗、失敗、既存処理の遅延、モデルの占有時間を測定する。HTTP期限切れはbackend停止の証明ではないため、LLMレーン3のadmission（更新・回路・設定・メモリ・ディスク）とターンロックの実際の解放を確認する。合成テストだけで実機遅延ゼロを保証しない。
- R3: R1/R2の評価でpublication=falseにしていた場合、結果を確認してpublication=trueへ戻す。既定の限定閲覧も既存の許可範囲内に限る。旧文の失効・未反映新着・取得範囲を確認する。無効化すると保存済みの患者コンテキストも表示しない。
