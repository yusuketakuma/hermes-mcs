# 患者背景情報の構造化契約（1.0.16）

既存の `extract_v1` / `extract_llm` artifact に `patient_context` 配列を追加する。患者テーブルやDB schemaを変更せず、保管済み本文・連携サマリーと同じ患者スコープで扱う。

| 属性 | 契約 |
|---|---|
| `category` | 基本情報、診断、既往、経過、ADL、生活、介護度、サービス、担当者、連絡先、アレルギー、機器、意向、服薬管理、栄養、認知、副作用経過、検査・観測、フォローの19分類。列挙正本は `patient_context.CATEGORIES` |
| `text` | 根拠引用に含まれる原文値。否定・過去・予定・条件・未確認を残し、推測や臨床的な確定値への変換をしない |
| `evidence` | 対象本文の一意に照合できる引用。別投稿・参考コンテキストの引用は拒否 |
| `subject` | LLMは `patient` / `family` / `other` を必須にする。見出しルールは対象者を推測せず `unspecified` |
| `details` | 27属性の `{key,value,evidence}` 配列。値は原文文字列、引用は同じ親引用内で一意に照合できること。キー正本は `patient_context.DETAIL_KEYS` |
| `origin` | 見出しルールの場合 `explicit_heading`。LLMの生成文字列をコードや指示として実行しない |

ルールは明示された見出しから次の見出しまで複数行を保持する。対応外の装飾見出しやコロン見出しは境界として区切り、前項目に取り込まない。全ての自由文から網羅的に情報を得られるルールではない。見出しがない文章の追加抽出は既存ローカルLLM経路で行う。入力全体を既存の長文分割で処理し、一部の失敗を完全な抽出結果と扱わない。

LLMのJSON grammar・項目検証・修復・chunk統合・batch・checkpointに同じ契約を適用する。LLM世代6・詳細契約2へ進め、既定1600 tokensは維持する。旧世代の成功・失敗結果を通常pendingへ戻し、新しい失敗予算・lease・chunk・QCの境界で再抽出する。ルール世代12への更新で既存本文の明示情報を通常のrun_pendingで補完する。

## 読取りと要約

既存 `evidence` / `timeline` / `search` / `thread` に根拠付きの項目を付ける。`read_model` の各投稿は最新のhash一致したv1とLLMを選び、canonical projectionがLLMを覆っていても追加情報を保持する。削除・不完全本文・古いhash・別患者・壊れた項目は採用しない。既存のlimit/cursor/total/truncated契約を維持する。

`read_model --scope detail` は原文値・引用・出典を返す。`aggregate` は分類と件数だけを返し、原文値・引用・記入者名を含めない。`project_metadata` は連携サマリーの `reported` / `fetched_empty` / `not_fetched` / `unknown` を区別し、別の出典として保持する。旧schemaのkarte_id欠落は未確認として扱う。

rollupの `patient_context` は `memo` と `chat` を別々に持つ。チャットの分類ごとに最新の報告投稿から全項目を集約するが、現在の確定した患者状態を意味しない。全文と以前の報告は詳細読取りに残る。本人限定の患者まとめには原記録の短い抜粋を追加し、基本情報・連絡先の分類は抜粋に出さない。共有カードに詳細を自動掲載しない。

連携サマリーは既存GET・認証・保存経路を使う。deep runは未取得を優先し、24時間経過したサマリーを再取得する。背景対象10件・段全体12GET・deadline余裕60秒・失敗後6時間の待機を維持し、保管済み患者は除外する。失敗しても最後の成功内容を保持する。

## 検証範囲

完全合成の複数行、長文、否定、家族、相異記載、編集・削除・別患者・壊れたJSON、一意引用、canonical優先度、旧schema、ページング、サマリー更新を確認する。実履歴の参照はローカルsnapshotの読取りと集計だけで行い、原文・患者名をfixture・文書・外部へ移さない。合成テストや引用一致は、実LLMの抽出精度・網羅性や実APIの全項目取得の検証ではない。

利用方法は [USER_GUIDE](../guides/USER_GUIDE.md)、全体レビューと未修正事項は [レビュー記録](../dev-records/review-1.0.16-20261007.md) を参照。

## 対応した詳細情報

以下を既存meds／labs／patient_context／requestの経路で保持する。副作用経過・観測・followupを別分類にし、19分類と27属性で区別する。実機での追加取得を完了した記録ではない。

| 優先 | 情報 | 役立つ場面・既存経路 |
|---|---|---|
| 1 | 全使用薬の実態：他院処方、市販薬、サプリ、実際の服用量・頻度、処方元、残薬・飲み忘れ | 既存medsと服薬管理を拡充。MCSのmedication_periodsは薬名・期間のみで用法・用量・処方元が無いため、チャット・原記録の確認を併用。医薬品master未収載を薬剤無しと扱わない |
| 1 | アレルギー／薬物有害事象の詳細：対象薬、症状、発生日、疑い／人による確認、対応、転帰 | allergy_intolerance／adverse_drug_eventと既存背景分類を利用。薬剤変更後の症状だけで因果関係を確定しない |
| 1 | 検査・観測値：体重、Cr/eGFR、肝機能、血糖などの値・単位・測定日・検体／条件 | 既存labs・clinical_values・任意のobservation_items/values取得を利用。基準範囲や測定日が不明な値を現在値と推測しない |
| 2 | 服薬支援の実行条件：嚥下、剤形の扱いやすさ、一包化、自己管理能力、誰がいつ支援するか | 既存ADL・栄養・服薬管理・担当者の原文を詳細化。職種が分かることと、行為の担当が確定していることを区別 |
| 2 | 療養移行と結果：退院・転院に伴う処方差分、支援後の変化、次回確認項目・担当・期限 | 既存イベント／処方変更／依頼／返信状態を組み合わせ、人承認を経ず依頼を確定しない |
| 共通 | 出典、観測日、投稿日、最終確認日、確認者、本人／家族／他者、確定／伝聞／未確認 | 抽出日や新しい投稿日を臨床情報の最新確認日と読み替えず、原文根拠と別々に保持 |

登録済みの処方期間と検査・観測値には既存の任意取得経路がある。一方、患者カルテ全40項目の一括取得は、機微項目を含み正確なkey契約が未確定なので、必要な属性を限定して別途検証する。氏名・写真・住所・連絡先を利用目的なく増やさない。

臨床上の収集項目の参考: 厚生労働省[高齢者の医薬品適正使用の指針（各論編・療養環境別）](https://www.mhlw.go.jp/web/t_doc?dataId=00tc4324&dataType=1&pageNo=1)。本表の実装優先度は、この指針の情報項目と既存コードの取得経路からの設計判断。

## 定期取得の有効化と再開

`clinical_metadata` はbool・既定false。`mcs setup init --yes --set clinical_metadata=true` で明示選択した環境では、既存deep runがキャッシュ済みsessionだけで登録薬剤・観測項目・各項目値を巡回する。GETのみ・no_extend_session・名前保持なし・medical/現在karte mapping限定・archived除外。相談groupの関連付けは推測しない。

各deepはHTTPの内部再試行・session probeも含め12GET、25秒、親deadlineの60秒前まで。予算による保留は次回再開し、未完を登録0行・失敗・完了と扱わない。患者ごとに全観測項目を巡回し、1項目のHTTP失敗で後続を止めない。薬剤登録／項目発見／session失効は6時間待機。成功した一巡後24時間、失敗を含む一巡後6時間で再試行する。

観測定義と値をkarte ID・項目ID・成功定義世代・定義fingerprintへ束縛する。同じ定義の再取得時刻だけで旧値を無効化せず、正規化した旧pinと新しい全定義が同値であることを証明する。実差分・破損・別mappingは旧値を現在値へ出さない。失敗時の最後成功内容は履歴として保持する。

初回入力は共通の `clinical_chunking.plan_chunks` で見出し・段落・文・関連する連続行を優先して分割する。薬剤の用量、観測項目、変更・支援・予定、明示フィールドなどの密度と原文長から出力量の目安を算出する。これは実token数や処理時間の保証ではなく、未知の自由文も全て処理対象に残す。短い高密度投稿も事前分割し、低密度の短文は1単位のままにする。連結は空白・改行を含め原文と完全一致し、各単位は既存入力上限以下にする。

出力が実際にlength打切りされた場合は失敗した区間だけをさらに細分化し、既存checkpointへlayoutを保存する。完了済み区間を同じ実行中と中断後の再開で再利用する。分割履歴と結果を本文hash・投稿日時・実モデル・prompt・分割契約・参考文脈に束縛し、全文が完了するまで本抽出を完了保存しない。各区間へ渡すルール候補も当該本文の範囲へ限定する。参考コンテキストだけの値を対象投稿からの値と扱わない。

canonicalのmanifestは共通分割と同じ原文境界にatom所有を割り当て、見出し・隣接atomを参照専用に保持する。分割契約をchunk世代とbundle fingerprintへ含め、古いlayoutと新しい証拠所有を混ぜない。category_presence等の必須判定、subject・否定・時制・根拠を維持し、任意の空欄・重複説明のみ省く。

本人限定の患者まとめは最新20投稿の処理中・完了・要確認と完了区間数を表示する。現在の原文・モデル・prompt・分割契約・設定に合う検証済み結果だけを採用し、途中結果や古いPASSを完了扱いしない。以前の投稿はこの進捗表示の対象外と明記する。抽出処理の完了は臨床情報の完全性や臨床対応の完了を意味しない。共有通知に進捗行を追加しない。

v6のprefilterは完全一致の短い挨拶3種だけを省き、語彙netで臨床情報の不存在を判定しない。了解・承知・ありがとうなどの返信、見出しなしの嚥下・支援情報もLLMへ送る。稼働枠・token予算・timeout・admission・認可を維持するため、旧履歴の再抽出と対象拡大は通常workerで順次処理される。

canonical v3/v4の既存事実にもoptional patient_contextを同じ事実引用・対象へ拘束して保存し、属性の意味づけも既存監査へ含める。新promptでbundle/chunk世代を更新し、投影世代3へ進める。source/doc_hash・PASS・公開fence・人承認・admissionを維持する。legacy書込みの制限を解除して同時書込みさせない。

登録データ・チャット・連携メモは別出典で読取り、原文・属性・以前の記載はdetailに保持する。自由文メモで見出し抽出できない部分はdetailのcomment/unclassified_textで原文と未分類状態を示す。aggregateでは値・引用・氏名・具体日時を返さない。候補・未取得・古い情報を現在の確定患者状態と推測しない。

## 大量の観測値と安全上限

自動取得は検証済みの50行pageごとに、karte・項目・定義fingerprint・timestamp・総数・取得policyへ拘束したchecksum付きstageを私有DBへ保存する。1slice5pageやGET／deadline予算で保留した場合は次deepで同じsnapshotの続きから再開する。stageは読取り公開せず、全pageの終端と総数が一致した場合だけclinical artifactをcomplete保存する。TS・mapping・定義・policyが変わった／破損したstageは再利用しない。

観測値は1項目1万行まで、登録観測項目は250項目までを支持する。容量超過はcapacity_limitとして未完を明示し、部分行を現在値にしない。他の項目の取得は続ける。既存manual取得の5page上限は維持する。未知のAPI項目や確認できない情報まで推測で作る意味での「全て」ではなく、指定情報の受入・保存・再処理と取得可能な全pageの対応である。
