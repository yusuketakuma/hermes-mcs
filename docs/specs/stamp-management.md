# MCSスタンプの取得・表示・人承認操作

この仕様は保管した投稿のスタンプを読み取り、人が確認した操作だけをMCSへ送る経路を定めます。対象は根元投稿と返信投稿です。添付ファイルを画面で選んだ場合も、そのファイルを含む投稿を操作します。ファイルごとのリアクションは作りません。

本書は現在のコード契約を説明するもので、実MCSへの操作成功、配備完了、実APIの互換性や性能を証明するものではありません。

## 責務と正本

| モジュール | 所有する責務 | I/Oと接続の扱い |
| --- | --- | --- |
| [stamp_contract.py](../../mcs/stamps/stamp_contract.py) | 種別・表示語彙、受信集計の正規化、設定の検証 | 純粋な値の検証。DBやAPIには接続しない |
| [stamp_read.py](../../mcs/stamps/stamp_read.py) | 押下者の再取得対象選定と、保管済み押下者の状態読取り | 渡されたSQLite接続を借用する。接続の生成・commit・closeはしない |
| [stamp_format.py](../../mcs/stamps/stamp_format.py) | 件数・本人分・押下者名・観測時刻の整形 | 渡された値だけを整形する |
| [stamp_write.py](../../mcs/stamps/stamp_write.py) | フォーム、操作受付、送信前照合、試行記録、結果照合・通知 | 受付はコマンドreceiptと同じトランザクション。API操作は受付commit後、呼出元がrun.lockを保持した状態で行う |

投稿メタデータ全般のデコードと読取りは、[message_observations.py](../../mcs/core/message_observations.py)が所有します。本文の正規化は[mcs_payload.py](../../mcs/ingest/mcs_payload.py)、実際のHTTP通信は[MCSAdapter](../../mcs/ingest/mcs_adapter.py)の責務です。通知・シグナル・表示側は各正本を直接使い、表示モジュールを取得や書込みの入口にしません。

## 種別と観測の意味

| APIの種別 | 表示 | 絵文字 |
| --- | --- | --- |
| `viewed` | 見ました | 👀 |
| `accepted` | 承知 | 🙆 |
| `thanked` | 感謝 | 🙏 |
| `good` | いいね | 👍 |
| `completed` | 完了 | ✅ |

書込みではこの5種だけを認めます。取消は種別ではなく、本人のスタンプを取り消す別の操作です。`all`は押下者一覧の集計用で、書込み種別には使いません。読取りでは形式が正しい将来の種別も保持し、未知の表示として扱います。未知の本人スタンプや複数の本人種別を、書込み前の既知状態として扱いません。

受信集計は`type`・`count`・`self_reacted`を検証します。取得済みの空配列は「スタンプなし」、未取得・不正値・取得失敗は「不明」です。空配列と欠測を置き換えません。表示時刻は押下時刻ではなく、取得して観測した時刻です。

本人の投稿に付いた件数表示では本人分を除き、本人が押したスタンプは別に表示します。押下者一覧は`complete`・`stale`・`failed`・`not_fetched`を区別します。再取得が不完全な場合は、過去の押下者を削除せず、取消があったとも判断しません。押下者の完全取得結果は24時間で古い状態となり、集計の更新でも再取得対象になります。

## 有効化と本人の確認

次の両方を設定すると、書込みは既定で有効になります。`stamps.enabled=false`で無効にできます。どちらかが未設定なら無効のままで、MCSアカウントや操作者を推測して補うことはありません。

- `stamps.operator`: 操作を認める1人の通知先利用者。`discord:<id>`、`slack:<workspace>:<user>`、`lineworks:<namespace>:<user>`のいずれか。
- `stamps.account_user_id`: スタンプを送るMCSアカウントの正の整数ID。

通知の対話操作が有効であり、operatorの接続先が現在の通知先と一致することも必要です。人が入力したIDで操作対象やMCSアカウントを差し替えることはできません。送信前にはその時点の`users/self`を取得し、設定・承認に記録したMCSアカウントIDと照合します。`users/self`がIDを返さない場合は、同じセッションで所属ステーションの名簿を取得し、本人（`is_self`）が1人に特定できたときだけそのIDで照合します。名簿の取得失敗・本人不明・複数該当では送信しません。保存済みの本人プロフィールだけでは送信を許可しません。

有効・無効を切り替えると、対象カードの操作メニューを更新します。LINE WORKSでは送信済み投稿を編集しないため、定期処理で既存の対象カードの更新版が順に追加投稿される場合があります。操作者とMCSアカウントが未設定の環境では、この設定差分による更新は行いません。

患者のアーカイブ状態、カードの失効、現在の通知先、投稿の所属・親子関係・完全な本文・本文hashも照合します。承認後に条件が変わった場合、その承認を新しい対象へ転用しません。

## 画面から受付まで

スレッドカードには、MCS本体のスタンプ欄にならい、表示中の最新投稿（返信がなければ根元投稿）の下に5種類のスタンプを同じ順（👀見ました・🙆承知・🙏感謝・👍いいね・✅完了）で並べます。SlackとDiscordは絵文字を中心に、LINE WORKSは名前付きで表示します。押したスタンプは1回の操作で送信を受け付け、自分が押しているスタンプ（強調表示）をもう一度押すと取消になります。ボタンは表示時の追加/取消と自分のスタンプを固定しており、押下時にMCS上の自分のスタンプが変わっていれば送信せず拒否します。受付の期限は、ホストが記録したクリック時刻から20分です。この1回押しは確認画面を挟みませんが、下記と同じ`ops.mcs_reaction`のreceipt経路を通り、理由には「カードから直接操作」を記録します。同じボタンの再送・二重押しは、操作者・設定・カードを確認し直してから最初の受付を返し、二重には送りません。カード上の表示はMCSで反映を確認した後の再描画で変わります。ほかの行を組み立てた後で行数・部品数が足りないカードではこの列を省き、下記のフォームだけを出します。

Slackでは通常操作を選択メニューへ集約し、5種類のスタンプと既存フォームの「別の投稿」を`context_actions`内の`feedback_buttons`3組にまとめます。自分のスタンプは`✓`で示します。各組の`action_id`に2個の既存トークンを含め、クリックの`value`がそのどちらかであることを検証します。カード更新時は`block_id`も変更します。既存のworkspace・app・channel・操作者・投稿・患者scope検査を通し、組の経路は`stamp_press`または`stamp`だけに限ります。5種類とフォームが揃わない旧specでは通常のスタンプボタンを保持します。Discord・LINE WORKSの描画と共通の操作受付契約は変えません。

Slack APIが小型表示を`invalid_blocks`で明確に拒否した場合だけ、現在の送信権限を再確認し、従来のスタンプボタンとメニューの`MCSスタンプ`へ描画し直して1回再試行します。本文・操作トークン・送信先を保持し、更新を新規投稿へ変更しません。タイムアウト・結果不明・その他の拒否ではこの再試行を行わず、旧形式も拒否された場合は止まります。通常の429待機・再試行の上限は変わりません。ログには固定コード`slack_compact_stamps_unsupported`だけを記録します。

このSlack小型表示は開発候補です。公式の[小型操作ブロック](https://docs.slack.dev/reference/block-kit/blocks/context-actions-block/)と[2個組のボタン](https://docs.slack.dev/reference/block-kit/block-elements/feedback-buttons-element/)の契約を使いますが、iOS/Android実機の配置・連続クリック・選択状態と実際のイベント形式は未確認です。本番反映前に、非機密の専用投稿で追加・反映確認後の同じボタンによる取消・「別の投稿」の動作を確認します。クライアント内の一時的な選択表示はMCS反映の証拠とせず、MCS読取り後の`✓`と保存済み結果を正本とします。図や合成テストをこの確認の代用にしません。

ほかの投稿は、Slackの「別の投稿」（小型操作欄がないときは「MCSスタンプ」）、Discord・LINE WORKSの「MCSスタンプ」操作で、runnerが返したフォームを使います。フォームはカードのsource generation、token、表示済みmanifestに拘束されます。既存スレッドカードのページ上限は8投稿で、スタンプフォームは該当manifestから最大20投稿までを候補にします。全履歴から任意の投稿を検索して操作するフォームではありません。

利用者は投稿、スタンプ、理由を選び、プレビューで確認してから承認します。スタンプの選択肢もMCSと同じ順で、自分が押しているスタンプを選ぶと取消になります（この形式より前に開いたフォームの「取消」も受け付けます）。添付の表示があっても、選択されるのはその添付を含む根元投稿または返信投稿です。本人スタンプが未取得・不明・処理中の投稿を、新しい操作の根拠にはできません。

共通UIはフォームに含まれるIDとhashから`ops.mcs_reaction`を組み立てます。人の確認、actor、理由、command IDを伴い、[mcs_requests.apply_command](../../mcs/ops/mcs_requests.py)を経由します。理由は空欄不可・最大200文字です。受付時にもフォームhash、本文hash、観測した本人状態、通知先と権限を再検証します。

受付成功の`queued`は送信完了ではありません。receiptと操作artifactを同じDBトランザクションで保存してから、定期処理の[run_check.py](../../mcs/ingest/run_check.py)が送信処理を行います。同じcommand ID・同じpayloadの再送は既存receiptを返し、別payloadで同じIDを使うと拒否します。受付中・結果不明の操作がある投稿には、別commandで重ねて送信しません。

現行の入口は通知カードの対話操作と共通コマンド経路です。専用の`mcs stamp` CLIや、スタンプ試行記録を修復・削除するCLIは提供していません。`mcs recover`による更新復旧を、スタンプ操作の再承認や再送とみなしてはいけません。

## 送信・取消・照合

| 操作 | 実行方法 |
| --- | --- |
| 追加 | 選んだ種別で1回のPOSTを試行する |
| 変更 | 新しい種別の追加POSTを1回試行する。先行する取消POSTは送らない |
| 取消 | 本人分の取消POSTを1回試行する。種別や他者IDを指定しない |
| 変更不要 | 最新GETの状態が希望どおりならPOSTせず確認済みにする |

送信は次の定期収集で処理し、新しい送信は人が確定した時刻から1200秒以内に限ります（確定時刻を持たない旧形式の要求は受付時刻から数えます）。既定10分間隔の収集と処理時間を見込みますが、遅延による期限切れは送信せず拒否します。送信前の最新GETでも承認時の本人状態と一致し、現在の対象条件を満たすことが必要です。送信直前には残り実行時間も確認します。送信後は同じ投稿を再取得し、希望する本人状態を観測できた場合だけ`confirmed`にします。HTTP成功statusだけでは確認済みにしません。

1回でも送信を試みる前に、DB外の試行記録を永続化します。通信例外や送信後の取得失敗では、反映していないと推定して再送せず、`unknown`として保持します。以後の照合はGETだけです。例外として、POSTにMCSが4xx（401・403・408・429を除く）を返し、直後のGETで承認時の本人状態のままと確認できた場合は、受け付けられなかったと判断して`rejected`（`stamp_server_rejected`）で終えます。この場合もPOSTはその1回だけで、同じ投稿の新しい操作は受け付けます。1200秒の受付期限を過ぎても、既に試行記録がある操作のGET照合は可能ですが、新たなPOSTには戻りません。端末側の追跡が終わっても、試行記録を消して再送可能にはしません。

| 状態 | 意味 |
| --- | --- |
| `queued` | 人の承認を受け付けて保存した。送信前または実行待ち |
| `confirmed` | 希望状態を観測した、または既存の確定試行記録を復元した |
| `unknown` | 試行した結果を確定できない。自動再送しない |
| `rejected` | 対象・権限・状態などの条件が合わず拒否した |
| `held` | 今回の処理を安全に進められなかったことを示す処理件数。独立した成功状態ではない |

結果は既存の非公開followup経路へ保存し、必要なカードを再描画します。UI側のfollowup保持上限は840秒です。この値は処理完了の保証や新しい送信許可の期限ではありません。followupの通知期限や通知失敗によって、保存済み結果・試行記録を破棄しません。

## DB復元と試行記録の保護

試行記録はローカルの`data/stamp_operations/`に保存します。`instance.json`とDBのinstance artifactが同じnamespaceを持ち、配下の`<project_id>-<message_id>-<mcs_user_id>/`にcommand IDごとの記録を置きます。ディレクトリは0700、ファイルは0600で扱い、読取り時も所有者・リンクなどの条件を確認します。

このディレクトリはDBの巻戻しに影響されない送信済み判定のためのもので、オフサイトバックアップではありません。記録には投稿・アカウントの識別情報が含まれます。一般公開、repoへの追加、外部送信の対象にしません。

DBを復元して操作が`queued`に戻っても、同じnamespaceの試行記録があればPOSTを再試行しません。`started`・`unknown`はGET照合だけに進み、`confirmed`・`rejected`は確定済みの結果を再現します。その後の投稿状態が変わったことを理由に、過去の承認をもう一度実行しません。

新しいrootへDBだけをコピーし、元のnamespaceや試行記録がない場合、既存承認を自動実行しません。namespace不一致、不正な記録、復元保留中も処理を保留します。この場合は未試行かどうかも確認できないため、受付期限を過ぎても自動解除しません。管理者が元の試行記録と復元状況を確認する必要があります。自動復旧や記録削除による再送解除は提供しません。

試行記録は同じ投稿・MCSアカウントのscopeごとに最大512件です。確定済みの記録も含み、上限に達すると新しい操作を拒否または保留します。自動削除はありません。容量を空けるために記録を削除するとDB復元後の重複送信防止を損なうため、本仕様は削除手順を定めません。

## 公開クライアントの根拠と検証範囲

2026-10-20に保存した[MCS公式サイト](https://www.medical-care.net/)の公開JavaScriptの静的調査では、次の送信意図を確認しています。認証付きAPIへの書込み結果やサーバの保証とは区別します。

- [message service](https://www.medical-care.net/chunk-HBPHJEEZ.js)は追加・取消のどちらもPOSTを使います。追加は`/messages/{id}/reactions`、取消は`/messages/{id}/reactions/delete`です。
- [timeline caller](https://www.medical-care.net/chunk-WZQSH3CG.js)は追加に`reaction_type`を渡し、取消では本文引数を省略します。異なる種別への変更では先行する取消を送りません。
- [HTTP helper](https://www.medical-care.net/chunk-KDTEL5ED.js)と[HTTP client](https://www.medical-care.net/chunk-EKDSNJRJ.js)の対応から、追加はform-urlencoded、取消は空本文となり、Content-Typeを追加しません。

MCSAdapterはこの形式で、既存セッションから1回だけPOSTを試行します。操作のための自動ログイン、セッション再確認による再試行、通信例外後の再送は行いません。公開クライアントのコードだけでは、サーバの置換処理の原子性、冪等性、全ての取消条件、既読・セッションへの影響は保証できません。

完全合成のDB・スタブによるテストは、wire形式、入力・本人照合、受付receipt、単一試行、結果不明時のGET限定、DB復元とnamespace保護を検証するためのものです。実API・通知サービスの実接続試験、ユーザー実データでの確認、性能測定の代わりにはなりません。過去の取得計画と調査履歴は[スタンプ取得計画](../roadmap/stamps.md)に残し、現行の書込み契約は本書と実コードを参照します。
