# Jev・Anthropic・OpenAIの設定と利用状況

このMCSの `.env` にAPIキーを登録すると、設定で無効化していないサービスを自動で使用します。
キーの登録前に、対象の投稿本文・患者情報を外部サービスへ送ることと、利用料金を確認してください。
本文や患者名を自動で匿名化する機能はありません。

## キーと自動有効化

| サービス | `.env` の変数名 | mode未指定でキーがある場合 | 処理対象 |
|---|---|---|---|
| Jev | `TYPESAFE_API_KEY` | `semantic.mode=assist` | 既存の意味チェック |
| Anthropic | `MCS_ANTHROPIC_API_KEY` | `cloud_llm.mode=on` | 患者コンテキストの作成・更新と、その品質修復（保存済み投稿の再抽出・意味解析は、再開期間を設定した間だけ。下の「保存済み投稿の再抽出」の説明を参照） |
| OpenAI | `MCS_OPENAI_API_KEY` | `cloud_llm.mode=on` | 選択した場合、Anthropicと同じ処理対象 |

キーはMCSの導入先にある `.env` に保存し、所有者だけが読み書きできる権限 `0600` にしてください。
通常ファイル・所有者・権限・サイズを確認して読み取ります。同じキーの行が複数ある場合や、値に空白・制御文字がある場合も読みません。プロセス環境やHermesのキーは流用しません。
キーの値をチャット、診断資料、Gitへ含めないでください。
入力中に設定や保存先が変わった場合は保存を止めます。保存後は内容を読み直して確認し、確認できない場合は結果未確認と表示します。
以前にプロセス環境やHermesの `.env` だけへ登録したJevキーは、このMCSの `.env` へ移す必要があります。
権限が `0640` や `0400` のファイルも読みません。移行できていない場合はキー未設定として送信を止めます。

modeと対象患者の設定を両方省略した場合、自動有効化されたサービスは全対象を処理します。
明示した `mode=off`、対象患者、除外設定、低い利用上限は維持します。
既存設定に `off` や予算 `0` がある場合、キーの追加だけでは有効になりません。
キーがない場合は外部へ送信しません。個別投稿の抽出・意味解析はローカルで継続し、クラウドは患者文脈の作成・更新に使います。クラウドを利用できない間も、ローカルでは受付条件を満たす処理を進めます。途中結果の処理先、品質の不合格、未精算の送信記録は保持し、切り替えただけで公開条件を解除しません。
`config.json` を読み取れない間（JSON構文の誤り、重複キー、NaNなど）は、キーがあってもAnthropic・OpenAIへ送信せず、保存済み回答の採用も保留します。設定の確認不能だけでは回答を破棄せず、利用記録も保持します。
`mcs_setup.py check` で設定ファイルの問題を確認してください。

Jevの自動有効化は `summary_mode`、`loop_mode`、`extract_qc`、canonicalへの切替を変更しません。
`enforce` や公開判定に必要な評価・承認も従来どおりです。

## 利用先とAPI別の予算

`mcs setup api-keys` の「1」でキーを非表示入力し、「5」で利用先・優先順位・API別予算を設定できます。
新規導入・更新後のキー設定でもOpenAIを登録できます。キーは既存の認証情報と同じMCS専用 `.env` に保存します。
OpenAIの用途別モデル設定は背景抽出・意味解析に `gpt-6-luna`（推論 `medium`）、患者コンテキストに `gpt-6.1-sol`（`medium`）、正式な品質確認で必要になった有限の修復に `gpt-6.1-sol`（`high`）です。個別投稿の抽出と意味解析は既定ではローカルで処理し、終了日時を指定して再開した過去分だけクラウドへ送ります。添付OCRの新規クラウド送信は再開しません。過去のクラウド記録の読み取り・回復も維持します。
用途別の最大出力は順に8192・16384・32768トークンで、推論トークンも含みます。既存の明示モデルは保持し、用途別の指定があればその設定を優先します。Anthropicでも用途別profileは常に使われ、profileを設定していない用途は既定値（再抽出・意味解析がHaiku 5.5 medium、患者コンテキスト・品質修復がSonnet 5.5 high）になります。
OpenAIの用途別設定は提供元専用の私有設定に保持します。`mcs setup api-keys` の利用先設定画面で実効モデルを確認できます。 利用先と予算を保存した後、同じ画面でキーの設定を続けられます。別の操作で設定が変わった場合は、画面を開き直してください。

用途別のprofileはCLIでも変更できます。たとえば `cloud-llm providers --patient-context-profile sol-high` はOpenAIの患者コンテキスト用profileを変更します。OpenAIには `--backlog-profile`・`--patient-context-profile`・`--quality-repair-profile` を使い、`--openai-` から始まる同名の引数も使えます。Anthropicには `--anthropic-backlog-profile`・`--anthropic-patient-context-profile`・`--anthropic-quality-repair-profile` を使います。値は各提供元で定義されたprofile名に限ります。
指定しなかった用途・提供元・利用先の選択・予算・キーは保持します。分割形式の設定も既存の設定保存経路で更新するため、私有ファイルを直接編集する必要はありません。Anthropicの用途別profileは設定がなくても既定値で有効です。profileを設定した場合は指定した用途だけが置き換わり、省略した用途は既存の設定を保ち、設定がない用途だけ既定値を使います。
患者コンテキストのprofileを変えると、以前クラウドで作成した患者scanは現在の契約と一致しなくなります。対象患者のscanを新しいprofileでやり直すため、その処理に費用がかかります。既存の記録は削除せず、新しい処理にも日額・月額などの費用上限を適用します。

`cloud_llm.provider` は `anthropic`、`openai`、`auto` から選びます。省略時は `auto` です。
`auto` は `provider_order` の順に、キーが登録され、施設の確認（[外部AI送信の施設確認](COMPLIANCE.md)）で許可された提供元を選びます。既定の順はAnthropic、OpenAIです。確認の記録が無い既存環境は、キーのある最初の提供元を選びます。
どれも許可されていなければ自動使用せず、キーのある最初の提供元を表示します。確認の記録を変えると `auto` の提供元が変わることがあり、その場合は提供元を変更したときと同じく患者コンテキストの契約が変わります。確認の記録がある環境では、`mode` を明示した場合も同じ順で許可された提供元を選び、`provider` を明示した場合は、その提供元が許可されていなければ送信しません（`mode` は off として扱い、`mcs_setup.py check` などが `external_transfer_review_required` で理由を示します）。確認の記録が無い既存環境で `mode` を明示した場合は、従来どおりキーのある最初の提供元を使います。
`mcs setup` の保存前の確認も同じ選択を表示します。
選択したAPIの予算上限やエラーで停止した処理を、別APIへ自動で再送することはありません。
上限到達後に別APIを使う場合は、利用先を明示的に変更してください。過去の使用額と未精算の予約額は保持します。

次の例はAnthropic優先で、合計の日25ドル・月75ドルを、Anthropicの日20ドル・月60ドルとOpenAIの日5ドル・月15ドルに配分します。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm providers --provider auto --priority anthropic,openai --anthropic-daily-usd 20 --anthropic-monthly-usd 60 --openai-daily-usd 5 --openai-monthly-usd 15
python3 mcs/ops/mcs_setup.py cloud-llm providers
```

API別の上限と合計上限を同時に適用します。API別上限の合計が合計上限を超える設定は保存しません。
API別予算を設定していない既存環境は、従来の合計上限を使います。API別予算を設定した場合、予算を割り当てていないAPIには送信しません。
`providers` の出力にも、`budget` と同じ `last_limit_change`・`limits_match_record` を表示します（「件数・費用・対象を制限する」の「上限の変更記録」）。
OpenAIはResponses APIの標準サービスを使い、応答の保存を `store=false`、プロンプトキャッシュを30分に指定します。
これは保存契約やデータ保持条件を保証する設定ではありません。利用先の条件を確認してください。
OpenAIの料金はモデルごとの版を記録し、LunaとSolの使用額を同じOpenAI予算と合計上限に算入します。価格の確認日と再確認期限は各モデルの料金定義で管理します。出典は[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)と[Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)の公式資料です。
入力・キャッシュ読取り・キャッシュ書込み・出力を数え、料金や使用量を検証できない応答は最大予約額を保持して送信を止めます。
料金表の再確認期限を過ぎたモデルでは、新しいクラウド送信を止めます。患者コンテキストの作成・更新などの処理はローカルで継続します。公式料金を確認した更新版を適用するだけで送信を再開します。

## 背景処理の並列化と患者の優先順

`cloud_llm.max_concurrency` は1〜32です。全プロセスで共通の送信枠を使い、設定値を超えるクラウド処理を同時に送りません。これは同時に送る要求の上限で、背景ワーカーの本数そのものではありません。
常駐処理（レーン2）が背景ワーカーを起動します。患者コンテキスト専用のワーカーと、保存済み投稿の再抽出・意味解析の再開期間だけ動くワーカーは1つのメモリ枠を共有し、合計本数は空きメモリ（前景用の予約を除き、1本256MiBで換算）と `max_concurrency` の小さい方までです。患者コンテキスト専用のワーカーは、患者の選択が1つずつ進むため最大2本です。再開期間が開いている間は、`max_concurrency` から1を引いた本数までにして、再開期間のワーカーに少なくとも1本の枠を残します（`max_concurrency` が1のときは患者コンテキストを優先します）。患者コンテキストを優先し、その処理が有効な間は再起動待ちの間もその分を空けておき、再開期間のワーカーは残りの範囲で起動します。患者コンテキストを無効にすると、専用のワーカーは処理中の1単位を終えてから終了し、空いた枠は次の判断で再開期間のワーカーが使えます。再開期間のワーカーは、予算の上限・鍵・接続先の設定などで新たに起動できない状態になると、持ち越した支払済みの結果を精算（保存、または元の投稿が変わっていれば保留）してから次の確認（60秒おき）で終了し、枠を空けます。記録の理由は `cloud_blocked` です（`mode` が on でなくなった場合は従来どおり `cloud_mode_off`、同じ確認で枠も超えている場合は `capacity_reduced`）。終了するまでの間は、その分だけ患者コンテキスト専用の起動を控えます。あとから再開期間が開いた場合も、枠を超えた専用のワーカーは処理中の1単位を終えた後の確認（60秒おき）で終了します。逆に、患者コンテキストを無効にしている間に起動した再開期間のワーカーは、患者コンテキストを有効にすると、その分を超えた本数が次の確認（60秒おき）で終了します。空きメモリが減ったときも、前景用の予約を下回るほどでなければ、超えた分のワーカーは処理中の1単位を終えた後の確認（60秒おき）で終了するため、それまでの間は合計が新しい本数を上回ります。確認が済んだ後も、それぞれの組でメモリの測定の揺れに1本の余裕を持たせるため、合計が新しい本数を最大2本上回ることがあります。起動したワーカーのメモリが空きメモリの測定に反映されるよう、1回の判断（約10秒ごと）で起動するのは2つの組を合わせて最大2本です。メモリの余裕を確認できない場合は追加起動せず、起動済みの背景ワーカーも終了してメモリを解放します。
更新・通常の常駐停止では、その常駐処理が起動した子だけを終了します。

履歴処理ではアクティブ患者を優先し、患者ごとの最新投稿が新しい順に処理します。新着の収集直後に動く処理は従来どおりローカルです。
履歴の対象は、正式な再開操作の記録に基づいて判定します。旧版の固定対象はそのまま保持し、継続的に履歴を処理する対象へ自動で移行しません。
患者コンテキストはその患者の保存済み投稿・添付OCRについて現行ローカルLLMの個別解析と必要な品質確認を終え、取得・根拠・公開の条件を満たしてから生成します。チャット原文・連携サマリーの原文・添付OCR全文と、現行の根拠に結び付いた補助要約を集約して入力します。個別投稿のクラウド抽出完了は前提にしません。取得漏れ・削除・空本文・保留・失敗は、完了として数えません。

## 外部サービスの保持条件を確認する

APIキーの登録だけでは、Zero Data Retention（ZDR）やHIPAAに関する契約の成立は確認できません。
AnthropicのZDRは対象組織での有効化が必要です。HIPAA向けの利用にはBAAと対応組織の条件があります。
送る情報と利用機能に適用される契約・保持条件を、[Anthropic公式資料](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention)で確認してください。
Jevも利用者の契約を別途確認してください。本機能が契約の成立や法令適合を判定することはありません。

## 件数・費用・対象を制限する

Jevは日本時間の1日10000要求が上限です。再試行、モデル一覧の取得、実通信する評価CLIも同じ上限へ数えます。
`semantic.daily_request_budget` に10000未満を設定すれば、その値を使用します。`0` は送信停止です。
modeを明示した既存設定で予算を省略した場合は、従来どおり `0` です。
10000を超える設定でも実効上限は10000です。評価CLIが通常のmodeを迂回する場合も、この件数上限を迂回しません。
背景の意味解析では、日上限の10%をリアルタイム処理のために残します。留保する件数は端数を切り上げます。日上限10000の場合、背景からのJev要求は9000件までで、残り1000件をリアルタイム処理に使います。Jevの枠を使い切っても、Anthropic・OpenAIによる処理は続けます。意味解析を有効にしている環境では、Jevが未設定、日次予算が0、または利用できない場合も、Jevの検証を省略して処理を続けます。
`python3 mcs/ops/mcs_setup.py doctor --probe data --json` で、Jevの使用数と背景枠の状態を確認できます。

Jevを省略しても、原文との対応、数量・薬剤などのコードによる検証、処理世代、公開範囲の確認は続けます。既に見つかった不一致を省略扱いで消しません。設定不正、利用期限切れ、送信結果・料金の確認待ち、人の承認待ちを、Jevの省略で解除することもありません。

AnthropicとOpenAIの合計に対して、1日の件数 `cloud_llm.daily_request_budget`、1日の費用 `daily_cost_limit_usd`、1か月の費用 `monthly_cost_limit_usd`（費用はドル）を設定できます。
費用の設定を省略した場合は、1日25ドル・1か月75ドルが上限です。1日の件数は省略した場合に上限を設けません。費用上限は予約時の最大額で判定するため、実際の費用が上限より低くても先に止まることがあります。
明示した `0`、低い上限、`mode=off`、対象範囲は更新後も保ちます。個別の費用上限を解除する場合は、後述のCLIで `none` を指定します。対応する設定値を `null` として保存し、更新後も解除を保ちます。
`cloud_llm.mode` を指定せず、日・月の上限を両方とも明示的に解除した場合は、期間予算が必要です。期間予算も無いあいだは送信せず、`check` と `cloud-llm plan` に `cost_limit_required` と表示します。

初回導入でも更新でも、省略した費用設定はコードの既定値に従います。以前のCLIで上限を解除し、その項目が削除されていた場合も25ドル・75ドルの既定値が適用されます。解除を続ける場合は、更新後に該当する上限へ `none` を指定してください。設定ファイルへ既定値を自動で書き込む移行はありません。

送信する期間と、その期間全体の予算（ドル）を指定できます。期間予算は日をまたいでも合計で数え、日本時間の0時に戻りません。日・月・期間の費用上限を同時に適用します。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm budget --period-usd 80 --until 2026-10-30            # 今から10月30日の終わりまで、合計80ドル
python3 mcs/ops/mcs_setup.py cloud-llm budget --period-usd 80 --from 2026-11-01 --until 2026-11-07
python3 mcs/ops/mcs_setup.py cloud-llm budget --period-usd none --until none                 # 期間と期間予算を解除
```

- `--until` はAnthropic・OpenAIの `cloud_llm.until` を設定します。Jevの `semantic.until` は変更しません。日付だけを指定すると、その日の23:59:59（日本時間）までです。
- 期間が無いときに `--from` を省略すると、期間は設定した時点から始まります。すでにある期間の金額を変える場合は開始時刻を保ち、使用済みの額も引き続き数えます。開始時刻だけを変える場合は `--from` だけを指定します。Anthropic・OpenAIは開始前と終了後に新しい送信（再試行を含む）を始めません。期間外の新しいクラウド処理は保留し、受付条件と品質条件を満たすローカル処理は継続します。送信中の要求は最後まで処理し、その結果は対象範囲や原文などの保存条件を満たす場合に保存します。予算や利用期間だけの変更では取得済みの結果を破棄しません。
- Jevは終了時刻を過ぎると、新しい要求（再試行と手動の評価ツールを含む）を予約しません。予約した直後、送信の前に終了時刻を過ぎた要求も送信しません。患者情報の照合では、その予約を未送信として記録し、期間を延ばすと同じ質問をもう一度問い合わせます。新着投稿の保存、既存の通知、送信中の結果の保存はそのまま続きます。Jevの開始時刻と期間予算はありません。Jevの量は1日の要求件数で制限します。
- 時刻は日付（`2026-10-30`）か、時差付きのISO 8601形式（`2026-10-30T18:00:00+09:00`）で指定します。設定項目は `cloud_llm.window_start`・`window_budget_usd`・`until` と、独立した `semantic.until` です。提供元別設定を使う環境では、認証された設定変更経路を使用してください。
- 期間予算は、予約時の最大額で判定します。結果が戻ると実際の額で数え直すため、表示額は進行中の予約の分だけ多く見えることがあります。

保存済み投稿の再抽出（過去の投稿を現行の抽出世代へ上書きする処理）は、既定ではローカルで処理します。費用上限と終了日時を指定した場合に限り、その終了日時までクラウドへ送れます。費用上限には、従来の期間予算か、全体と対象提供元の双方の日額・月額上限を使います。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm budget --period-usd 60 --reextract-backlog-until 2026-11-20   # 11月20日の終わりまで再開
python3 mcs/ops/mcs_setup.py cloud-llm budget --reextract-backlog-until none                         # 再開を終了
```

- 設定項目は `cloud_llm.reextract_backlog_until` です。期間予算（`window_budget_usd`）なしで再開する場合は、全体の `daily_cost_limit_usd`・`monthly_cost_limit_usd` と、`provider_budgets` 内の対象提供元の日額・月額上限が必要です。提供元が `auto` の場合は、`provider_order` 内のすべての提供元に両方の上限が必要です。不完全な設定は保存せず、直接書いた場合も設定エラーとして送信を止めます。
- 既存の期間予算は自動では解除しません。必要な日額・月額上限を設定したあと、`--period-usd none` で明示的に解除できます。開始時刻と金額の片方だけが残る設定は拒否します。全体と提供元別の上限は、それぞれ独立して適用します。
- 再開中は、患者名を含む投稿本文を外部APIへ送ります。対象は `cloud-llm resume --confirm-human` で記録した履歴の範囲と、`project_ids`・`exclude_project_ids` の範囲に含まれる投稿です。
- 期間予算は、患者コンテキストを含む期間内の利用額の合計に適用します。上限に達すると、患者コンテキストのクラウド送信も止まります。
- 抽出結果の監査（`semantic.extract_qc="annotate"`）で裏付け不足または緊急度の相違を指摘された投稿は、まずローカルで指摘を添えて1回だけ再抽出します。その再抽出結果を監査し直しても指摘が残り、投稿日時が直近60日以内で、同じ投稿の現在の本文をまだクラウドで再抽出していない場合に限り、再開中のクラウドworkerがもう1回だけ再抽出します。この上限は API の要求1回ではなく、投稿の本文1つにつき再抽出1回です。長い本文を分けた要求や応答を直す要求も同じ1回に含まれ、どれも本文を送ります。費用上限や停止で途中まで送った1回は、次の機会に同じ回として、最初の要求を予約したときの送信先・モデル（応答を直す要求のモデルを含む）で残りだけを送り、送信済みや結果の分からない要求は送り直しません（その送信先が上限の間は、優先順位を変えて別の送信先が使えるようにしても待ちます）。設定・記録した施設の確認・鍵がその送信先・モデルを提供しなくなった場合は、別のモデルで最初から送り直さず、その回を終えて確認候補にします（クラウドを止めていても、ローカルの抽出の処理が終えます）。設定・施設の確認記録・鍵を読めない間、確認待ちの間、`cloud-llm stop` などの一時的な停止の間は終えずに待ち、何も送りません。最初の要求を予約する前に費用上限などで止まった場合は1回と数えず、後で設定を変えたモデルでも送ります。通常の再抽出としてクラウドへ送ったことがある本文や、送ったクラウドの結果が失敗・保留になった本文は、投稿者名などが更新されても、もう送りません（本文が変わった場合は新しい本文として扱い、元の本文に戻した場合は以前その本文で送った分も数えます）。この記録は送信の会計記録（約2か月で整理）とは別に残ります。このとき投稿本文に加えて、監査が指摘した項目名と緊急度の指摘をクラウドへ送ります。送信条件は上記の再開期間・費用上限・`cloud-llm stop`・施設の確認・`project_ids` の範囲・履歴の範囲と同じで、旧抽出の保留が有効な投稿は送りません。送信後に失敗した場合はローカルでやり直さず、元の抽出とその監査結果をそのまま残します。クラウドの再抽出後も指摘が残る投稿と、すでにクラウドで再抽出した投稿は `mcs view qc` の `needs_confirmation`（確認候補）に表示し（`--needs-confirmation` で絞り込み）、それ以上自動では再抽出しません。クラウドの再抽出をまだ行っていない投稿は `followup_state` に `cloud_reextract_pending`（クラウド再抽出待ち）と表示します。この確認候補の表示がずっと続くのは、送信の記録（`extract_cloud_attempt_v1`）を残した送信だけです。記録を残す前の版で送った投稿は約2か月で整理される送信予約で判定するため、整理の後は再び `cloud_reextract_pending` と表示されることがあります。その場合も対象は直近60日の投稿だけなので、再度送ることはありません。途中まで送った回の間に監査の指摘内容が変わった場合は、保存済みの応答を確かめられないため、何も送らずにその回を終えて確認候補にします。指摘によるローカルの再抽出を済ませた投稿は、再開期間中でも通常の再抽出としては送りません（同じ投稿を何度も有料で送らないため）。人の ⚠ 誤り報告による再抽出と、抽出世代の更新による再抽出は従来どおりです。
- 添付ページの解析は、再開中もクラウドへ送りません。旧抽出を保持する保留が有効な投稿も送りません。意味解析の未処理分（`semantic_backlog`）には、同じ費用条件で独立した `--semantic-backlog-until` を指定します。再抽出の終了日時だけでは意味解析を再開しません。意味解析の対象範囲と既存の同意・停止条件も維持します。
- 意味解析の再開は `--semantic-backlog-until none` で終了します。この操作では設定項目を削除せず、明示的な `null` を保存します。新しい送信を止め、保存済み回答の解釈に使う契約を保つためです。項目の初回追加と削除は契約の変更として処理中にも検知し、承認の再照合が必要になる場合があります。
- 新しい送信を行うのは、再開中だけ起動する再抽出用のクラウドworkerです。定期収集と常駐処理の通常の抽出はローカルのままです。
- 終了日時を過ぎると新しい送信を始めません。送信中の要求は最後まで処理し、保存条件を満たす結果を保存します。
- 期間予算の期間は、開始から61日までです。使用額の記録は62日で削除されるため、開始から61日を過ぎると使用額を確かめられないとして送信を止め、`check` に `window_history_unverified` と表示します。
- `cloud-llm plan`・`estimate` の `period_budget` に、期間の開始・予算・その時点の使用額（予約中の最大額を含む）を表示します。
- `budget`・`plan`・`estimate` の `reextract_backlog_blockers`・`semantic_backlog_blockers` には、再開を妨げる設定上の理由を表示します。APIキーや現在の会計状態を含む送信可否の確認は `check` を使います。

費用の上限は、次のコマンドで表示・設定できます。CodexやClaude Codeからもそのまま実行でき、共通の費用設定は認証された設定変更経路で保存されます。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm budget                                   # 現在の上限を表示
python3 mcs/ops/mcs_setup.py cloud-llm budget --daily-usd 2 --monthly-usd 40     # 上限を設定
python3 mcs/ops/mcs_setup.py cloud-llm budget --daily-usd none                    # 1日の上限を解除
python3 mcs/ops/mcs_setup.py cloud-llm budget --history 10                       # 上限の変更記録を新しい順に10件
```

設定ファイルを読み取れない場合、既知の設定項目に誤りがある場合、ほかのCLIによる設定保存と競合した場合は保存しません。競合したときは設定を再確認してから再試行してください。既存の別経路や外部ツールでは同じロックを使わないため、設定の同時編集を避けてください。`max_concurrency` の既定値4は全プロセス共通の上限です。
`usd_jpy` は円換算の試算に使う任意の固定レートで、自動更新しません。

**上限の変更記録**: 提供元別設定（`data/provider_settings/`）を使う環境では、設定を保存するたびに、その保存の作業フォルダ（`data/.provider-settings-stage-<操作ID>/change.json`、所有者だけが読める）へ変更記録を1件残します。記録は、保存した入口（`cloud_llm_budget`・`cloud_llm_providers`・`provider_dialog`・`settings`・`remote_access`・`jev_model`・`setup_init`・`setup_slack_channels`・`setup_fact_source`・`setup_features`・`update_migration`・`install_bootstrap`・`install_runtime`。経路を特定できない保存は `unattributed`）、保存日時（UTC、表示用）、保存前後の4ファイルのハッシュと設定の状態（提供元ファイルのハッシュと共通設定の要約値）、運用上限の保存前後の値と変わった項目です。Jevモデルの切り替えは承認記録の `command_id` も残します。上限を変えない保存でも記録します。

- 対象の上限は、`cloud_llm` の運用上限（日額・月額・期間予算と開始・終了日時・件数・同時送信数・再開期限など）、API別の日額・月額、`semantic.daily_request_budget`・`semantic.until` です。値は数値、`null`（上限なし）、日時、`absent`（未設定のため既定値を使う）、`invalid`（数値・日時として読めない値。値そのものは残しません）のどれかで、`absent` と `null` を区別します。
- 記録には設定の文字列・認証情報・`.env` の内容・患者情報を含めません。台帳DBには書きません。記録の内容は書き込みの前に作り、書き込みでの入出力の失敗は保存前の状態へ戻します。同名の記録がすでにある場合、読み戻しが一致しない場合、直後の確認で設定が変わっていた場合は、保存中の記録を残して担当者の確認を待ちます。
- 照合はロックを取らずに読みます。保存の途中では新しい設定と記録がそろわないため照合しません。
- `budget` と `providers` は、新しい保存200件分の作業フォルダだけを開きます。現在の設定を作った保存は、日時ではなく、記録の保存後の状態が現在の設定の状態と一致するもので判定し、そこから保存前後の状態をハッシュでたどります。
- 出力の `last_limit_change` は、たどった記録のうち上限が変わった最新のもの（`state: "changed"`、入口・日時・変わった項目の前後）を示します。記録が1件も無い場合は `no_record`（この機能より前の保存には記録がありません）、たどれる範囲で上限が変わっていない場合は `unchanged`、200件の範囲に変更が見つからない場合は `not_in_recent`、従来形式の設定は `legacy`、記録を読み取れない場合は `unavailable` です。
- `limits_match_record` は、現在の設定がいずれかの記録の保存後の状態と一致するかを示します（記録が無い場合と、保存中で照合しない場合は `null`）。`false` は、現在の設定が記録と一致しないことだけを示し、記録の無い変更があったとは断定しません。原因には、記録を残さない保存（中断した保存の確定など）、この機能より前の保存、読み取る範囲より前の記録などが考えられます。`limits_record_note` に説明を、最新の記録と値が異なる項目を `limits_differing_from_record` に表示します。
- `budget --history N`（1〜100）は、新しい順にN件の記録を `limit_history` に表示します。`previous_record_found: false` は、その保存の前の状態を作った記録が読み取る範囲に見つからないことを示します（最初に記録された保存、記録を残さない保存の後の保存などで起こります）。記録の無い作業フォルダの数は `unrecorded_saves`、読み取らなかった不正な記録（リンク・大きすぎる・形式違い）の数は `rejected_records` です。
- 記録はこの版以降の保存から始まります。従来形式（`config.json` だけ）の環境には記録を残しません。上限の変更に新たな承認は求めません。

論理的な設定構造の例です。提供元別設定を使う環境では、この断片をファイルへ直接書かず、設定画面またはCLIを使ってください。

```json
{
  "semantic": {"mode": "off"},
  "cloud_llm": {
    "mode": "off",
    "project_ids": [],
    "routes": ["patient_context", "reextract"],
    "daily_request_budget": 0,
    "monthly_cost_limit_usd": 0
  }
}
```

手動で有効なmodeを指定する場合は、対象も明示してください。`project_ids` は患者のプロジェクトID一覧、
`null` は全対象、`[]` は対象なしです。クラウド処理の `exclude_project_ids` は指定した患者を除外します。
`routes` では `patient_context`、`reextract`、`semantic_backlog` を選べます。省略時はすべてを対象にします。クラウドへの新規送信は、既定では `patient_context` の患者コンテキスト作成・更新と、その品質修復に限ります。`reextract`・`semantic_backlog` は、routeの選択に加えて上記の個別の再開期間を設定した場合だけ、新規送信を行います。これらのroute指定は過去のクラウド結果・送信結果不明の要求・会計記録を読み取り、回復できるか確認する対象範囲でもあります。モデルは利用先と用途に応じて選びます。OpenAIの既定は上記の用途別モデルです。

リアルタイム枠の投稿抽出と意味解析はローカルで処理します。取り込み・通知・編集を観測してから10分未満の処理対象は、即時処理用にローカルへ残します。背景枠に回った過去分の個別抽出と意味解析も、再開期間を設定しない間はローカルで継続します。クラウドでは患者コンテキストを作成・更新し、許可した再開期間中だけ過去分の再抽出と意味解析も処理します。品質修復、人承認、再試行、保留の既存条件は維持します。

同じスレッドに新着の返信があっても、過去分の処理と患者コンテキスト生成では、許可された保存済み文脈を使えます。送信前と保存前に、その時点の原文・返信・編集の識別値、設定、ジョブの所有権を照合します。処理中に内容が変わった場合は、古い結果を現在のものとして保存しません。新着を直ちに処理する枠はローカルのままです。

継続して履歴を対象にクラウドで患者コンテキストを処理するには、更新後に `cloud-llm resume --confirm-human --reason '過去チャットをクラウドで処理'` を実行してください。再開の本人確認記録と結び付けて、保存済みの投稿や、その後に保存・変更された内容を背景処理の対象にする記録を作ります。旧版で固定した対象は、この操作を行うまで従来の原文照合を維持します。対象の記録へ本文や認証情報は含めません。

処理途中の結果は、実際に処理したサービスと原文に結び付けます。別の処理先でやり直す場合は開始位置から生成し、前の途中結果を保持して、異なる処理先の結果を混ぜません。ローカルで途中まで進めた単位は、その処理先で完了させる場合があります。

クラウドが使えないときも、ローカルの受付条件、原文との対応、品質確認、公開条件は維持します。既知の不合格を切替で消さず、確認できるまで保留します。送信状況や料金が不明な同一要求は、別APIへの変更やジョブの作り直しだけで再送しません。未精算の予約額を保持し、安全に継続できる単位だけをローカルで処理します。Jevが利用可能な間は照合し、省略した場合は `SKIPPED` と理由を記録して、検証済みの結果と区別します。

更新後は、クラウドの回答本文を既存のローカルDBへ会計記録と同時に保存します。その後に抽出結果や患者コンテキストの保存で中断しても、入力・取得世代・モデル・要求内容・現在の処理担当が一致すれば、回答を再利用して通常の検証を続けます。再利用には新たな送信や費用予約はありません。回答の保存前に中断した場合や、証跡が欠けた場合は結果不明のまま保留し、同じ処理をローカルへ切り替えません（患者コンテキストは次の段落の扱いになります）。旧版の会計記録に回答本文がなければ復元できません。

患者コンテキストでは、クラウドが処理できなかった理由によって扱いを分けます。

- 一時的な理由（同時送信数の上限、その日の件数・費用の上限、失敗が続いた後の送信の一時停止、キーのファイルを一時的に読めない場合）では、ローカルへ回さずにクラウドの再開を待ちます。まだクラウドへ送っていない資料も待ちます。キーのファイルを読めないために待つのは、設定がその患者にクラウドを指定している場合だけです。クラウドの設定が無い導入先は待たずにローカルで処理します。以前にクラウドへ送った入力だけは、下の「どちらにも分類しない理由」と同じ扱いになります。すぐローカルで進めたい場合は `cloud-llm stop` か `mode=off` を使います。待っている間に同じ患者へ別の連絡が届いても、本文が変わっていない資料の支払い済みの回答は、クラウドの再開後に再送なしで使います。
- 確定的な理由（期間の終了、月の上限、期間予算、`cloud-llm stop`、`mode=off`、対象外の患者、施設が承認していない送信先）と、送信後の失敗（5xx・529、通信の失敗、時間切れ、応答の上限超過など。429 は、その単位の今の入力にクラウドの結果がすでにある場合だけ待機）では、その単位をローカルで処理します。
- ローカルで処理するとき、同じ入力の支払い済みの要求は再送せず、ローカルで置き換えたことを会計記録（`superseded_local`）に残します。予約額・確定額の集計は変えません。結果がまだ届いていない要求は、送信の待ち時間に約15分を足した時刻を過ぎてから置き換えます。後から届いた回答は会計にだけ記録し、採用しません。
- キーの欠落や設定の誤りなど、上のどちらにも分類しない理由では、従来どおり、支払い済みの要求が残る単位を保留します。`mode=off` を明示すると、その単位をローカルで作り直します。クラウドの利用をやめるときに `cloud_llm` の設定を削除しただけでは明示の off にならず、以前クラウドで処理した資料は保留のまま残ります。ローカルで作り直すには、設定を消さずに `mode` を `off` にしてください。
- ローカルで作り直す患者のコンテキストは、概況を作り直すまで表示されません。

理由ごとの扱いの一覧は [患者コンテキストの仕様](../specs/patient-context.md)の「クラウドの停止理由と、待機・ローカルへの切替」にあります。

新しいクラウド送信にも、1日25ドル・1か月75ドルの既定上限とAPI別上限を適用します。過去の使用額と進行中の予約額も数えます。

| 外部AIのmode | 動作 |
|---|---|
| `off` | 外部AIへ送信しない |
| `dry_run` | 送信せず、ローカル処理の保存に成功した単位の試算を記録する |
| `shadow` | 選択した外部AIへ送信して比較する。ローカルの結果を正本にする |
| `on` | 検証を通った外部AIの結果を使用する |

外部処理が使えない場合も、ローカル処理の受付条件や期限は維持します。
未処理の対象を完了扱いにはしません。

## 送信せずに試算・照会する

導入先で次のコマンドを実行できます。保存済み記録を読み取り、APIへは送信しません。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm plan
python3 mcs/ops/mcs_setup.py cloud-llm estimate --days 14
python3 mcs/ops/mcs_setup.py cloud-llm log --days 14
python3 mcs/ops/mcs_setup.py cloud-llm compare --days 14
python3 mcs/ops/mcs_setup.py cloud-llm outstanding
```

`outstanding` は保存されている会計履歴全体から、結果記録がない要求と、結果を精算できない要求の件数・最古の経過時間・10分以上の件数を集計します。本文や患者識別子は表示しません。読取り上限に達した場合は `unknown`、不正・重複・対応しない記録がある場合は `partial` とし、未確定の件数を0とは表示しません。この照会で予約額の解除や再送はしません。患者コンテキストの消去で記録を消し、件数だけを引き継いだ未精算の送信は、保存されている記録とは別に `carried_unresolved_requests` として表示します（再送はしません）。
会計履歴が増えて既定の読取り上限（5秒・10万件）では `unknown` になるときは、`cloud-llm outstanding --full` で上限を広げて全件を確認します。最長で5分かかります。検証の内容は同じで、読取り専用のため収集や解析は止まりません。

`--since YYYY-MM-DD` は日本時間の日付で絞ります。`log` だけは `--project` でも絞れます。
文字数はトークン数ではありません。dry-runは保存に成功した処理単位の観測から試算します。
失敗・未完了・未着手の処理は含めないため、全対象を処理する総費用の見積りではありません。
履歴が不足する場合、費用の試算には未確定の項目が残ります。
現在の患者文脈の対象は、原文だけでなく、抽出結果・診療情報・生成契約の変更も含めて判定します。
過去の日別傾向は保存済み投稿の時刻からの近似で、未取得の履歴を含む全件数ではありません。
見積りでは、現在の対象条件で数えた未処理分、日々の継続分、分割・修復・再試行による追加分、シャドー運用の追加分を分けます。取り込み・通知・編集を観測してから10分未満の処理対象は、現在の候補から除きます。その後に候補となる全件を処理する費用の総額ではありません。
文字数に基づく分割数は既に基本の要求数へ含め、二重に加算しません。修復・再試行の量が未測定なら数値を出しません。
実際のusageがあれば、記録の要求数・文字数・トークン数を母数として入力と出力を補正します。
出力の実績がない場合は、出力上限を費用の参考幅に使います。この幅は実際の請求額を保証するものではありません。
`compare` は保存済みのローカル結果との一致を集計するもので、独立した正解との精度評価ではありません。
比較では主体・状態・否定・原文の位置を区別し、割合には分子と分母を添えます。旧記録に分母がなければ未計測として扱います。

AnthropicはHTTPの試行前に件数と費用を予約します。
予約後に送信しなかった試行（期限切れ、送信直前の再確認で止めた対象範囲・停止状態・設定変更）は0円で精算します。
HTTPの応答があった試行は、エラーでも予約額のまま計上します。応答からusageを検証できた場合だけ、成功時と同じく実際のusageで計上します。
公式のエラー一覧には、どの状態が課金されないかの記載がないためです。
過去分の再抽出の要求では、固定の指示の先頭部分をキャッシュ対象の接頭辞（`cache_control: ephemeral`、5分）として送り、その後に続く要求ごとの本文はキャッシュしません。患者コンテキストと意味解析の要求はキャッシュの接頭辞を指定しません。
利用記録の費用は、API応答の実際のusage（キャッシュ作成・読取りの内訳を含む）で計算します。
送信前の予約は、要求本文のバイト数に余裕分を加えた入力を、長文入力の単価にキャッシュ書込みの最大の割増（2倍）を掛けて見積もるもので、1Mトークンの上限額ではありません。
`cloud-llm plan`・`estimate` の試算はプロンプトキャッシュの割引を考慮しない上限側の値です。
このため表示額は実際の請求額と一致するとは限りません。月額上限に近い場合は保守的な予約によって送信が先に止まります。
予約時は月単位の集計を保持し、新たに追加された利用記録を読み取って更新します。月額上限を設定していない場合も同じ方式です。集計済みの記録の変化を検知した場合は、集計を作り直します。
料金表は2026-11-24に公式料金で再確認し、次の確認期限は2026-12-24です（`claude-haiku-5-5`・`claude-sonnet-5-5`・`gpt-6-luna`・`gpt-6.1-sol`。いずれも以前の版から料金に変更はありません）。期限までに公式料金を再確認し、検証済みの料金表へ更新する必要があります。期限切れ・未知の料金条件では送信を止めます。期限の7日前から、キーを登録して利用中の提供元について `mcs_setup.py doctor` が再確認期限を予告します（用途ごとの設定で使うモデルのうち、最も早く期限を迎えるもの）。
AnthropicとOpenAIの利用記録は62日、Jevの利用記録は7日保持します。修復・添付OCR・現行の患者コンテキストが参照している利用記録は、参照が残る間は62日を超えても残します。
`cloud-llm plan`・`estimate` の `source_repair_evidence_holds` には、原典修復の保留に関わる記録の件数が出ます。IDは出しません。
`unattributable_accounting_rows` が1以上なら、利用記録の構造が壊れているため、すべての患者で原典修復の結果を採用しません。
`old_reserved_repair_slots` は、600秒を過ぎても送信予約のままの修復の件数です（内容が長すぎて検査できないものは含みません）。実行中のものを含むことがあり、送信が途中で止まったとは限りません。止まった修復は再送せず、その原典の本文や対象範囲が変わるまで結果不明のまま残ります。
各項目は特定の形の不正だけを数えるため、0件でも修復が保留されていないとは限りません。件数を確かめられなかった項目は `null` に、読取りの期限や容量に達した場合は全体が `unknown` になります。どちらも0件とは限りません。
応答後に対象範囲や原文が変わって採用できなかった結果も、固定の理由を別の記録に残します。
結果の破棄はAPI要求の取消しではないため、要求件数や利用料金を減らしません。

## Jevのモデルを切り替える

Jevのモデルは自動では切り替わりません。Jevを使っている環境（`semantic.mode` が off 以外で、キーがあり、日次予算が1以上で、施設の確認がJevを含む場合）では、
`python3 mcs/ops/mcs_setup.py check` が1日1回までJevのモデル一覧を取得し、使用中より新しい固定版があれば次のように表示します。
一覧の取得は1要求として日次上限に数えます。利用枠を予約した後、送信の直前にもう一度この条件（施設の確認を含む）を確かめ、外れていれば送信しません。
取得できなかった場合も翌日まで再取得しません（ほかの処理が保存中で待っても予約できなかった場合だけ、次の確認で再取得します）。
Jevのモデル一覧が固定版のIDを返すことは提供元の仕様として確認できていません（一覧は別名の一覧として案内されています）。
一覧に固定版のIDがない場合や取得に失敗した場合は「最新」とはみなさず、「新しいモデルの有無を確認できませんでした」と表示します。

```text
  情報: Jev: 新しいモデル jev-X.Y.Z を利用できます（使用中: jev-1.14.0）。自動では切り替えません。…
```

使用中のモデル・コードの既定・前回の一覧で見つかった新しい版は、`python3 mcs/ops/mcs_setup.py jev-model` で表示します（通信しません）。
切り替えるときは、人が確認したうえで理由を付けて実行します。

```bash
python3 mcs/ops/mcs_setup.py jev-model --to jev-X.Y.Z --confirm-human --reason '新しい版を確認した'
```

- 指定した版へ、完全合成のデータだけで検出の確認（`semantic_bench detect` と同じ9件）を送ります。送信は日次上限に数え、患者情報は送りません。
- すべての確認が期待どおりだった場合だけ `semantic.model` を保存し、承認記録（`ops.jev_model_set`、変更前後の版と確認結果）を残します。
  判定が期待と違った場合（終了コード1）や、Jevが回答せず評価できなかった場合（終了コード2）は何も変更しません。
- 切り替えると、次の定期処理から新しいモデルを使い、完了済みの意味解析は新しいモデルで順にやり直されます。その分の要求が日次上限の範囲で増えます。
- 元に戻すときは `--to default`（コードの既定）か、表示された以前の版を指定します。既定へ戻すときは確認を送らず、`semantic.model` を削除します。
- `latest` などの別名と、以前のリリースが固定していた版（`jev-1.13.0`）は指定できません。
- 承認記録を先に保存し、その後で設定を保存します。設定の保存を確認できなかった場合は承認記録のUUIDを表示するので、
  同じ `--to` に `--command-id <UUID>` を付けて再実行します。確認を送り直さずに、まだ反映されていない設定だけを保存します。
  その後に別の切替があった場合は、後の変更を上書きしません。
- 提供元別設定（`provider_settings`）の保存中断で保留記録が残っていると、設定の読み込みは承認記録の検索より先に止まります。
  全ファイルが保存済みなら、先に `provider-pending-finalize` で保留記録を確定してください（INSTALLATION.md）。
- 解析結果の採用方法が `canonical`（検証済み結果）の間は切り替えません。canonical の承認は使用中のモデルを含む候補の識別子に結び付いているためです。
  先に `mcs_setup.py fact-source shadow` に戻し、モデルを切り替えてから新しいモデルで評価をやり直し、合格した評価証拠で canonical を承認し直します。
- Jevの配線確認（`semantic_jev.py --smoke --live`）・`semantic_bench`・`mcs_setup.py jev-value` も、使用中のモデルへ送ります（切替前の確認だけは切替先の版へ送ります）。

## 停止・再開する

AnthropicとOpenAIの処理を停止するときは、理由を付けて次の操作を行います。

```bash
python3 mcs/ops/mcs_setup.py cloud-llm stop --confirm-human --reason '外部処理を一時停止'
python3 mcs/ops/mcs_setup.py cloud-llm resume --confirm-human --reason '設定と利用状況を確認して再開'
```

返された `command_id` を控え、同じ操作を再試行するときは `--command-id` で指定します。
書込みロックは最大180秒待ちます（待つ間はその旨を表示します）。取得できなければ終了コード3となり、停止・再開は未適用です。
この場合は同じコマンドIDで再試行してください。開始済みの外部通信を即時に取り消す操作ではありません。
停止中は、患者コンテキストの要約の品質確認（Jev への送信）も保留します。
認証・支払い・料金確認の問題による停止も、原因を解消してから明示的に再開します。
設定ファイルを読み取れない場合でも `stop` は記録できます。`resume` は設定を読み直せるまで拒否されます。

### 患者コンテキストを消去して作り直す

患者コンテキストの結果と、その外部AIの会計記録を消去して、一から作り直せます。すでに使った額は引き継がれ、上限の判定と使用額の表示は消去の前と同じ額を数え続けます。

```bash
# 1. 設定で extract.patient_context.enabled を false にし、送信を止め、作り直しの見積りを取る
python3 mcs/ops/mcs_setup.py cloud-llm stop --confirm-human --reason '患者コンテキストの作り直し'
python3 mcs/ops/mcs_setup.py cloud-llm estimate --days 14
# 2. 消去の内容と前提を確認する（変更しない）
python3 mcs/ops/mcs_setup.py cloud-llm context-reset-plan
# 3. 表示された preview_hash を渡して消去する（バックアップを取ってから消去）
python3 mcs/ops/mcs_setup.py cloud-llm context-reset --preview-hash <preview_hash> --confirm-human --reason '患者コンテキストを作り直す'
# 4. enabled を戻して再開する
python3 mcs/ops/mcs_setup.py cloud-llm resume --confirm-human --reason '患者コンテキストを作り直す'
```

`context-reset-plan` の `refusal` が `null` でない間は消去できません（`read_incomplete` は確認の読取りが上限に達したことを示します。`stop_reason` が `read_deadline` のときは、ほかの処理が少ない時間に再実行します。それ以外の理由は再実行しても通らないので、開発者に連絡してください）。
バックアップは手順3の実行時に取り、1時間以内のものだけを使います。拒否されたときのバックアップは削除されます。消去の後は公開中の患者コンテキストがすぐ表示されなくなり、通常の処理で作り直されます。
結果が分からないまま残っていた送信（`unsettled_reservations`）と同じ内容を、作り直しで改めて送ることがあります。
`context-reset-plan` の `generation_records` は、消去で消える生成枠の記録のうち読めないもの（`unreadable`）と未来の時刻のもの（`future`）の件数です。これらは消去を止めません。`future` の件数は時刻とともに変わるため、確認から実行までの間に `preview_changed` になることがあります。そのときは `context-reset-plan` からやり直します。消去の後は、全患者の概況作成の1日の回数が0から数え直されます（その日に4回使った患者もすぐ作り直せます。使った額は引き継ぎます）。詳しい消去範囲は [患者背景情報の契約](../specs/patient-context.md) を参照してください。

拒否されたときの理由と対処は次のとおりです。

| 理由 | 対処 |
|---|---|
| `patient_context_enabled` | 設定で `extract.patient_context.enabled` を `false` にする |
| `cloud_not_paused` | `cloud-llm stop` で外部AIの送信を止める |
| `quality_claim_active`・`generation_active`・`cloud_in_flight`・`jev_in_flight` | 実行中の処理が終わるまで（10分程度）待って再実行する。`generation_active` は、今も有効な概況作成の担当があるときだけ出ます。読めない生成枠の記録や未来の時刻の記録では出ず、それらは消去で消えます |
| `accounting_unverified`・`accounting_inconsistent` | 会計記録を確認できないため消去しない。`cloud-llm check` の内容を開発者に連絡する |
| `preview_changed`・`spend_changed` | 確認の後に記録が変わった。`context-reset-plan` からやり直す |
| `backup_missing`・`backup_disk_low` | バックアップを取れない、または確かめられない。空き容量を確保して手順3から再実行する |
| `config_unreadable` | 設定ファイルを読めない。`setup check` で確認する |
| `command_id_conflict` | 別の操作の `--command-id` を指定している。指定を外すか新しい値にする |

消去前のバックアップ（`data/backups/patient-context-reset-*.db`）へ戻すときは、通常のバックアップと同じ手順（[ローカル backup の復元](BACKUP.md#local)の `mcs_local_backup.py restore`）で復元します。復元すると外部AIの送信は自動で止まり、消去の後の作り直しで使った額の記録は復元後のDBにありません。提供元の利用明細を確認してから `cloud-llm resume` で再開してください。

DBをバックアップの状態へ戻したときは、外部AIの新しい送信を自動で停止します。
復元した時点より後の送信と課金の記録が復元後のDBにないため、再開すると同じ内容を再び送ることがあり、その分は上限の集計にも入りません。
停止の理由は健康状態の警告に出ます。提供元の利用明細を確認してから、上の `cloud-llm resume` で再開してください。
外部AIの設定・APIキー・送信の記録がどれもない導入先では停止しません。
再開時には現在の設定、キーの存在、料金表、保存済み利用記録を再確認します。Jevだけを使わない場合は日次予算を `0` にします。`semantic.mode=off` は意味解析全体を停止する設定です。

## 更新時の注意

患者文脈の処理は `patient_context_refresh.py`、更新計画は `patient_context_plan.py` が所有します。
終日処理し、日本時間00:00に作業日が切り替わります。日付をまたぐ処理は単位の期限内で継続します。保存データと設定の旧識別子（`patient_context_nightly`・`night_id`・`nightly_*` の失敗コードなど）は互換性のため読み続け、新規の記録は `patient_context`・`workday_id`・`patient_context_*` を使います。
実装やモデルの変更で候補の識別値が変わり、旧候補や保留中の承認記録の再確認、再抽出が必要になることがあります。
患者文脈は、推論ルールの版（抽出の版・患者文脈の契約と計画の版・ルールの版）が変わると、全患者分を作り直します。
保存済みの公開文脈を表示するときは、保存された処理経路の契約を使い、生成元の記録との整合性も確認します。APIキーやクラウドのモード・対象範囲の変更だけでは、公開済みの文脈を非表示にしません。
処理経路が変わった患者は、新しい設定に合う文脈を作り直します。原文・抽出結果・モデル・ルールや生成契約が変わり、保存済み文脈の現行性を確認できない場合は表示されません。取得範囲・根拠・権限・公開条件を確認できない場合も同様です。
予算・換算レート・並列数だけの変更では、保存済みの生成契約も、応答待ちの結果も無効にしません。
次の要求（再試行・修復・次の区切り）は、その時点の予算で判定します。
予約した後、送信する前に日次・月額の上限が新たに設定されたり引き下げられたりした場合、その試行は送信せず、未送信として0円で精算します（送信前の再確認が拒否し、予約は `not_sent` で解放されます）。送信の直前には対象範囲・停止状態・権限を確認し、保存の直前には対象範囲と権限を確認します。受信した後に停止・遮断・料金表の期限切れになっても、受信済みの結果は予約時の料金で精算して保存し、次の新しい送信から止めます。
通信の失敗（タイムアウト・切断・接続の拒否など）は、送信済みかどうかを証明できないため、二重の課金を避けて再送しません。提供元の 5xx・529（混雑）も、課金の有無が分からず同じ要求の再送は記録上拒否されるため、待たずにその単位をローカルLLMの処理へ回します。429（回数制限）は、有効な Retry-After（秒数。HTTP 日付の形式は無効として扱います）があればそれに従って待ってから再試行します。ただし、待ち時間が処理の残り時間に収まり、試行回数の上限にまだ達していない場合に限ります。有効な値がないとき、Anthropic は再試行せず、OpenAI は同じ条件の範囲で、間隔を倍にしながら少しのゆらぎを加えて再試行します。Anthropic の支出上限の 429 と OpenAI の利用枠（quota）系の 429 は再試行しません。
1回の試行で応答を待つ時間は、モデルと推論強度の組ごとに決めた上限と、その単位の残り時間の短い方です。profile を指定しない従来の契約は120秒のままで、名前付き profile はそれより長く待ちます。この秒数は実測のない初期値で、ストリーミングは使いません。待ち時間を過ぎた試行は、ほかの通信の失敗と同じく再送しません。
応答を読み取る大きさの上限は出力上限から決めます。上限を超えた応答は中身を読めないため、その単位だけを予約額のまま計上して保留し、同じ要求を再送しません。ほかの単位と提供元の送信は止めません。利用量を確認できないそれ以外の応答は、従来どおり人が再開するまで全体の送信を止めます。

合成テストで確認するのは振り分け、上限、保存、停止・再開の制御です。
実APIでの速度・生成品質と本番での受入は別に確認します。
処理の所有者と公開条件は[推論経路](../development/LLM_RUNTIME.md)と[患者文脈の仕様](../specs/patient-context.md)を参照してください。
