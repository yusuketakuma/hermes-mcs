# 解析への投入保留を確認・解除する

既存の解析ジョブを上書きできない場合、MCSは後続の解析対象と通知の意図を別に保留します。
保存に失敗した範囲も記録し、確認できない内容を解析・通知に使わないようにします。
保留は自動では解除しません。

解除は、元ジョブの形式を現行版が読み取れ、保存済み投稿と通知元を確認できる場合に限ります。
読めない元ジョブや未対応バージョンを、後続の保留だけから作り直す操作ではありません。
不正な形式のジョブは失敗状態へ隔離しますが、元の内容と試行回数を残し、自動再試行を止めます。

## 操作前の条件

通常の更新手順を完了し、旧workerの停止を確認してから使います。
更新処理は常駐workerと残存する解析プロセスを停止し、停止を確認できなければ更新を中止します。
解除後の新しいジョブは、解除に対応した現行版で処理してください。
旧版を別のターミナルなどから起動して同時に使う運用には対応しません。

以下のコマンドはMCSの導入先で実行します。`123`と`456`は架空の患者プロジェクトIDと
スレッド先頭の投稿IDです。実際の対象IDに置き換えてください。
`--offline`では外部APIを呼ばず、ローカルの確認・再投入だけを行います。

## 確認してから解除する

まず、保留の概要を読み取ります。この表示は解除や通知の可否を判定しません。

```sh
.venv/bin/python mcs/semantic/semantic.py --offline --intake-preview 123 456
```

次に、対象全体を検査し、解除に必要な識別値を取得します。この操作も読取り専用です。

```sh
.venv/bin/python mcs/semantic/semantic.py --offline --intake-prepare 123 456
```

成功時のJSONにある `job_sha256`、`hold_epoch`、`snapshot_sha256` を、次の各引数へ指定します。
コマンド内の大文字部分と `1` は、準備結果の値に置き換えてください。

```sh
.venv/bin/python mcs/semantic/semantic.py --offline --intake-release 123 456 \
  --expected-job-sha256 JOB_SHA256_FROM_PREPARE \
  --expected-hold-epoch 1 \
  --expected-snapshot-sha256 SNAPSHOT_SHA256_FROM_PREPARE
```

解除は、書込みロックと対象workerのロックを取得し、準備時の保存内容と再照合して行います。
途中で失敗した場合は解除全体を取り消します。成功すると、元ジョブを保存したまま新しいIDで
再投入し、保留の本文・識別子と解除の記録を残します。解除操作自体は通知を送りません。
同じ準備結果で再実行した場合は、最初の解除結果を返し、ジョブを追加しません。

同じ入力では試行上限・延期回数・次回の実行時刻を引き継ぎます。新しい入力では、通常の
解析ジョブと同じ再投入規則を使います。再投入後の通知は、確認した時点の投稿内容と保存済みの
通知元に基づいて判断します。通知元イベントの状態や試行回数は変更しません。

## 解除を拒否する場合

元ジョブの形式が不明、投稿の内容が変更済み、通知元が欠落、対象患者に送信中の通知がある、
保存に失敗した範囲が対象を含む場合は、保留を維持します。解析が無効・一時停止中、別workerが
対象を処理中、準備後に状態が変わった場合も解除しません。

検査には上限があります。保留・スレッド内の投稿・対象患者の通知イベントはそれぞれ128件、
添付は512件までです。本文などの合計サイズ、各保存行のサイズ、検査時間にも上限があり、
超過時は一部だけを解除せず全体を拒否します。

状態変更による拒否なら、処理や送信が落ち着いてから準備をやり直します。形式不明・保存失敗・
内容変更がある場合は、その原因を確認してください。DBの保留や診断行を削除したり、元ジョブの
内容を書き換えたりして解除を通す操作はしないでください。
