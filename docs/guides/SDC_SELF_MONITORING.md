# Macの状態監視（自社・顧客向け候補）

1.1.0ではCSDCを有効化・接続して提供しません。コードは同梱しますが、新規導入では無効です。通常の起動では、`config.sdc.enabled`が未設定または`false`の間、CSDCの専用ジョブ（状態送信・poll）は登録されません。送信には別の同意も必要です。`optional_features.csdc`は初期設定の案内を表示するかだけを決める設定で、通信を止める設定ではありません。すでに`sdc.enabled=true`を設定している環境を、更新が自動で停止・変更することはありません。以前に有効化して状態が残っている環境で、後から設定を`false`や未設定にした場合に送信が止まることは、中央側の修正待ちのため、まだ確認していません。接続は中央側と実機の受入が整った後の版で行います。

顧客向けの接続と実機受入、中央の正式受入（SDC02）は未完了です。版とプロセス状態を中央へ送ります。患者情報、チャット本文、患者件数、hostname、ファイルパスは送りません。通常の状態監視（heartbeat）は遠隔操作を受け付けない状態報告です。応答は受付の確認や時計の診断に使います。別同意の定型診断は、後半の「遠隔支援の内容確認と本人同意（前景CLI）」を参照してください。遠隔サービス再起動・更新・SSHは未接続です。

## 導入前の確認

検証用Cloudflare account/domain/Access、専用D1、費用上限、責任者と停止手順を承認します。Macは専用OSユーザーとFileVaultを使います。ログイン前・通信断・停止中の即時通知は保証しません。実機の導入/接続/24時間負荷/撤去は別の明示承認後です。

既存の自社検証経路では、導入担当がrepo外の`~/.mcs-security/`を0700で作り、承認した`origin`（HTTPS・443・path/queryなし）、`audience`、`environment`だけを含む`endpoint.json`を0600で配置します。鍵は独立した0600の`credential`に保存され、config.jsonやargvには入りません。顧客向けKeychain対応を代替しません。顧客向けの新規導入は、次の個別配布設定の入口を使います。

### 新規導入での公開設定の取り込み（開発候補）

認証済みConsoleから個別に受け取るmonitor設定を、新しい私有領域へ保存する入口です。実際のissuer・配布経路・復元時の外部基線と、顧客環境での受入は未完了です。Consoleの真正性は、ファイルの内容やHTTPSの見た目だけでは確認できません。既存の自社検証用領域と登録はそのまま保持します。

1. 導入担当が過去の導入・復元履歴を別に確認し、新しい領域を準備します。既存ディレクトリは空でも拒否します。次の保存先は例です。

   ```sh
   mcs connect --prepare-provision-root --state-root "$HOME/.mcs-security-customer-new" --confirm-human --reason initial-installation
   ```

2. 保存されたroot IDを、独立に把握している認証済みConsoleで指定してmonitor設定を発行します。同じConsoleの対象、登録、世代、hashを確認し、公開JSONを受け取ります。登録コードや秘密鍵をJSONへ追加しません。
3. 同じ対象の設定を取り込みます。ファイルとは別にConsoleのorigin・hash・対象等を入力し、表示を比較して保存を選びます。`/path/to/monitor.json` は受け取った公開JSONの場所へ置き換えます。

   ```sh
   mcs connect --import-provision /path/to/monitor.json --state-root "$HOME/.mcs-security-customer-new" --customer --confirm-human --reason initial-provision
   ```

   保存後に「登録へ進む」を選ぶと、同じ生存処理から既存の登録へ続きます。登録コードとConsoleの対象を確認し、監視内容への同意を別に行います。保留・中断した場合は同じファイルと独立確認で取り込みを再実行します。保存済み記録だけを新しい登録許可にせず、receipt・ID・元期限を更新しません。通常の`connect`で欠落や停止記録を初期化しません。
4. R1登録がactiveになった後、配布との一致と受領を照合します。これらは各操作で1要求だけ送ります。

   ```sh
   mcs connection --provision-status monitor --state-root "$HOME/.mcs-security-customer-new"
   mcs connection --provision-ack monitor --state-root "$HOME/.mcs-security-customer-new" --confirm-human --reason provision-received
   ```

R1の登録成功だけでは、公開設定と同じ登録であることは未確認です。中央のstatus/ACKが実際のenrollment・device・claim等を照合します。未発行deviceやACKを初回登録の前提にはしません。ACKのPOSTは、再送も含め元のimport期限までです。期限後の結果不明はstatusで同じreceiptを照合し、新しいACKを送りません。管理者承認の遅延などで未完了でも既存のR1監視は継続します。未送信とみなした別IDや設定の手編集で回避しません。試行上限には送信前の保存済み予約も含み、保存後の期限切れや中断で予約を巻き戻しません。

ACKが401（時刻ずれ等）または429（回数制限）で受け付けられなかった場合は、結果不明として同じIDと本文を保持します。原因を確認した後、本人確認付きで残りの試行回数と元のimport期限の範囲だけ再送できます。自動では再送せず、予約回数・期限を延ばしません。それ以外の4xxや中央statusの失効・置換済み・期限切れは拒否として保持し、ACKを再送しません。

公開設定で有効な形式でも、既存endpointが扱えない明示`:443`等は保存前に保留します。末尾ドット付きの数値hostは、中央が受理できる場合も製品側で拒否し、署名対象のoriginを書き換えません。通常の顧客Keychain呼出し全体の終了時間を、この追加だけで保証するものではありません。

### 同じ端末への支援・再起動設定の配布（開発候補）

monitorの登録がactiveになった端末に、同じroot・tenant・installation・enrollment・端末世代を対象とするsupport、続いてrestartの公開JSONを個別に取り込みます。それぞれのorigin・audience・用途別pin・期限は独立しています。ファイルではなく認証済みConsoleから確認したprofile・hash・対象を入力してください。`--customer`は最初のmonitor登録専用で、支援の取り込みには指定しません。

```sh
mcs connect --import-provision /path/to/support.json --state-root "$HOME/.mcs-security-customer-new" --confirm-human --reason support-provision
mcs connect --import-provision /path/to/restart.json --state-root "$HOME/.mcs-security-customer-new" --confirm-human --reason restart-provision
mcs connection --provision-status support --state-root "$HOME/.mcs-security-customer-new"
mcs connection --provision-ack support --state-root "$HOME/.mcs-security-customer-new" --confirm-human --reason support-received
```

restartの照合も同じコマンドのprofileを`restart`にします。配布のstatus/ACKだけは、どのprofileでも既存のmonitor ingest先とそのaudienceを使います。支援・再起動の処理自体は各profileの送信先と用途別pinを使います。配布受領の確認は案件の同意・操作の承認や、実行成功の証拠にはなりません。

新しいprofileを保存した同じ生存処理で、一度だけ空の支援・再起動記録を作ります。保存後に中断・部分失敗した場合や、記録が欠落した場合は、再取り込み・再起動で初期化の許可を復活させません。停止・同意・結果不明も保持します。復旧は担当者と確認し、旧記録を削除したり互換ファイルを作ったりして回避しないでください。未完の支援設定は通常のR1監視を止めません。

利用時は現在のBundleと期限、用途別pin、端末の実使用鍵、root・案件の束縛を再確認します。Bundleを差し替えると、送信先やpinが同じでも既存の同意・操作は継続できません。この入口は診断の自動送信や遠隔再起動を有効化しません。真正なissuer・配布channel・復元時の外部基線と顧客実機での受入は、引き続き未完了です。

支援・再起動slotを保存した記録は旧版では未対応として停止します。既存領域を保持し、新方式の復元・旧版への切替は別に受け入れます。互換用の`endpoint.json`を手で併設したり、記録を削って新規導入へ戻したりしません。認証エラー等で既存登録が一時停止した場合の本人による`mcs connect`再開は維持し、明示切断・中央停止・失効・鍵交換中の保留とは区別します。

## 登録・確認・停止

1. 管理画面で患者情報を含まない別名と登録コードを発行します。
2. `mcs connect`でコードを非表示入力します。双方の所属・環境・別名・送信範囲・fingerprintを比較し、管理者が承認します。
3. 中央が認証済みの登録期限を返す場合は、管理者の承認前でも端末側で表示内容と送信範囲に明示同意できます。同意を私有領域へ保存してから、既存の専用launchdジョブを導入します。同じ登録を5分周期で確認し、管理者の承認と所属・環境・別名・fingerprint等がすべて一致した場合だけ接続を確定します。承認前はheartbeatもinventoryも送りません。

中央の登録期限が未提供・不正の場合は自動接続を設定しません。管理者承認後に同じ私有領域で`mcs connect`を再実行し、表示を比較して「同意」を選ぶ手動経路を使います。顧客の新規登録は`mcs connect --customer --confirm-human --reason <理由>`を使い、顧客用の信頼済みendpointを配置した別の私有領域とKeychainに保存します。既存の自社用credentialを移行・上書きしません。初期設定のwizardは顧客の登録を代行せず、この手順を表示します。

本体の初期設定を保存して動作条件の確認が終わると、状態監視へ進む任意の案内があります。信頼済みendpointがない場合は「未設定」と表示して本体設定を正常終了します。新しい選択領域では「顧客」「自社検証」「今は登録しない」を明示選択し、既存の登録用途は保持します。`--yes`や本体設定の保存確認は状態監視の同意になりません。本体setupで未知のURLを指定したり送信先を自動発見したりせず、個別配布の独立確認は前節の入口で行います。

同意は送信先と私有領域、登録・端末・鍵、所属・別名・環境・範囲・同意版・中央の期限に束縛されます。ジョブの導入失敗でも同意記録と本体設定を保持します。同じ私有領域の`mcs connect`で再開してください。`config.sdc.enabled`は専用ジョブの有効化、私有stateの`enabled`は接続確定後の送信許可で、別の状態です。

初回の本体設定への保存に失敗した場合は、導入開始時と同じ設定ファイルの世代であることを確かめ、保存済みの表示内容を再提示して本人が再試行を選んだ場合だけ保存を再開します。後からの停止・保存先変更・同内容への書き直しを上書きしません。同意記録の前に、同意hashへ束縛した導入準備を保存します。SDCの設定変更は本体側の私有lockで直列化し、設定の比較と保存の間にSDCの停止操作が割り込まないようにします。このlockはSDCの設定操作だけが対象で、他の設定writerとの汎用transactionを提供するものではありません。

登録時の応答が失われても、登録コードや鍵をバックグラウンドへ保存して再登録しません。端末IDをまだ保存できていなければ本人が同じコードを再入力して同じclaimと鍵の登録を回収します。confirm送信前には同意と結び付いた開始記録を保存し、応答やactive保存の失敗時は同じ登録の認証済みstatusで照合します。期限後は既に開始した確認のactive照合だけが可能で、新しいconfirmは送りません。鍵交換後の確認は従来どおりkeys/statusを使います。

`mcs connection`はローカルの状態を表示し、通信しません。時計状態は初回unknown、認証済みheartbeat応答のserver_timeを診断した次の新規送信からok/skewedになります。接続・プロセス・正常性は別です。実行版の証拠がなければloaded_commitはnullです。

`mcs rotate-key`（顧客のKeychainでは`--confirm-human`と秘密を含まない半角の`--reason`が必要）は新鍵を先に安全保存し、応答が切れても同じrotationへ収束させます。24時間で交換候補が失効した場合は、旧active鍵を保持したまま新しい候補を用意し、再実行を案内します。旧鍵は現在保存済みheartbeatの再送確認と結果照会だけに使い、新しい状態は新鍵で送ります。

`mcs disconnect`は専用ジョブだけを停止してから中央suspendを試みます。オフライン時は中央未確認と表示します。資格情報の削除は別の明示選択で、顧客のKeychainでは`--confirm-human`と`--reason`も必要です。業務データを削除しません。顧客のKeychainで資格情報を削除した私有領域は再登録に使えません（鍵が無いことを再登録の許可として扱わないため）。再開するときは、新しい私有領域を準備して登録し直します。

顧客のKeychainへの書込み・削除は、操作IDと理由を私有領域の記録へ先に保存してから1回だけ実行します。結果が確認できない操作は自動で再試行・修復せず、その私有領域での鍵の利用と送信を止めます。状態表示と送信停止は鍵を読まずに使えます。子プロセスが完了を記録した操作だけは、同じコマンド（connect・rotate-key・disconnect）に`--reconcile-credential --confirm-human --reason <理由>`を付けて実行すると、現在の値を一度だけ照合して記録を完了します。この実行は照合だけで終わり、新しい鍵の操作・通信・送信の再開はしません。停止後の再開は管理者が旧端末を確認した上で、新しい登録コード・端末ID・鍵を使います。

## 障害

独立実行の稼働確認は、導入先root・`data`・状態ファイルのシンボリックリンクを辿りません。rootをリンクで指定した構成は未確認となり、更新も`host unverifiable`で停止する場合があります。導入先の実体ディレクトリを確認し、既存の[更新手順](UPGRADE_AGENT.md)に沿って設定を整えてください。

429/503は5→10→20→30分（±20%）のbackoff、Retry-Afterを尊重します。4xxは送信を止め、自動再試行やサーバーsequenceへの追従はしません。401等で中央の登録がactiveなら、時刻・設定の原因を直した後にmcs connectで同じ端末IDでの再開を明示選択できます。403やsequence巻戻しは管理者へ旧端末の確認と新規登録を依頼します。送信中1件の本文はACKまで固定し、未送信は最新1件にまとめます。遷移記録は1000件/8MiB/7日までです。Connector停止でMCS業務を停止しません。

登録の自動確認では401/403/409、同意内容との不一致を保留として保存し、自動解除しません。明示停止・鍵交換中も自動接続しません。期限や保留理由は管理者と確認してください。患者DBの復元holdとは別の境界で、私有領域の複製・移設はroot bindingで拒否します。全端末復元・移設（SDC08）の実機受入は未完了です。中央が停止してもMCS本体と通常の6定期ジョブは継続します。

### 固定診断イベントの送信（別同意・開発候補）

通常の状態監視・遠隔支援とは別に、固定したエラー分類・段階・重大度・10分ごとの件数を送る候補です。生ログを隠して転送する機能ではありません。患者情報・本文・添付・秘密値・パス・URL・自由な例外文は採取しません。新しい導入では無効のままです。真正なsupport設定とactiveな監視登録を用意してから、Consoleで対象・送信先・期間を確認します。

```sh
mcs diagnostics enable --state-root "$HOME/.mcs-security-customer-new" --valid-for-hours 24 --confirm-human --reason diagnostic-consent
mcs diagnostics status --state-root "$HOME/.mcs-security-customer-new"
mcs diagnostics disable --state-root "$HOME/.mcs-security-customer-new"
```

有効時間は1〜2160時間（最大90日）から明示指定します。画面の送信項目・対象・期限を確認して番号「1」を選ぶまで保存しません。中央Consoleの診断同意も別に必要です。ローカル許可だけでは採取・送信せず、既存の監視ジョブが現在の中央同意を確認した同じ処理内でだけ採取します。既存ジョブを新設・有効化する操作ではありません。

定期処理はR1・構成情報に続いて、診断を1回あたり最大1通信だけ進めます。元の60秒と呼出元の残期限を延長しません。最初の状態照会後に採取・保存し、次回以降に同じ本文とIDで送ります。送信結果不明なら先に状態を照合し、勝手に別IDで再送しません。再送は最初を含め最大4回です。

採取できるのは既存healthの固定分類と独立実行の状態記録など、意味を確認した情報源だけです。未観測の更新処理やHermesの稼働状況などは採取不足として保持し、全項目の確認済みとは扱いません。件数は観測した診断分類の件数で、患者数や実際の障害発生総数ではありません。

端末の内容は1000行・1MiB・7日以内に制限し、本文を固定済みのbatchは部分改変しません。取消・期限・容量で内容を保持できない場合も、結果不明のID等の必要な証拠を残します。`status`は中央照会や鍵取得をせず、既存の保持期限に従って期限切れの内容を整理する場合があります。

`disable`は診断だけの新規採取・送信を止めます。開始承認済みの1通信が終了したとは断定せず、遅いACKも再有効化の根拠にしません。期限後・停止後の再同意は`enable`で作り直さず、同じ対象で`renew`と同じ確認引数を指定します。既存receipt・取消・結果不明を保持して中央の現在同意を再確認します。記録が欠落・破損している場合は自動初期化しません。真正な配布・中央Console・顧客Keychain・実機受入は未完了で、これらの合成検証だけで顧客へ有効化しません。

### 遠隔支援の内容確認と本人同意（前景CLI）

`mcs support connect <case UUID>` は、人がConsoleで確認したcaseについて、署名済みの目的・診断項目・対象scope・担当ref・期限・送信先を表示します。Console上のcase・対象・担当refと照合し、番号「1」を明示した場合だけローカル同意と中央の受付ACKを保存します。空入力・EOF・Ctrl+Cは中止です。本人同意前に行う通信は、本人が起動した固定metadataのpreview取得だけです。connect自体は診断を実行しません。診断には別の個別承認と、本人による `mcs support run` または `mcs support watch` の起動が必要です。サービス再起動は未接続です。

支援先originと用途別公開pinは、前節で承認したsupport Bundleを正本として使います。Storeが既存のbootstrap契約へ投影し、別の`support-bootstrap.json`を併設すると拒否します。managed配布を使わない既存の現地provisionでは、従来の私有bootstrapを保持します。URL・pin・任意ファイルを引数やserver応答から採用しません。root fingerprintと監視先hash、支援先、公開pin、現在の監視identity・実使用鍵hashを照合します。managed経路ではtenant・installation・端末世代等も独立したBundleから固定し、署名previewが一致することを確認して、本人同意をreceiptへ保存します。操作自身のscopeを信頼の初期値にしません。

公開bootstrapの真正な配布・pin発行と初回provisionの運用受入は未提供です。製品に実環境の既定支援先・合成pin・自動初期化はありません。承認済み初期provisionがない端末は保留になります。既存の同意stateが欠落・破損した場合も自動修復せず、失効証拠の消失を復元できるとは扱いません。新しい中央epochと現地再承認が必要です。既存の監視登録・鍵交換の手動経路は別です。

`mcs support status` はローカルの同意・期限・ACK・結果不明だけを表示します。中央の現在の認可、通信の可否、Keychainの利用可否を暗黙に検証しません。acceptが結果不明の場合、同じcaseで再度 `connect` を明示実行すると、保存した同じUUID・同じ本文だけを再試行します。初回送信はpreview期限内、送信開始の永続証拠がある再試行は元のcase同意期限までです。期限延長・新UUIDの自動発行・previewの自動更新はしません。未送信のままpreview期限が切れた場合は、新しいcaseと再同意を担当者に依頼してください。

`mcs support stop` はローカルの新規受付を先に停止します。前景sessionが終了済みなら終了確認済みと表示し、開始済み要求がある場合は「終了は未確認」と表示します。開始承認済みの1要求は停止後に完了する可能性があり、後から到着した同じ要求のACKは証拠として保存しても停止を解除しません。state lock競合・保存失敗では「停止未完了」です。通常の状態監視は継続し、中央caseの閉鎖はConsoleで別途確認します。

前景処理は専用の非待機session lockで1本に限定し、全体300秒（親の期限が早ければその期限）、HTTPは既存10秒、署名検証は5秒と子プロセス回収で制限します。短いstate lock→監視lockで保存・identity再確認を行い、HTTPや本人入力の間は監視lockを保持しません。停止と既に開始したI/Oの終了は別の証拠です。新しいscheduler・thread・常駐serviceは追加しません。

### 個別承認済みの固定診断を1回だけ実行する

`mcs support run` は前景で1回だけpollします。継続照会は後述のwatchを別途明示起動します。保存済み本人同意と中央受付ACK、現在の監視identity・実使用鍵・固定支援先・用途別pinが一致する場合だけ通信し、署名された操作と個別承認を、保存receiptのscope・epoch・許可診断項目・担当refへ照合します。診断名は固定3種だけです。任意shell・file・URL・LLM・患者DB・サービス再起動は要求できません。操作とgrantの用途別pinが承認済み集合になければ保留し、用途を自動追加しません。通常の監視ジョブへ自動接続する機能ではありません。

admit・grantのUUIDと正確な本文は通信前に単一の `support-state.json` へ保存します。grant検証後にも同意・停止・現在binding・owner世代・期限を確認し、STARTEDを原子的に保存してから、固定ローカルproviderを1回だけ呼びます。STARTEDや結果不明の記録がある後の起動は診断をやり直さず、同じreceiptのmetadata照合に限定します。個別操作の生存owner世代は本人同意のowner世代とは別で、後のプロセスへ実行grantを持ち越しません。

診断DTOと正確なreport本文・ID・hashを保存してからreportを送信します。reportのACKが不明な場合は本文を盲目的に再送せず、metadata-only statusで元のreport IDとraw本文hashを照合します。`report:null` や中央operationの状態だけでは、未受付・失敗・再実行可能とは判定しません。一致したreport受付証拠と、診断が示した機器状態は別です。コマンドのreportが`succeeded`でも、source未登録や根拠不足の項目は`unknown`/`null`のままです。provider例外・開始後の期限切れ・停止は結果不明として保存し、再実行しません。

未解決operationは同時に1件だけ保持します。解決済みreport受付の証拠は32件までで、満杯では過去の証拠を削らず新規開始を保留します。STARTED前には最大16KiBのreportを私有JSONへescapeした量と停止用tombstoneの容量も予約します。保存失敗やlock競合を成功扱いしません。admitのACK不明も、既存statusで既知の同じadmit receiptをmetadata照合します。ローカルに永続したADMITTING・grant未要求・STARTEDなしの証拠があり、中央が同じreceiptについてcanceled/expired・state_revision 0・reportなしを返した場合だけ、未開始の終端証拠としてslotを解放します。reportなしだけでは非実行証拠になりません。locally_admitted・consumed・running・unknownやrevision不一致、未知receiptの拒否、grant要求済み/STARTEDの記録は保持して保留し、新しいIDやprivate stateの手編集で迂回しません。

grantの最初のUUID・intentより前に単調時計の基準を固定し、HTTP・署名検証・fsync・待ちを同じ予算へ算入します。中央の秒切捨てに備え、署名されたgrant寿命から1000msを控除した期限と壁時計の有効窓を両方確認します。壁時計の逆行や単調時計との乖離は別の保留条件です。時計採取中のpreemptionはmonotonic-before/wall/monotonic-afterの区間として扱い、採取区間内の不確実性を時計ジャンプと断定しません。残る100msの乖離検出閾値は安全側の実装定数で、実機時計精度・性能・同期の実証ではありません。採取遅延も開始予算を延長しません。

ローカル停止後は、新たなstatus通信も行いません。既に開始承認された要求のbytesや、開始済みproviderを後から回収できるとは表示しません。case期限後でも、ローカル同意が明示停止されておらず現在identityが一致する既存receiptだけは、元reportのID・hashを書き換えずmetadata照合できます。監視R1・scheduler・thread・serviceの構成と周期は変更しません。


### 同意期間内の前景継続照会

`mcs support watch` は既定60秒、`mcs support watch --interval 30` は30秒の待機間隔で照会します。選択肢は30/60だけで、接続や一回実行のrunから自動で開始しません。本人が明示起動した前景処理で、全体300秒・開始時の同意/ACK元期限・親の早い期限の最小までです。新しい同意ownerや更新された期限へ乗り換えず、終了後に同意・grant・UUIDを更新して継続しません。

watchは待機中を含め単一session lockを保持します。待機は単調時計で最大1秒ずつ区切り、停止・owner変更・期限を検査します。state/監視lockはsleep中に保持しません。sleep中のstopは新規受付を止めても、watchが終了するまで「開始済み要求の終了は未確認」と表示する場合があります。Ctrl+C/EOF/例外でも保存済みreceipt・STARTED・UUID・本文を保持します。明示した `--state-root` のstop/statusは製品configが破損していても、そのconfigを読まず同じ私有rootで停止・表示できます。未指定rootが設定から解決できない場合は保留し、configを補修しません。

空poll・確定したreport受付ACK/本文hash照合・確定した未開始pregrant終端の後だけ、次の待機期間へ進みます。結果不明・未解決grant/admit・holdでは同じreceiptを保持してwatchを終了し、新しいpollやIDを作りません。1回処理の完了から次の30/60秒を数え、遅延分を連続catch-upで取り返しません。30/60秒は待機中の照会間隔であり、承認要求から診断完了・report確定までのSLAではありません。HTTP・署名・provider・保存・busy・オフラインで追加時間や保留が生じます。実機の停止応答・性能・時計精度は未測定です。R1の300秒job、周期、署名、通信先、サービスには変更しません。

### 再起動の計画と個別同意（開発候補・実環境未受入）

再起動の準備は、診断への同意と別に行います。対象は登録済みのstandaloneサービスだけで、OS再起動・任意サービス・任意コマンドは対象にしません。以下の入口は準備と同意登録のためのもので、完了してもサービスを自動再起動しません。

1. `mcs support plan-restart <case UUID>` で、現在の案件同意と中央の受付を確認します。取得先・対象・期限を表示し、本人が同意した場合だけ、現在のサービス登録と実行中のサービス所有者の状態を取得します。送信内容を確認して、再起動計画用の点検結果を中央へ登録します。
2. 中央Consoleで個別の提案・承認を確認します。診断への同意だけでは再起動を許可しません。
3. `mcs support consent-restart <operation UUID>` で、署名済みの変更案と対象・期限を確認します。本人が同意し、計画時と同じサービス所有者・登録・案件が維持されている場合だけ、変更同意と中央の受付証拠を保存します。

正式な接続先・再起動用途の公開pin・初回状態を信頼できる導入経路から供給する手順は、まだ実環境で受け入れていません。未供給の端末では、これらの入口は鍵の取得・通信・状態採取をせず停止します。診断用pinを再起動用へ流用せず、応答内のURL・鍵・scopeを信頼の初期値にしません。記録の欠落・破損・停止を新規導入とみなし、同意を初期化することもありません。

登録情報の読取りは、同じ計画につき初回を含め最大4回です。再開しても残り回数と元の期限を引き継ぎます。認可拒否・競合・上限超過・取消・期限切れでは再試行しません。応答本文が壊れている場合も、確認済みのHTTP拒否を通信障害へ変換しません。点検結果や変更同意の送信結果が不明な場合は、別IDを発行してやり直さず、保存済み記録を保持します。

計画時に採取するサービスの世代・状態は、その時点の観測です。後で同じサービスが動いていることや、再起動の成功を証明しません。所有者が交代した、処理中、更新中、状態が不明、更新用lockがまだない、といった場合は保留します。点検のために通常業務の受付を閉じたり、lockや更新記録を作成・削除したりしません。Runtime側は設定済みの同じ私有領域のrestart Bundleを確認して、既存の点検経路へ渡します。このmetadata確認は公開鍵の形式を検査しますが、Keychain・署名検証・外部通信を呼びません。送信や変更同意の確定前には、CLI側で現在の資格情報と権限を再検証します。

`mcs support status` は保存済みの準備・同意情報を確認する入口です。現在の中央認可やサービスの生存を保証しません。`mcs support stop` は親の支援同意を先に停止し、続いて再起動の準備・同意を停止します。途中の保存に失敗した場合は停止未完了と表示します。保存したACK・停止記録・結果不明の記録を消して再開しないでください。実際の再起動、終了から後継サービスの起動までの対応関係、実機の受入は別の確認事項です。

独立実行の再起動開始経路では、顧客の鍵を確認するたびに、その試行だけが所有する専用プロセスでKeychainを読み直します。再使用禁止の記録を保存した後も確認を省略せず、最後の読取りとプロセスの正常終了を確認してから開始します。読取りは一回最大1秒と元の期限の早い方までとし、取消・時間切れ後は開始せず、実際の終了・回収を待ちます。回収待ちが続く間は予約を保持します。この変更は遠隔再起動を自動で有効化せず、通常の監視・前景診断の全読取りを置き換えるものでもありません。外部のKeychain更新と開始の原子性は保証しません。

### 現地での確認・復旧が必要な場合

次の場合は現地の操作者・管理者による確認が必要です。`mcs support status`で読めるのは保存済み情報だけで、中央の復旧やMCS本体の正常動作を確認するコマンドではありません。OSやconnectorが動かない場合は、`status`や`stop`も実行できないことがあります。

| 状況 | 現地で行う確認 |
| --- | --- |
| 中央停止・通信不能 | MCS本体の収集・通知と支援の接続状態を分けて確認し、中央の復旧は中央担当へ依頼します。支援の停止だけでMCS本体が停止したとは扱いません。 |
| OS未起動・FileVault解除前 | 現地で起動し、本人がOSの標準認証で解除します。遠隔支援から起動・解除はできません。 |
| Keychainがロック中・利用拒否 | 本人がOSの標準操作で利用可否を確認します。鍵の自動再作成・平文保存への切替で回避しません。 |
| connector・設定・同意記録の欠落や破損 | 保存済み記録を保持し、導入担当と初期設定・復旧手順を確認します。同意記録を削除して新しい操作を開始せず、必要な中央epochの更新と現地再承認を受けます。 |
| サービス所有者との権限差・権限不足 | 管理者が対象サービスと操作者の権限を確認します。sudo・root helperや患者データの読取り権限追加で迂回しません。 |

パスワード・FileVault回復鍵・Keychainの秘密値をチャットへ送らないでください。支援を止める場合は`mcs support stop`の結果を確認し、「停止未完了」や「開始済み要求の終了は未確認」を終了済みとして扱いません。`watch`の終了や中央での案件closeも、保存済みの`unknown`を成功・解決済みにはしません。

[更新・中断復旧](UPGRADE_AGENT.md)、[DB復元・鍵回復](BACKUP.md)、[通知結果の確認と再送判断](NOTIFICATION_RECOVERY.md)は、それぞれの計画・影響や損失の確認・人承認の手順へ進みます。遠隔支援への同意はこれらの実行承認を兼ねません。現在の支援CLIが実行する操作は定型診断だけで、再起動の準備・同意登録はサービス再起動の実行へ未接続です。R5の更新、R8のSSH・画面共有は別の受入と承認が必要です。
