# 自社検証Macの状態監視（R1候補）

この機能は未配備・実機未受入です。自社1台だけを対象に、版とプロセス状態を中央へ送ります。患者情報、チャット本文、患者件数、hostname、ファイルパスは送りません。命令受信・restart・更新・SSHはありません。

## 導入前の確認

検証用Cloudflare account/domain/Access、専用D1、費用上限、責任者と停止手順を承認します。Macは専用OSユーザーとFileVaultを使います。ログイン前・通信断・停止中の即時通知は保証しません。実機の導入/接続/24時間負荷/撤去は別の明示承認後です。

導入担当がrepo外の`~/.mcs-security/`を0700で作り、承認した`origin`（HTTPS・443・path/queryなし）、`audience`、`environment`だけを含む`endpoint.json`を0600で配置します。鍵は独立した0600の`credential`に保存され、config.jsonやargvには入りません。顧客向けKeychain対応を代替しません。

## 登録・確認・停止

1. 管理画面で患者情報を含まない別名と登録コードを発行します。
2. `mcs connect`でコードを非表示入力します。双方の所属・環境・別名・送信範囲・fingerprintを比較し、管理者が承認します。
3. 再度`mcs connect`を実行し、端末側でも「同意」を選びます。接続監視の専用launchdジョブだけを導入します。

`mcs connection`はローカルの状態を表示し、通信しません。時計状態は初回unknown、認証済みheartbeat応答のserver_timeを診断した次の新規送信からok/skewedになります。接続・プロセス・正常性は別です。実行版の証拠がなければloaded_commitはnullです。

`mcs rotate-key`は新鍵を先に安全保存し、応答が切れても同じrotationへ収束させます。24時間で交換候補が失効した場合は、旧active鍵を保持したまま新しい候補を用意し、再実行を案内します。旧鍵は現在保存済みheartbeatの再送確認と結果照会だけに使い、新しい状態は新鍵で送ります。

`mcs disconnect`は専用ジョブだけを停止してから中央suspendを試みます。オフライン時は中央未確認と表示します。資格情報の削除は別の明示選択です。業務データを削除しません。停止後の再開は管理者が旧端末を確認した上で、新しい登録コード・端末ID・鍵を使います。

## 障害

429/503は5→10→20→30分（±20%）のbackoff、Retry-Afterを尊重します。4xxは送信を止め、自動再試行やサーバーsequenceへの追従はしません。401等で中央の登録がactiveなら、時刻・設定の原因を直した後にmcs connectで同じ端末IDでの再開を明示選択できます。403やsequence巻戻しは管理者へ旧端末の確認と新規登録を依頼します。送信中1件の本文はACKまで固定し、未送信は最新1件にまとめます。遷移記録は1000件/8MiB/7日までです。Connector停止でMCS業務を停止しません。
