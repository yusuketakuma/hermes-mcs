# 添付資料の文字起こし（1.1.2向け）

macOSで画像・PDFの文章をローカルで取り出し、投稿本文とは別の原資料として保存します。
診療情報提供書、訪問看護・薬剤管理・居宅療養管理・リハビリ等の報告書、
処方資料、PCAポンプの表示を対象にしています。
Yomitokuは医療専用に追加学習したモデルではありません。文書認識の結果に、
医療文書の項目分類と、ページ・引用位置を保持する処理を組み合わせます。

## 導入と更新

Yomitokuの公開コード・モデルはCC BY-NC-SA 4.0です。個人の非商用研究など、
利用条件に合う用途で導入してください。商用利用は提供元との別契約が必要です。
本機能の導入操作は、商用利用の許諾やモデルの再配布許可にはなりません。

```sh
bash install.sh --with-yomitoku
```

MCSのPythonとは別に、`MCS_ROOT/ocr-venv`へPython 3.13とYomitoku 0.16.1を導入します。
公式ソースの固定commitを使い、必要なモデルは導入時に取得します。
既存のモデルキャッシュは削除しません。選択した導入項目は更新時にも引き継ぎ、
依存や導入手順が変わった場合は再導入が必要になります。

導入しただけではOCRは動きません。実行ファイルの絶対パスを指定して有効にします。
次は標準の導入先を使う例です。`$HOME`は実際のホームディレクトリに置き換えてください。

```sh
python3 mcs/ops/mcs_setup.py init --set 'attachment_ocr={"enabled":true,"executable":"/Users/your-user/.mcs/ocr-venv/bin/yomitoku","timeout_seconds":120}'
```

保存済み添付のOCRとローカルLLM解析は、毎分の独立ジョブで進めます。収集の認証エラーなどで
新規取得が失敗していても、保存済み資料は現行性・患者権限を確認して処理します。
アーカイブ・閲覧禁止・権限失効・患者情報がない資料は解析しません。
OCR実行中の設定OFF・実行設定変更も保存前に確認し、新しい結果を採用しません。
手動では`python3 mcs/ops/mcs_ocr.py --run`を使えます。
1回のジョブは最大900秒で、ローカル解析を優先しながら原画像のOCRも進めます。
1ページ・1添付を処理して必ず終了する制限はありません。重複起動は専用ロックで防ぎ、
保留・無進捗・失敗の段階を同じ回の中で繰り返さず、もう一方の処理へ進みます。
ローカル解析は背景枠とGPUの順番待ちを使います。OCR本体も起動前にメモリーの余裕を確認し、
不足・不明なら試行回数を消費せず保留します。
個別ページの新規クラウド送信は行いません。クラウドLLMは対象患者の原文・添付OCR全文・補助要約を集約した
患者コンテキストの作成・更新と、その品質修復に使います。既存の対象範囲・予算・同時実行枠に従います。
クラウドの保留や送信結果不明を完了扱いにはしません。
OCR中は収集やLLMと共用の書込みロックを保持しません。演算ライブラリは各1スレッドとし、
同時OCRを専用ロックで防ぎます。Yomitoku内部の処理には並列実行があります。実行中の通信と、一時領域外への書込みは禁止します。

## 原文と出典

投稿本文は書き換えません。OCR資料は添付ID、投稿ID、ページ、元ファイルのSHA256、
ページ本文のSHA256、使用エンジンと版を持つ別の保存記録です。
添付の詳細表示にはページ本文と医療項目を、集計表示には状態だけを返します。
添付が変更・撤回された場合や投稿が削除された場合は、古い文字起こしを現行の資料として使いません。
通常の保持期間に従って添付実体だけが削除された場合、保存済みの文章は残し、元ファイルがない状態を区別します。

OCR文は投稿者の発言として扱いません。ページごとの原文と引用を使って解析し、
必要なローカル解析と品質確認が完了した原資料を患者コンテキストへ統合します。
保留や送信結果不明が残る資料は、完了として数えません。
投稿日時を資料内の診療日時として補いません。原資料の更新・撤回時は、古い情報への依存を記録して再評価します。

チャットでは原文の下に「添付の文字起こし」を分けて表示します。長い本文は既存の本文表示から開きます。
カードには文字起こしの状態と、作成時点の患者コンテキスト進捗を`👤 73%`のように表示します。
個別クラウドの進捗アイコンは表示しません。進捗だけでは更新せず、別の理由で更新する場合も初回の値を使います。
作成時点の進捗を確認できない場合は`👤 —`と表示します。
元の添付ファイルは再アップロードせず、既存の本文・スレッド・ファイルの配送経路で更新します。
個別解析の新規クラウド送信は行わずローカルで継続します。クラウドは患者コンテキストの作成・更新に、既存の対象範囲と予算で使います。外部exportは追加しません。

必要な解析が完了したOCR資料は、薬剤言及履歴、服薬管理の報告、測定値の時系列表示にも採用します。
親投稿・添付・ページを出典として保持し、資料にない測定日時・用量・単位を補いません。
測定値の系列化には、対象者・値・単位・明示された日付と原文の照合が必要です。
保存済みの`labs`・`vitals`も、共通の原文検証を通した観測値として患者コンテキストへ渡します。
本人・実施済み・引用一致・明示日付・単位を確認できる記載だけが対象です。作成日・生年月日・予約日などが
同じ引用にある場合は測定日へ転記せず、正しい測定日も混在する場合を含めて保留します。
観測値を渡したことと系列化の完了は別です。複数段落の資料など、系列化の既存条件を満たさない記載は未確認に残ります。

## 紹介状の経過を読む

患者コンテキストの「経過タイムライン」では、解析済みの診療情報提供書を、
「紹介状の記載（日付順）」「紹介状の記載（時点不明）」「紹介状の基本情報」に分けて表示します。
明示された年月日を使い、年・月までの記載はその精度で残します。生年月日・文書作成日や投稿日時は、
診療上の出来事の日付にしません。否定・予定・訂正は原文に残します。

対象は独立した「診療情報提供書」「紹介状」の見出しがあり、文字のある全ページで必要な解析が完了した資料です。
新しい添付から最大50件などの読取り上限があり、未解析や上限到達は点検未完了として表示します。
追加のLLM照会は行いません。項目・日付の対応と制限は[紹介状の時系列仕様](../specs/referral-timeline.md)を参照してください。

## 読み取る項目

| 資料 | 整理する内容 |
| --- | --- |
| 診療情報提供書・退院資料 | 傷病名、紹介目的、既往歴、家族歴、現病歴、症状と検査結果、治療経過、処方 |
| 患者背景・療養資料 | アレルギー、生活背景、家族・介護環境、ADL・認知、栄養、医療機器、療養方針・本人の意向 |
| 訪問看護等の報告書 | 報告期間・訪問日時、病状経過、実施した看護・リハビリ、服薬状況、家庭の介護状況、衛生材料、特記事項 |
| 薬剤管理等の報告書 | 記載された薬剤・服薬状況、経過、指導・支援内容、評価を原文の見出し単位で保持 |
| PCAポンプ | 残量、持続流量、ボーラス量、ロックアウト時間、積算量、要求・実施回数、薬液濃度 |

項目は原文の見出しと引用位置を基に分類します。記載のない病名やアレルギーを
「なし」と補いません。「既往歴及び家族歴」のような複合欄は一つの引用として残します。
薬剤の規格を服用量として転記せず、薬剤名を似た名称へ置き換えません。
見出しのない自由記載や未対応の見出しも全文に残りますが、自動分類されないことがあります。

PCAの数値は同じ行のラベル・数字・単位が対応する場合だけ候補を作ります。
残量と積算量、持続量とボーラス量は別の項目です。同じ行のラベルと値がタブで区切られている場合も、
一つのラベルに数字と単位が対応すれば候補を作ります。別行、複数のラベルや値、単位不足、
`0`と`O`の混同がある候補には数値を付けません。数値付きの候補も臨床的な正しさを保証しません。
残量から終了日時や投与量を計算せず、設定変更も行いません。

## PCAの記載と誤り報告

経過タイムラインではPCAの記載も未確認候補として表示します。残量・流量などの原文と添付ページを保持し、
同じ行の測定日・観察日・計測日に直結する日付だけを使います。日付なしや年が不明な記載は時点不明とします。
続きページにPCAの明示がなくても候補は残し、数値を確定しません。作成日・投稿日時から測定日を補いません。
投与量・終了時刻の推奨や設定変更には使いません。

薬剤詳細の「添付#番号・ページの誤りを報告」は、そのOCRページの解析を対象にします。
薬剤が0件になったページも、「本文表示」から添付の解析ページを開き、対象ページの誤りを報告できます。
投稿本文の報告とは分け、確認画面で人が承認した理由と対象を記録します。
原文や元画像は変更せず、対象ページをローカルLLMで再解析します。患者コンテキストの対象であれば、
必要な確認を通過した結果を患者コンテキストの更新に使います。個別ページのクラウド再解析は行いません。
結果不明・解析未完了・古い対象は報告を受け付けません。保留中の送信を推測で再送する操作ではありません。

今回の解析処理の変更により、適用前の解析は再評価対象になり得ます。過去の課金応答・会計記録は保持します。
同じ原資料・送信内容・承認範囲・モデルの確定応答は、旧保存証拠と現在の解析条件を検証して再利用します。
結果不明・破棄済み・証拠不足の応答を再利用したり、再送の許可に変えたりしません。
クラウド会計の復旧に失敗しても、独立して進められる資料のローカル解析は継続し、復旧待ちを監視へ残します。
同じ旧クラウド要求はローカルへ切り替えず、結果の確認や回復ができるまで保留します。
再評価にも既存の承認範囲・予算が適用されます。未報告ページも含めた旧版との再利用を一律に保証するものではありません。

## 形式と制限

- 画像はJPEG・PNGなど、実体の形式を検査してから処理します。対応外のファイルは未対応として残し、紹介状・PCAの点検では未解析と分けて除外件数に数えます。
- PDFはテキスト層を優先し、文章のないページや画像を含むページはYomitokuで読み取ります。ページごとの処理方法を保持します。
- 1添付64MiB、30ページ、画像1ページ4,000万画素、描画合計8,000万画素、出力2MiBを上限とします。
- 表は空欄と結合セルの位置を残します。1表のセル数と行方向の展開はそれぞれ10,000件までとし、位置の重複や出力上限を超える表は処理失敗として残します。
- 初期設定では1件120秒までです。大きな資料や処理失敗は完了扱いにしません。初回を含む3回までは1時間以上の間隔で試行し、
  以後は前回の結果保存から24時間以上空けて1回ずつ再処理します。既存ジョブの実行枠・資料の順番待ちに従うため、実行時刻は遅れる場合があります。
  失敗履歴と元資料は残し、再処理で検証に通った新しい結果を採用します。対象外の形式と検証済みの成功結果は日次再処理しません。
- 原本OCRの1件あたり上限（初期120秒）とは別に、ローカル推論が1ページに使う期限は最大300秒です（残りのジョブ予算が短い場合はそれ以下に収まります）。ジョブ全体の900秒は処理予算であり、保存時のwriter待ちなどを含む厳密な壁時計の上限ではありません。
- 保存済みで未処理の添付も順に対象にします。削除済み・取得失敗の添付を自動で再ダウンロードする機能は追加しません。
- 訪問日の丸印やチェック欄、読みにくい手書き、機器の表示は文章だけでは正しく読めないことがあります。欄の意味や日付を推測で補いません。

Yomitokuは文書向けで、機器の液晶画面などの情景文字は得意分野とされていません。
文字起こしが保存できたことと、薬剤・病名・測定値が正しいことを区別します。
研究用の精度評価では、原画像と人による正解付けで確認してください。

- [日本医療情報学会・JP-CLINS診療情報提供書 v1.7.1](https://jpfhir.jp/fhir/clins/ighistory/igv1.7.1/referral-doc.html)：病名、既往・家族歴、アレルギー、身体・社会背景、処方、原資料の区別。FHIRへの適合を主張するものではありません。
- [厚生労働省・訪問看護計画書等の記載要領（2026年3月27日）](https://www.mhlw.go.jp/content/12400000/001681763.pdf)：2026年6月以降の看護報告書・記録書の項目。
- [JMS・PCA法について](https://medical.jms.cc/diagnosis/ifp/pca/04.html)：持続投与、ボーラス、ロックアウトを分ける根拠。投与量の推奨値は実装に取り込みません。
- [Yomitoku公式リポジトリ](https://github.com/kotaro-kinoshita/yomitoku)：API、CPU軽量処理、対象文書、利用条件。調査日：2026年11月5日。

## 旧OCR結果からの更新

表の空欄位置を失う旧形式のOCR結果は、履歴を残したまま現行の原資料から除外します。
元ファイルが残っていれば、次回のOCR実行で新形式として読み直し、必要なローカル解析へ進みます。
元ファイルが保持期間に従って削除済みの場合は利用不可となり、自動で再取得しません。
新しい原資料を使う患者コンテキストの作成・更新と品質修復には、既存の承認範囲と予算を適用します。
旧結果の課金応答は精算記録を保持しますが、新形式の臨床結果として採用しません。
