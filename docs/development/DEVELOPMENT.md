### 目的からコードと資料を探す

| 目的 | 配置と境界 |
|---|---|
| 収集・保存・解析・表示 | `mcs/`。`core/` は保存基盤、`llm/` は共通推論、`patients/` は患者集約、`medications/` は薬剤処理、`signals/` は検知、`export/` は手動外部出力、`ingest/` は収集、`extract/` は抽出、`semantic/` は意味解析、`notify/` は通知の組立て、`views/` は読取り表示、`ops/` は管理操作 |
| 通知先への接続 | `adapters/{slack,discord,lineworks}/` と共通の `adapters/common/`。Hermes接続の入口は `hermes_plugin/`、独立hostは `mcs_standalone/`、LINE WORKSの互換CLI入口は `lineworks_adapter/` |
| 導入・常駐・復旧 | 入口は `install.sh` と `scripts/mcs`。`deployment/launchagents/` は常駐設定、`deployment/scripts/` は定期実行wrapper、`deployment/recovery/` はcheckout外へ配置する復旧ツール |
| 開発用の生成・検査 | `scripts/development/` は文書・画面・リリース記録などの生成器。`ci/` は安全ゲートと事故記録の回帰対応、`.github/workflows/` はCI・リリース連携 |
| 合成テスト | `tests/` は実装領域に対応し、共通ヘルパーは `tests/support/`、固定の入力は `tests/fixtures/`。実SDKとの契約確認は `integration/` で別に実行 |
| 評価のコードと入力 | 評価器は `mcs/extract/eval/`・`mcs/semantic/eval/`、固定の評価基準・合成資産は `evaluation/`。定期処理と評価実行を分ける |
| 配布する公開原本 | `resources/drug-master/`。公式原本と出典・版・hashを保持し、本番の私有辞書やテストfixtureと混ぜない |
| 現在の手順と契約 | `docs/guides/` は操作、`docs/specs/` は契約、`docs/development/` は開発手順。入口は[文書の索引](../README.md) |
| 計画と履歴 | `docs/ROADMAP.md`・`docs/roadmap/` は基準日付きの計画。版ごとの受入・計画・画像は `docs/releases/v版番号/`、版横断の事故証跡は `docs/dev-records/` |
| 変更の記録 | `changes/` は未リリースの変更記録、`changes/archive/` は生成後の履歴。利用者向けの正本はルートの `CHANGELOG.md` |

ルートの `Makefile`・`pyproject.toml`・`conftest.py` は共通の開発・検証設定、`AGENTS.md`・`SECURITY.md` は作業と安全の制約です。コード移動時は、CLI・pluginの入口、導入先、生成器、テストと文書参照を一緒に確認します。

`mcs/_mcs_path.py` による既存のflat importを維持します。旧抽出世代 `v2/`・`v3/` は説明のみで、残存コードを実行対象へ戻しません。更新用コードと独立した復旧ツールの共通処理は、checkoutが壊れた場合にも復旧できるよう各配置先に保持し、対応テストで一致を確認します。

### 関数内 import の使い分け（手書き）

import はモジュール先頭に置くのが原則。関数内に残すのは次の場合だけ。

- **正本への依存**: semantic処理は`semantic_transport`・`semantic_store`等の所有moduleを直接参照する。テストの差し替えもその正本へ行い、CLI facadeへの呼戻しや遅延importで循環を隠さない。
- **起動コストの抑制**: 10分ジョブや CLI が使わない重いモジュール（`mcs_setup`・`ledger` など）。
- **任意 SDK**: `adapters/discord/{actions,cards}.py` の `discord`、独立実行の公式 SDK（AGENTS.md・`ci/gates.py` の制約）。

## 運用

ジョブの時刻・起動引数・配置先の正本は[スケジューリング構成](../../deployment/launchagents/README.md)です。
`runtime_mode=standalone`では単一hostが定期ジョブ・cmd取込・抽出workerと接続を所有し、
Hermes cronとは併用しません。以下のcron・wrapper配置先はHermesモードの説明です。
モード選択と停止・再開は[独立モード](../guides/STANDALONE.md)を参照してください。

- スケジューラ: hermes cron `MCS unread check`（`*/10 * * * *`,
  `--no-agent` script `~/.hermes/scripts/mcs_check.sh`） — ログ `data/mcs.log`。
  実行履歴・incident は `hermes cron runs` / `hermes cron incidents` に残る。
  MCSサーバーの負荷対策として、収集は24時間10分間隔に変更した。
  health watcher 自身は5分間隔でローカルの状態を確認し、
  `health.tick_interval_s`（既定600秒）と`health.max_missed_runs`から欠測許容を判定する。
- 深掘り trickle: hermes cron `MCS durable drain`（`10,40 * * * *`, `--jobs-only`） —
  未読取得を飛ばし fetch_jobs のみ消化。全患者の全履歴を
  `since=0` まで少しずつ取得(1run=最大8患者×3頁、cursor は payload に
  耐久保存、中断しても次 run で続きから)。config `deep_history` で
  有効/無効、`trickle_pages` で頁数変更
- discovery: `fetch_jobs(kind='discovery')` が1日1回 `/projects` を
  列挙 → 未読を出さない新規患者を自動登録し trickle seed。
  `discover_archived` が有効なら `/kartes?is_archived=1` も列挙し、
  `is_archived=1` で登録＋`history_head` job(最終同期予約)を同一Txで
  起こす。アーカイブ患者はfrontier/backfill対象外・通知抑止。
  保存済み投稿のルール抽出・AI抽出・意味チェックはアクティブ患者を先に処理し、
  残り枠でアーカイブ患者を処理する。新規・変更投稿は通知なしで意味チェックへ

#### 承認済み参照セットによる統計検証（`mcs_refstats.py`）

統計コードの変更が結果を変えていないか、人が承認した参照セットで
回帰確認する運用ゲート。

```bash
# 1. snapshot 上の統計を参照セットとして capture（pending 置場へ）
$PY mcs/ops/mcs_refstats.py capture --name nightly --preset operational

# 2. 内容を人が確認し、file_hash を承認コマンドに渡す
$PY mcs/ops/mcs_refstats.py pending --name nightly   # file_hash を表示
echo '{"command_id":"<uuid>","actor":"<人>","name":"nightly",
       "file_hash":"<hash>","reason":"<理由>"}' |
  $PY mcs/views/mcs_view.py control refstat_approve --project 1 --confirm-human

# 3. 以後、任意の snapshot で再計算して突合
$PY mcs/ops/mcs_refstats.py verify --name nightly   # match/drift/regression/unverified/superseded/definition_missing/definition_changed
```

- 承認は既存の人承認経路（`--confirm-human` + receipt）のみ。file は
  `<data>/refstats/{pending,approved}/` に置かれ、承認時にバイト列の
  SHA-256 を `refstat_approval_v1` artifact に記録する（applied receipt
  と突合するため、artifact 単体の不正挿入では承認済みにならない）。
- `verify` は読み取り専用。file の hash と artifact が一致しない、
  artifact が snapshot に存在しない場合は `unverified`、旧承認の
  file に差し戻された場合は `superseded` で失敗（exit 2）。
  同一 snapshot での差分は `regression`、別 snapshot での差分は `drift`。
- 抽出監査（`extraction_audit`）の統計を含む基準は、capture 時に監査の計測定義
  （`audit_definition`）を記録する。verify で定義の記録が無ければ
  `definition_missing`、現在の定義と違えば `definition_changed` とし、数値は比較
  しない（exit 2）。新しい定義で capture し直し、本人承認を取り直す。
- 現行の抽出監査では、同じ患者・投稿・原文について対象版の保留記録がある場合や
  保留記録を読めない場合、現行ワーカーの hold 契約を確認できない。保留を確定
  せず、抽出結果がある投稿は `attention`、`omission_proxy` は `partial`・
  `hold_status_unverified` とし、`hold_unknown_posts` に件数を記録する。抽出結果
  がない投稿は `no_output` のままにする。
- 版7から版8への固定評価は、`audit_cohort.py pin` と `compare` の両方に
  `--inference-version 0.1` または `--inference-version 1.0` を指定する。
  省略時は現在の公開推論世代を使う。指定した世代は計測定義に含まれ、異なる
  世代の pin は比較できない。0.1 は旧公開世代を選ぶための指定であり、当時の
  実環境で保存された snapshot の完全な再現は未検証。定義変更前の pin は保持し、
  元の baseline を同じ条件で再現できなければ、作り直した比較を成功扱いしない。
  固定評価の保留記録も選択した公開世代に限る。世代キーの欠落は 0.1 として扱い、
  記録のメタデータが不正で世代を確認できない場合は要確認とする。
- capture は `as_of` 未指定時に snapshot 生成時刻を query へ固定して
  保存するため、時間窓つき統計でもデータ不変の再 publish は `drift`
  にならない。
- `--data-dir` は稼働中 ledger.db のあるディレクトリと一致させる
  （既定 `~/.mcs/data`）。承認 op は ledger の実パスから同じ場所を
  導くため、別ディレクトリの pending は承認対象に届かない。
- 参照ファイルは集計値のみを含み、メッセージ本文を含まない。

  過ぎても記録上の応答を確認できない場合 — 「対応がなかった」とは
  言わない）、`rx_request_visibility`（医師等他職種宛の処方関連依頼の
  言及 — 処方パイプラインの先行可視化・FYI）、`adherence_concern`
  （「管理できない」・飲み忘れ・残薬等の服薬管理困難の言及 — 処方変更
  ではなく介入検討の提示）、`discharge_notice`（薬変更共起のない退院・
  転院の言及 — 共起ありは transition_reconciliation が担当）、
  `symptom_after_med_change`（同一投稿内の薬変更言及＋新規/継続症状 —
  因果は人が原記録で判断）、`comm_concentration`（直近72hの記録集中）、
  `rx_period_expiry`（期間表現の終了間近）、`rx_period_lapsed`
  （期間表現の終了後に新しい期間表現の記録がない — 内服切れの
  可能性。終了後 `rx_lapsed_days` 日まで）、`transition_reconciliation`
  （extract_llm の型付き discharge/transfer イベント±14日の薬変更言及の
  共起 — 「退院」文字列ではなく抽出イベントを使う）。
- 候補は「原記録の確認を求める提示」であり、記録が見つからないことは
  対応の欠如を意味しない。文言もその旨を明記する。
- 自己同一性: 深掘り実行（`--jobs-only`）と自己プロフィール未記録のtickで、MCSの`GET /users/self`から氏名・
  職種・所属施設を取得し `self_profile_v1` artifact として記録する
  （変化時のみ追記）。その施設の投稿由来の言及はアラートにせず、
  その施設・職種の投稿は応答者として数える。config `signals.*` は
  手動オーバーライドとして優先される: `self_organizations`・

  とみなす追加の宛先表記。自動判定は「薬剤師」「薬局」「調剤」を含む宛先）。
  `mcs_setup init --self-org/--self-professions` でも設定できる。
- 自局スタッフ一覧: 自己同一性と同じ頻度（`--jobs-only` の深掘り実行と、
  自己プロフィール未記録の tick）で、`/users/self` の各所属局について
  `GET /stations/{id}/staffs`（`per_page=100`、最大10ページ、

  `{staff_id, name, professions, station, is_self}` を

  投稿の送信者名と同様にローカル台帳にだけ保存される。失敗は
  run 結果の `station_staff: "failed: <型>"` として記録し（`errors` には
  入れないので health を degraded にしない）、既存の一覧を保つ。
  通知カードの `📝 タスク作成` の担当者候補（`notify_cards.assignee_choices()`、
  最大25件）はこの一覧を使い、無ければ自局名で投稿した送信者で代替する。
- カードの view 一覧（メニュー）: `自分のタスク` は
  `notify_views.my_tasks_view()`（押した人の表示名と担当者欄を
  `assignee_matches()` で空白無視照合。「氏名（事業所）」は氏名部分で
  照合。手入力の別表記は拾えない）、`未確認一覧` は `unacked_view()`
  （直近7日に更新された thread/signal カードで、最新 manifest の shown と
  現在の source_generation に対する未取消の ack が無いもの。digest カードは
  複数 project にまたがるため対象外）、`🔎 この患者を検索` は
  `patient_search_view()`（取得済み・本文 full の投稿を空白除去した部分一致で
  AND 検索。FTS5 の unicode61 tokenizer は日本語を語に分割しないため
  `mcs_view` の search と同じ instr 方式。10件まで＋履歴取得状況の注記）。
  いずれも receipt に本文を残さず、`_action_rows` は Discord の部品上限
  （`MAX_COMPONENTS=40`）に収まる分だけ4行目のボタンを出す。
- 朝の日次ダイジェスト（`notify_digest.py`、`daily_digest.enabled`、既定オフ）:
  tick の `_deliver` 冒頭（`--no-notify` でも）で `maybe_enqueue()` が
  `hour_jst` 以降・当日分が無いときに `kind='daily_digest'` の text intent を
  1件積む。前回の digest 行（`payload.date`/`until`）が「1日1回」の durable
  marker で、窓は前回の `until` から（初回は24h）。本文は enqueue 時に固定
  （ID と件数。`include_names` が true のときだけ患者名を ID に添える）し、送信時は `daily_digest` がオフなら
  `StaleSend` で破棄する。取得状況は `mcs_queries.coverage_gaps()`
  （incomplete ルームと理由コード・待機/失敗ジョブ・本文未取得・返信未取得）を
  使い、0件でも欄を出す。アラートは `signals.notify` がオンのときだけ、
  `request_overdue`/`request_aging`/`rx_period_expiry`/`rx_period_lapsed`
  を除外して型別件数。滞留行は open 3日超かつカードで一度も ack
  されていないシグナルキー（`STALE_ALERT_D`）を数える。
- 緊急度: `clinical_urgency.message_urgency()` が表示用の判定を集約する。
  現行 extract_llm の `urgency:high` は、根拠引用と本人・時点を照合し、
  臨床的な緊急性を示す根拠が残る場合に `llm` とする。`urgency:routine` は
  `None`（本文側の LLM 判定が語彙ルールより優先）、`urgency:unclear`
  は棄権でありクリアランスではないため `rule` 評価へ落ちる
  （extract_v1 の緊急候補も同じ根拠確認を通れば `rule`、通らなければ `None`）。
  ルール抽出だけが緊急とし LLM 判定が無い場合も、この確認を通す。カードの
  `📋 構造化` には `🚨 緊急度高`（LLM 判定）/ `🚨`（ルール照合）で表示し、
  テキスト通知の ⚠️ とシグナルの即時化も同じ判定を使う。ルール候補は
  本人・現在の文脈を照合し、否定・条件・仮定・過去などを除いてから表示する。
  生の抽出flagだけで表示せず、語句に基づく候補判定を臨床判断の確定とは扱わない。
  extract v5 から `high` は本文引用の `urgency_evidence`（最大2件）を
  必須とし、定位できない `high` は `unclear` へ降格する。
  Jev監査の不一致（`urgency_qc_disagreement()`）は表示注記
  `（監査では通常判定/判断保留）` と `notify_urgent` の抑止に効き、
  `vital_urgency` ポリシー（既定off）は閾値超過を `vital_flags`/緊急度へ
  反映する（`changes/extract-v5-urgency-evidence-unclear-1.0.16.json`）。
- `signals.med_exclude_names`（空白無視の完全一致）に列挙した薬剤名は
  med_change_no_followup の対象外 — 在宅酸素など調剤対象でない療法用。
- 通知階層: 即時 tier は `pharmacist_request_unanswered`・
  `discharge_notice`・`transition_reconciliation`。他は既定で digest
  tier — 未送信のダイジェスト intent に畳み込まれ、
  `signals.digest_interval_h`（既定24h）遅延で1通にまとめて送る。
  言及元の抽出が `urgency:high` のシグナルは即時化される。
  `signals.digest:false` で全件即時、`signals.tiers` で型ごとに上書き可。
- 人による却下: `mcs_view.py control signal_dismiss --confirm-human` に
  `{"project_id":…, "signal_key":"…", "reason":"…"}` を渡すと、理由・
  実行者付きの dismissed 遷移行を追加する。同じ証跡の間は再検出を
  抑制し、証跡が変われば新しい状況として再openする。任意の
  `"reason_code"`（`false_positive` / `already_handled` / `duplicate` /
  `out_of_scope` / `other`。`operation_contract.DISMISS_REASON_CODES`）を
  付けると dismissed 行に `dismiss_reason_code` として残る（それ以外の値は
  `bad_reason_code`。未指定の旧コマンドはそのまま受理）。カードの
  `🚫 却下` は選択式でこれを付ける。集計は読取り専用の
  `mcs_signals.dismiss_reason_counts(db)`（型別・理由コード別の件数、
  コードの無い旧行は `unclassified`。actor・自由文は出さない）で、
  `mcs_view.py signals` の `dismissals` に出る。却下は
  ラベルであり誤検知の証明ではない（「対応済み」で却下された真陽性もある）。
- 閾値の人承認変更: `mcs_view.py control signal_policy --confirm-human` に
  `{"project_id":…, "policy":{"req_age_days":14,…}, "reason":"…"}` を渡すと
  `signal_policy_v1` artifact として記録され、最新が有効値となる
  （キーごとに上限/下限あり。未承認なら既定値）。統計の閲覧が検知条件に
  影響する経路はなく、閾値は人確認コマンド経由でのみ変わる。
- 同一シグナルキーの再通知は最終送信から7日（既定値、policyで変更可）の
  クールダウンで抑制する — open/resolved を往復するシグナルが通知を
  連発しない。
- 通知は config の `signals.notify:true` を明示設定した場合のみ既存の
  notify_outbox 経路（kind='signal'、本文はenqueue時に固定）で送る。
  既定は通知なし。送信直前にフラグとシグナルの現状態を再検査し、
  無効化・解決・却下済みの intent は送らない。

### 抽出の誤り報告（カードの ⚠ ボタン）

カードの `誤りを報告` は preview → 本人確認を経て human command
`ops.extract_feedback`（`message_id`・カードが表示した `artifact_id`・
`field` = summary/urgency/meds/symptoms/requests/vitals/patient_context/labs/events/other・`reason`）を
enqueue する。runner は対象が今もその投稿の現行 extract_llm のときだけ
`extract_feedback_v1` artifact（message_id・artifact_id・hash・field・
note・actor・at）を追記する（違えば `extraction_changed`）。
extract_llm の `pending_pred` は「現行抽出を指す報告がある投稿」を
QC の単発再抽出と並列の条件で1回だけ再び pending にする（no-signal
prefilter は適用しない）。再抽出の成功時は新しい結果で、LLM 失敗時は
報告対象の内容を再発行して、どちらも `meta.human_fix`（`feedback_id`・
`applied`）付きの新 artifact に置き換える — 報告は現行を指さなくなり、
ループしない。`human_fix` 行は thin 再試行の対象にもならないので、
報告1件につき LLM 呼出しは最大1回。
v4 読取りモデルが現行の投稿には報告ボタンを出さない。読取りは
`mcs_queries.extract_feedback(db, project_id)`（`current` = まだ再抽出
されておらず、v4 も現行でない）で、`mcs_view.py qc --project N` の
`extract_feedback`（message_id・artifact_id・field・current・created_at の
新しい順20件。メモ・actor は出さない）に出る。統計への反映は未実装。

### 人が確認して依頼を登録・更新

**エージェントは内容・根拠・担当者・期限を提示し、人の明示承認を得てから実行する。**
機能の実装依頼や候補抽出だけを、個々の臨床依頼の登録承認と解釈しない。
`actor` と `--confirm-human` は信頼されたローカル境界での申告で、本人認証の仕組みではない。
依頼登録・変更はMCSへ送信せず、ローカル台帳だけを変更する。通知・自動完了は行わない。

承認内容をローカルの `approved-request.json` に用意する（hashは `evidence` の実値に置換）。
必須の `command_id` はUUID。投入前に決め、応答を受け取れなかった場合も
再送時には同じID・同じ内容を保持する（エラー時も既に公開された可能性はある）。
新規操作は `reason`（空白のみ不可、最大2000文字）も必須。理由は操作者・時刻・対象版とともにreceiptへ保存する。
更新前から残っている旧形式のキューは処理できるが、欠けていた理由を補作しない。

```json
{"command_id":"00000000-0000-4000-8000-000000000001","actor":"確認者",
 "source_message_id":456,"source_hash":"取得した64桁content_hash",
 "title":"人が確認した依頼内容","assignee":"担当者","due_date":"2026-09-30","reason":"原文を確認し対応が必要と判断"}
```

```bash
$PY mcs/views/mcs_view.py requests create --project 123 --confirm-human < approved-request.json
```

更新用JSONは `request_id`、表示された `expected_revision`、人が確認した最新本文の
`expected_source_hash`、`actor`、`reason`、`patch` を指定する。

```json
{"command_id":"00000000-0000-4000-8000-000000000002","actor":"確認者","request_id":1,"expected_revision":1,
 "expected_source_hash":"最新の64桁content_hash",
 "patch":{"status":"done","assignee":null},"reason":"実施結果を確認"}
```

```bash
$PY mcs/views/mcs_view.py requests update --project 123 --confirm-human < approved-update.json
$PY mcs/views/mcs_view.py receipt --project 123 --command-id UUID --payload-hash HASH
```

- 状態は `open / in_progress / done / cancelled`。人の承認による再開も可能。
  `patch` はtitle/assignee/due_date/statusのみ。省略は維持、担当者・期限のnullは解除。
  期限は実在する `YYYY-MM-DD`。担当者・期限を抽出結果から自動確定しない。
- 投入応答 `queued` は完了ではない。返されたcommand_id/payload_hashでreceiptを確認する。
  `applied`＝保存済み、`rejected`＝拒否理由あり、`not_processed_or_not_in_snapshot`＝未処理または未公開。
  投入中の `unknown / queue_durability_unknown` は公開後の保存確認失敗（終了コード1）。
  返されたID/hashで結果を照会し、同一ID・同一内容だけで再送する。
  ネットワーク障害や取込中は処理・snapshot公開が遅れる。ファイル消失だけで成功判定しない。
- 同じID・内容は同じ結果を返し、異内容の再利用は拒否。更新はrevisionと現行source hashの一致が必須。
  taskの確定時source_hashは不変。元投稿の編集後は `stale`、消失後は `source_missing` と表示し、
  人手項目は残す。編集後の更新は最新hashの確認が必要、消失後の更新は拒否。
  hashだけでは編集前の原文は復元できない。
- requestsとcommand_receiptsは同時commit。受付記録はactor・変更前後・結果を保存する。
  snapshotの `generation_id/generated_at` は公開世代と生成日時で、データ取得成功の証明ではない。

## 認証

- Bearer token = `localStorage['ngStorage-lastSessionToken']` (JSON parse 必須)
- 失効時: `auto_login()` が Keychain `security find-generic-password -s mcs-adapter`
  のパスワードを login フォームへ input event で注入 → submit click
  (Chrome ネイティブ autofill は DOM 駆動不可のため Keychain 方式)
- loginId はアプリが `storingLoginId` で永続化。空の場合は config の
  `mcs_login_id` で補完
- Keychain 登録は `mcs_setup init` の対話入力または環境変数
  `MCS_SETUP_PASSWORD` を使う。秘密値は標準入力で `security -i` に渡し、
  read-back 検証失敗時は既存の登録値の復元を試みる。実パスワードを
  コマンド履歴や argv に埋め込まない。

## 安全ゲート

- 既読化は fetch_state=complete かつ ledger commit 済みの患者のみ、
  snapshot timestamp (list_unread 応答値) を必ず送信 — 省略すると全既読になる
- API はリダイレクト拒否・proxy 無効。DL は許可済みorigin/CDNのみで、Bearerはorigin以外へ送らない
- エラーは構造化 (kind/status) — レスポンス本文はログに出さない
- 定期実行は患者本文・氏名を stdout/log に出さない。明示的な `mcs_view` の閲覧出力は例外。
- outbox は pending/failed/accepted + 指数 backoff — 通知失敗で喪失しない
- 途中送信の本文・添付・宛先が変わった場合は自動再開せず保留し、重複送信を防ぐ

## 検証

```bash
scripts/run_tests.sh                  # tests/ + integration/ の合成テスト全件 (test_hermes_* は hermes-agent が無ければ収集対象外。一時HOME・一時DB+スタブのみ)
make lint                            # CIと同じ範囲・ruff設定
```

テストは一時DBと通信スタブだけを使い、実MCS・Discord・Keychain・原本DBへ
アクセスしない。`integration/test_hermes_*` は hermes-agent checkout 上でのみ
収集される（合成テストのみの `test_mcs_*` は既定の `testpaths` と `scripts/run_tests.sh`
無引数実行で `tests/` と共に収集される）。
領域をまたぐ共通テストヘルパー（一時 Ledger の `make_ledger`・`ledger_fixture`）は
`tests/support/common_testkit.py` に置き、領域固有のものは各 `*_testkit.py` に置く。

一時領域にはpytest標準の`tmp_path_retention_policy=failed`を使います。
成功したcallの`tmp_path`は依存fixtureの終了後に解放し、module/sessionの共有領域は途中で消しません。
setup/teardownの失敗時に領域が残る保証はなく、runner終了時には一時HOME全体を削除します。
診断用ログ・JUnit・検証記録を残す場合は、一時HOMEの外へ保存してください。

### CIの並列実行と診断

`lint-test`は`tests/meta`・`tests/ops`と、それ以外の`tests/`・`integration/`の2群を並列で実行します。
`macos`は`tests/meta`と`tests/ops`の2群です。いずれも`ci/run_pytest_groups.py`から既存の
`scripts/run_tests.sh`を起動し、群ごとに一時HOMEと認証情報の隔離を維持します。
ディレクトリ単位の指定で既存の収集条件とファイル内の順序を保ち、片方が失敗しても全群の終了を待ちます。
1群でも失敗すればジョブは失敗です。SDK統合と安全ゲートの専用ジョブも維持します。

Python環境は毎回作成し、uvの依存取得キャッシュを使います。提供元設定やテスト結果、仮想環境自体は
キャッシュしません。`enable-cache: auto`により、タグのpushなどではキャッシュ復元を避けます。
詳細は[setup-uvの公式キャッシュ手順](https://github.com/astral-sh/setup-uv/blob/main/docs/caching.md)を参照してください。

各群のログ・JUnitと、遅い30件の実行時間を一時HOMEの外へ保存します。GitHub Actionsでは失敗時も診断ファイルを
7日間保持します。全体を再実行する前に、失敗項目と[pytestの実行時間表示](https://docs.pytest.org/en/stable/how-to/usage.html#profiling-test-execution-duration)で原因を確認してください。

### hosted CI を開始できない場合のローカル同等チェック

課金・利用上限・runner 障害で最終 SHA の CI job が開始できない場合だけ、
`scripts/development/ci_local.sh` で `ci.yml` の6 job（lint-test・hygiene・standalone-sdk・
incident-gates・macos・hermes-integration）を、その SHA の clean な clone で直列に実行します。
`lint-test`と`macos`の内部では、CIと同じ2群の並列実行を使います。
未commit・untracked の変更がある checkout では実行を拒否し、job・run 行・固定版はすべて clone 側のランナーと `ci.yml` から読みます。
CI が実行されて失敗した場合の代わりにはなりません。重いテストを含むため共有 slot を取ってから実行します。

```bash
scripts/development/ci_local.sh --out /path/outside/repo            # 既定はネットワークなし
MCS_CI_PYTHON=... MCS_CI_STANDALONE_PYTHON=... MCS_CI_HERMES_AGENT=... scripts/development/ci_local.sh
scripts/development/ci_local.sh --fetch                              # ci.yml の固定版を出力先へ取得
```

python・pytest・uv・hermes-agent の ref は `ci.yml` から読み取ります。出力先に job ごとのログ、
`summary.tsv`（状態・終了コード・開始/終了時刻・runs-on・host）、`meta.txt`（SHA・clean 確認・固定版）を残します。
前提が揃わない job は「実行不能」となり、全6 job が pass した場合だけ終了コード0です。
ubuntu runner 固有の差は未検証として残り、結果は CI 成功として記録しません。
`tests/meta/test_ci_local_runner.py` が job 名と run 行の `ci.yml` との一致を検証します。

### 台帳・通知見出しの性能回帰

`Ledger`が接続とtransactionを所有し、同じ保存呼出しで同一スレッドを更新する場合の
集約・projectionの無効化を一度にまとめます。この状態は次の保存呼出しへ持ち越しません。
患者名の任意索引は`ledger_schema.initialize`が作成します。名前がNULLの行を索引から除き、
全患者の列挙や履歴取得ジョブが名前順へ変わることを避けます。名前が未設定の患者も処理対象です。
既存のread-only snapshotやbackupに索引の存在を要求せず、schema世代は変更しません。

```bash
scripts/run_tests.sh tests/core/test_thread_projection_invalidation_batch.py tests/core/test_patient_name_index.py tests/notify/test_perf_cards.py
```

同じ合成入力と未処理状態で新旧を比較し、SQLの仕事量と観測なしの時間計測を分けます。
検索だけでなく挿入・更新・索引作成・DB容量・snapshot公開の費用も確認し、
未取得・保留・失敗を完了へ変えずに評価します。索引の回帰は同名・空名・Unicode・
アーカイブ済み患者と、初回履歴取得の順序を含みます。

### ローカルLLMのレーン/ubatch ベンチ（所有者機・承認した窓でのみ）

目的（提案5）: 背景レーンの serial（レーン2のみ）/ concurrent（レーン2+3同時）の比較と、
`-ub 128/256/512` の比較。`scripts/evaluation/llm_lane_bench.sh` が計測し、記録は数値のみ
（実投稿・応答本文は保存しない。生成した合成プロンプトは保存する）。

```bash
scripts/evaluation/llm_lane_bench.sh --phase e2e --i-stopped-the-workers --dry-run   # 計画確認（サーバに触れない）
scripts/evaluation/llm_lane_bench.sh --phase e2e --i-stopped-the-workers             # 稼働中サーバで要求を流す
scripts/evaluation/llm_lane_bench.sh --phase bench --i-stopped-the-workers           # サーバ停止中に llama-bench
scripts/evaluation/llm_lane_bench.sh --report                                        # 全 run の集計と採用規則の機械評価
```

- 停止対象: `ai.mcs.extract-drainer`・`ai.mcs.extract-drainer-2` を
  `launchctl bootout gui/$(id -u)/<label>` で止める（`launchctl print` が 113 を返す状態だけ
  通す。それ以外は exit 3）。bench phase はさらに `ai.hermes.llamacpp`（無ければ
  `ai.mcs.llamaserver`）を bootout する。bench は両サーバラベルの未登録（113）・プロセス不在（pgrep 1）・接続不可（curl 7）のすべてを確認する。タイムアウトや観測不能も拒否する。サーバ応答中の bench、停止中の e2e は exit 4。
- 所要時間の目安: e2e ≈ 15 分/‑ub（9 背景要求×2 block×2 mode + realtime、各要求最大 300 秒）、
  bench ≈ 15 分（4 回のモデル再ロード + pp 8192×5 反復×4）、合計 ≈ 35 分/窓 + サーバ再起動。
- 復旧: `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/<label>.plist` を drainer 2 件と
  サーバに行うか、`mcs_setup.py services` で再同期し、`launchctl print` と `/slots` で確認する。
- 比較条件: 同一モデル/量子化/`-c`/`-np`/`-fa`/`-ctk`/`-ctv`/schema/sampling/max_tokens を固定。
  04:00 の再起動 cron と 05:10 の更新チェックを避ける。hermes cron `MCS unread check`（10 分毎、
  レーン1）は止めず、混入は `foreign_busy_before` で記録する。ollama embedding が GPU を共有する点に
  注意し、5 分以上 idle 後に開始、温度・他負荷を揃えるため A B C A（512→128→256→512）順。
- **`-ub` の変更は `~/Library/LaunchAgents/ai.hermes.llamacpp.plist`（Hermes 所有）の編集であり、
  本 script は plist を編集しない。** e2e の `-ub` 比較は 512→128→256→512 の 4 窓で行い、各 run の
  `env.json` に記録された実 argv（`server_ub`）で照合する。llama-bench は候補の絞込みのみ
  （`--spec-type`/`-np` は指定できない）。
- 採用規則: baseline（`-ub 512` × serial）に対し保存済み有効結果/時間（代理値。保存段階の run.lock
  競合・QC は含まないので本番の worker 集計と併読する）が改善し、新着 p95・JSON 妥当性・timeout 率・
  RSS/swap が悪化しない候補のみ。新着応答は基準・候補とも全件HTTP/curl成功・JSON妥当・正常終了が必要。成功件数を持たない旧summaryも判定不可なので、承認した測定窓で再計測する。欠測は0扱いしない。最終判断は所有者。
- 出力先: `~/.local/state/mcs-quality/v1.0.27/llm-bench/<ts>/`（env.json・plan.json・prompts/・
  e2e/requests.jsonl・bench/・summary.json/txt）。
- drainer 停止中はヘルス監視の遅延警報が出得るが再起動はされない（`org.mcs.recovery --if-stale` は
  更新 marker がある時だけ動く）。テストは dry-run・ガード・report だけで実サーバに触れない。
