## 要点

- **判断が1か所にない**: クラウドとローカルのどちらで処理するかが、少なくとも7か所の判断の重なりで決まります。
  - `_cloud_mode`
  - `_contract`
  - `infer`
  - 送信前の確認
  - `guard_local_fallback`
  - `_needs_cloud_scan`・`cloud_summary_needed`
  - 品質確認の要否と worker の構成

  判断ごとに見る入力が違うので、同じ資料が「クラウド」「ローカルで恒久扱い」「永久保留」のどれにもなり得ます。
- **どちらでも処理されずに止まる経路がある**: 1単位で複数回送る資料が途中で失敗した場合、送信後にタイムアウトした場合、送信中に設定が変わった場合です。止まった単位は表示にも出ません。
- **一時的な理由でも恒久的にローカル扱いになる**: 送信枠の混雑・キーの一時的な読み取り失敗・その日の上限でも、資料が恒久的にローカル扱いになります。仕様と食い違います。
- **ローカルのモデル名で成果物が失効する**: ローカルのモデル名を変えると、クラウドで作った成果物と公開版がすべて失効します。
- **子が0本だと全体が止まる**: クラウドが on のとき、患者コンテキスト用の子プロセスが0本になると全体が止まります。ローカルだけの設定では、1単位ずつしか処理しません。

## 必ず直す（作り直しの前）

### M1. 複数回送る単位の途中失敗

- 該当: `patient_context_scan.py:64,110`、`patient_context_refresh.py:926-951`、`cloud_policy.py:954-971`
- 何が起きるか
  1. 1回目は成功し、2回目は 5xx で失敗します。
  2. 単位をローカルで最初からやり直そうとしますが、1回目の要求が `repeat_success` で拒否されます。
  3. 次の周回では `cloud_result_unsettled` になります。

  この繰り返しが永久に続きます。
- 対応
  - ローカル代替の可否は、「この単位の有料回答が採用されたか」で決めます。
  - 採用しなかった有料回答は `superseded_local` として処分し、会計を確定させます。

### M2. 一時的な理由で恒久的にローカル扱いになる

- 該当
  - `cloud_inference.py:400-402`（CloudBusy）
  - `extract_llm_provider.py:272`（キーの一時的な読み取り失敗）
  - `patient_context_refresh.py:838-848`（`local_route`）
- 何が起きるか: 一時的な理由でも、資料が恒久的にローカル扱いになります。作り直しの間は、送信枠を過去投稿用の子と共有するため、CloudBusy が起きやすくなります。
- 対応: 理由を「一時的」と「確定的」に分けます。
  - 一時的（先送り）: 送信枠・キーの一時的な読み取り失敗・回路・その日の上限
  - 確定的（ローカルへ）: 期間の終了・月の上限・所有者の停止・mode=off

### M3. 期間予算の終わりに途中の資料が止まる

- 該当: `patient_context_refresh.py:919-922`
- 何が起きるか: クラウドで途中まで処理した資料が `window_cap`・`expired`・料金の期限切れに当たると、先送りのまま解けなくなります。
- 対応: 確定的な理由のときは、mode=off と同じく最初からローカルで処理し、旧区間に処分を記録します。

### M4. クラウドが on で子が0本のとき

- 該当
  - `extract_llm_resident.py:146,179`
  - `cloud_backlog.py:266,401-408,744-751`
- 何が起きるか: メモリ不足やレーン2の停止で子が0本になると、クラウドでもローカルでも処理されなくなります。
- 対応: 生きている子がないときは、レーン3がローカル担当として処理します。

### M5. ローカルのモデル名が契約と公開判定に入っている

- 該当
  - `patient_context_refresh_state.py:238`
  - `patient_context_refresh_readiness.py:277-286`
  - `patient_context_refresh_sources.py:207,216`
- 対応: 契約から処理系の名前（ローカルの model と provider）を外し、成果物ごとに出所 `provenance {backend, model, profile}` を持たせます（U0）。P0-2 に含めます。

## 直した方がよい

1. **送信後のタイムアウト**（結果不明）: クラウドでもローカルでも処理されず、止まったままになります。費用は最大額で計上済みなので、ローカル代替を許可しても二重の請求にはなりません（決定 b）。
2. **送信中の設定変更**: 送信中に設定が変わると、破棄した回答が同じプロンプトを永久に塞ぎます。破棄した単位は、ローカル代替を許可します。
3. **止まった単位が見えない**（`patient_context_refresh.py:1407-1430`）: 理由のついた保留状態として保存し、`setup check` と状況表示に件数を出します。
4. **品質の修復がクラウド専用**（`patient_context_quality_controller.py:144,356,1417-1419`）: ローカルの設定では、60秒ごとの先送りを永久に繰り返します。
5. **品質確認の要否を mode で決めている**（`patient_context_quality_receipts.py:33`）: 成果物の出所で決めるようにします。
6. **mode を切り替えると成果物が行き来する**（`patient_context_refresh_state.py:241-243`）
7. **ローカルの処理量**: ローカルだけの設定では1単位ずつです。クラウド on でローカル代替をする場合は、最大4本の子が背景2枠を取り合います。
8. **走査も要約と同じ高い profile を使っている**: 走査も上位モデル・`max_tokens` 16384 で予約するので、その日の上限に早く届きます。

## 統一した経路の提案

- **U0**（P0-2 と一緒に、作り直しの前）: 契約から処理系の名前を外し、成果物ごとに出所を保存します。公開判定は「受け入れる出所」と照合します。
- **U1**（S2 ②要求記録）
  - 論理単位ごとに要求記録を集約し、ローカルの呼出しも費用0の記録として同じ kind に残します。
  - `decide_local` は「その単位の有料回答が採用済みか」で決めます。
- **U2**（S2 ③実行）
  - 処理先を決める純粋関数 `route(unit, record, availability, policy) -> cloud | local | defer | hold(reason)` を1つ作り、一時的か確定的かの分類はここだけが持ちます。
  - `CloudSendUnit` と `LocalSendUnit` は同じ interface にします。
- **U3**（S2 ⑦）: 品質の修復を送信ユニット経由にし、品質確認の要否は出所で決めます。
- **U4**（worker の構成）
  - クラウド担当とローカル担当に分けます。ローカル担当は昼1・夜最大2とし、レーン3は常にローカル担当として残します。
  - クラウドの子はローカルを呼ばず、処理をローカル担当へ渡します。
- **U5**: 短い資料のまとめ送り・走査用 profile の分離・作り直しの順序・止まった単位の表示。
