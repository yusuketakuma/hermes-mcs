# 患者コンテキストの拡張（時系列・新しい情報の優先・訂正・状態変化）設計（2026-11-15、所有者の決定待ち）

## 依頼

所有者の依頼は次のとおり。

- 患者コンテキストに含める情報を増やす。
- チャットから得た情報を効率よく配置する。対象は、時系列、患者ごとの時系列データ、新しい情報を優先する並べ方、更新されたデータの扱い、患者の状態変化。

この文書は、草案と、別のエージェントによるレビューを統合したものです。実装は、下の「所有者の決定」が済んでから始めます。

## 現状（要点）

- **公開版の中身**: 公開版 `patient_context_v1` は、LLM が根拠ID を12件まで選び、原文を引用する文の並びです。薬・バイタル・予定・タスクは、決定的な集計 `patient_rollup` が持ちます（`rollup_builder.py:654-955`）。🧾 は保存済みの rollup を使わず、開くたびに作り直します（`rollup.py:177-179`）。
- **状態の決め方**: 「書かれた日付で一意に決まるときだけ最新を採る」という判定が、7か所に別々にあります。
  - `patient_context_projection.project`
  - `rollup_builder.py:905-920`
  - `measurement_timeline`
  - `observation_series`
  - `care_event_timeline`
  - `extraction_context.format_state`
  - `semantic_relations`

  これらは、同じ対象とみなす単位、完了の条件、出力の意味がそれぞれ違うので、今回は統合しません。
- **背景分類**: 対象（entity）を持たない背景分類では、異なる報告が2件あると両方とも「不明（unknown）」になります（projection.py:493-506）。
- **根拠の選び方**: `select_facts` は5つの区分（現在・食い違い・予定・不明・過去）から1件ずつ交互に取ります（plan.py:46）。そのため、過去の記載も枠の約1/5を取ります。
- **訂正・削除の扱い**: 資料が1件でも訂正・削除されると、公開版の全体が表示されなくなります（readiness.py:322-323）。一方、読取り時に「無効になった根拠を含む文を外す」絞り込みはすでにあります（view.py:267-275）。
- **処理契約の範囲**: 処理契約には、`patient_context_plan`・`patient_context_projection`・`inference_dependency_loss` のファイルhashと、各版番号・モデルが含まれます。scan（資料ごとの調査）はこの契約全体に束縛されています。

## 設計

1. **作り直しの前に契約を分ける**（レビュー M1）
   - scan の契約（調査指示・chunk・分類と属性・引用の検証）と、要約の契約（選択・projection・並べ方）を分けます。
   - 要約側が変わっても A（まとめ）だけを作り直し、全患者の B/C 調査をやり直さずに済むようにします。
   - S2 設計 §6 の「受領行が62日で消えて一斉に失効する」問題も、作り直しの前に解決します。
2. **新しい情報を前に出す**（レビュー S1）
   - 各欄は決まった順に並べます。同じ対象の中では、臨床の日付（なければ投稿日）が新しい順にし、そのあと区分の順にします。
   - 状態を断定せずに見せる形にします。
     - 先頭に「最新の記載（MM-DD 投稿#N）: Y」を出します。
     - 「以前と異なる記載あり: X（MM-DD）」は折りたたみます。
     - 各行に「最終記載 MM-DD」を付けます。
   - 種類ごとの減衰（例: バイタル・症状は7日、ADL は30日、介護度は180日、診断・アレルギーは減衰なし）は、1ページ目に出すかどうかの切り捨てにだけ使います。値は設定で変えられるようにします。
   - `select_facts` を、区分の交互並べから重み付けに改め、過去の記載が占める割合を下げます。これは作り直しの前に入れます。
   - 同じ本文の転載は1件として数え、確認数は表示しません。
3. **時系列は読取り時の純粋関数で作る**（レビュー M4・M5）
   - 新しいモジュール `patient_timeline.py` が、`evidence()` と `build_rollup` の結果を受け取り、同じ snapshot から1画面につき1回だけ計算します。
   - 状態は自分で判定せず、既存の出力を読むだけにします。対象は clinical_state、`project_measurements`、`observation_series`、`intervention_states`、`discrepancies` の経時変化です。
   - 古い期間のまとめ方:
     - 30日以内: すべて。
     - 31〜180日: 月ごとに、最初と最後の値と件数。
     - それより前: 最後に分かっている状態だけ。
   - まとめた結果は保存せず、毎回、現在の hash に結び付いた資料から作り直します。こうすれば、まとめの中に削除済みの値が残りません。
   - 上限は、大量投稿の合成 fixture で時間を測ってから決めます。
4. **訂正・削除は項目単位で外す**（レビュー M2）
   - 公開版の一致判定を、「全体にかかわる部分（範囲・契約・権限・取得状態）」と「資料ごとの署名の差」に分けます。
   - 変わった資料の根拠と文だけを外し、既存の barrier 付きの再 projection で区分を付け直します。
   - 画面には「訂正があった記録 N件は再確認中」と出します。新しい公開版や QC 判定は作りません。
   - 訂正のときに3時間の間隔を免除することはしません（レビュー S4）。
5. **B5 には読取り時の絞り込み後の内容を渡す**（レビュー M3）
   - 試行ごとに、絞り込んだ後の view からブロックを作り、既存の `extraction_context` の frame（binding・digest・試行の固定）を広げて渡します。
   - 直近30日に、外している資料が1件でもあれば、B5 は使いません。
   - TOTAL_MAX 1200 字の内訳を明記します。
6. **全体像の1ページ目**（レビュー M6・S2・S5）
   - 1ページ目の内容と上限:
     - 最近の記載の変化: 5件まで
     - 現在の薬: 15件まで
     - アレルギー・副作用
     - 次の予定: 今日以降だけ。過ぎた予定は「以前の予定」に移します。
     - 未解決の課題
   - 背景は2ページ目以降に出します。1ページの文字の予算は3200字です。
   - 薬・アレルギー・予定・課題は、患者コンテキストの有効・無効に関係なく、決定的な処理から表示します。LLM の欄だけ「作成中」とします。
   - アレルギーと薬は、記載が見つからなくても行を省略しません。「記載が見つかりません（取得範囲…）」と出します。
   - 例外のときは固定の失敗文を出し、古いまとめは出しません。
7. **状態変化**（レビュー S3）
   - 既存の signals（退院・移行時の照合・処方変更後の未フォロー・処方期限・処方変更後の症状）と、入力関数を共有します。
   - 足す変化:
     - 処方元・主治医・薬局の変更
     - 剤形・一包化などの服薬支援の方法
     - 服薬管理者・保管場所
     - 残薬・アドヒアランスの記載
     - 食形態・嚥下
     - 新しいアレルギー・副作用の記載
     - 医療処置・機器の開始と終了
     - 麻薬の開始・増量
     - 比較できる腎機能・体重の2点（判定はしません）
     - ACP・療養場所の記載
     - 入院中
   - 見出しは「最近の記載の変化」とします。「以前 → 新しい」の矢印は、日付で順序が一意に決まるときだけ使います。
   - 臨床の判定はせず、「変化なし」とも書きません。
   - 並びの基準（投稿時刻か臨床日か）を表示と仕様に明記します。
