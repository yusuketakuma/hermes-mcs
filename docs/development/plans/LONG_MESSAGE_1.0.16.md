# 長文・高密度投稿の処理改良（1.0.16）

## 目的と範囲

長文に限らず、短い本文に多くの薬剤・観測値・背景情報が並ぶ投稿でも、出力上限後の分割を待たずに適切な処理単位を用意する。ローカル実装・合成検証・必要な既存の私有一時DBでの評価までを範囲とする。本番DB・設定・既読状態・通知・配備・外部公開は変更しない。

## 作業と所有範囲

1. 抽出担当: stdlibのみの共通分割関数とlegacy LLM経路を実装する。見出し・段落・文・リスト行を優先し、全文の連結一致を保証。密度から出力量の目安を使い、候補のない自由文も処理対象に残す。MAX1600・TIMEOUT300・deadline・admissionは維持。初期layout・分割履歴・完了checkpointの束縛を整合させ、batchが密度判断を迂回しないようにする。出力は不要な空欄や説明を抑え、引用・主体・否定・時制の契約を維持する。
2. semantic担当: 現行canonical v1/v2/v4のatom/manifest/所有・依存context・証拠範囲・PASS公開と監査を維持し、同じ分割判断へ接続する。分割契約更新はcache世代へ反映し、完了区間再利用と未完非公開を維持する。
3. 表示担当: 本人限定の既存患者まとめに処理中・完了・要確認の状態を短く表示する。現sourceに束縛したcheckpointだけを計数し、処理済み件数を抽出項目数や臨床的完全性と混同しない。共有通知へ追加しない。必要な完全合成画面例と回帰を更新する。
4. 親: 呼出元/共有契約/差分を統合し、仕様・日本語changes・生成文書を更新する。関連テスト、CI範囲lint、安全ゲート、生成・画像・記録チェックを実施する。

## 受入条件

- 空白・改行・Unicodeを含め全文が欠落/重複なく覆われる。長い一文は安全上限内で処理し、関連する主体・見出し・隣接情報は参考情報として保持し、参考だけを対象本文の証拠にしない。
- 高密度投稿は初回呼出前に分割でき、低密度の短文へ不必要な呼出を増やさない。見積りはヒューリスティックでありtoken厳密値や性能保証と扱わない。
- 否定・過去/予定・家族/他者、薬剤と用法、症状と対応、見出し依存を完全合成で検証する。
- 中断/length/修復lengthで完了済み区間を再推論せず、編集・モデル/prompt/分割契約差分・壊れたcheckpointは再利用しない。
- 全文未完を完成結果として保存・公開しない。正しい空結果は完了区間として扱う。
- UIは本人限定、状態を文字で明示。古い情報・未確認・失敗を完了と表示しない。実SDK/実画面/臨床的精度の未検証を合成成功と区別する。

実装後に追記する。実投稿の原文・患者名・識別子・実値は本記録・fixture・外部へ含めない。

## 追加承認とmain hotfix（2026-10-07）

ユーザーが、本人以外を本人と誤認するアラートの修正、元スレッドへの追加投稿、薬剤師向けUIUX、遅延解析の既存投稿更新/更新中表示、現在ブランチ全体のmain統合と即時適用を明示依頼した。さらに統合後の差分影響を重点調査して修正する。外部push/公開は別途扱う。

- B:原文scope guardと全urgency呼出を整合。family/other/混在/否定/過去/予定/条件を完全合成で再現し本人実兆候を維持。
- C:患者アラートを既存verified threadのnative delivery/grant/receipt経路へ移す。不確定scopeでchannel fallbackせず保留。遅延更新は同message/thread IDを再利用し別投稿を増やさない。患者元threadを持たないsystem alertsは既存専用targetを維持。
- A:短い原文根拠/主体/投稿日/AI判定観測/原本導線、解析更新中と要確認の区別。さらにrollup/clinicalvalues/signalの他者混入を共有guardで修正し、旧cache読取りも保護。
- 親:全文分割の句点境界を修正（前区間に句点を保持）。branch/main状態と導入形態/所有済みサービスを確認。main統合前に必要検証、適用前に私有backupと既存停止/再開手順を使い、統合後に差分影響の再検証と実機反映を確認する。既存main/worktree変更を消さず、共有GWのownerを確認する。

初回全体検証は8889 passed/3 SDK skip、7 failures。4件は実行中source変更を含むingestのcode_changed/lock検証であり、最終source固定後に確認する。3件のsemantic失敗は共有text_chunksが句点を次区間へ送る境界バグを再現し、cut=index+1で根因を修正した。関連48件成功。テスト期待を弱めていない。

事前分割の中間ビルドを同じローカル投稿で私有一時DB評価し、8初期区間・16呼出・length1回・703.9秒で1slice中に完了、最終JSON保存/読み戻し一致。旧局所分割は934.5秒/2sliceだった。キャッシュ条件・分割粒度が異なり、性能改善率・臨床精度の保証と扱わない。背景項目は18対21、詳細属性0対2と件数も異なるので、件数だけで網羅性向上を主張しない。後の句点境界/アラート修正を含む最終版の実精度評価ではない。本文/患者名/識別子/実値は記録/fixture/外部送信へ含めず、本番DBへ書き込んでいない。

## 最終統合前の影響確認

アラート主体/sourcethread/遅延更新/集約の横断一式で9003件成功・3SDK skip、28件の失敗を捕捉した。旧signalがchannel rootを作る前提のfixtureは元sourceのgrant/receipt/thread/body証明へ移行し、確認・却下・担当・人承認のassertを維持した。実不具合はdb=None/minrow/旧schemaのreadcompatとplain送信先未設定の判定順序で、source/restoreの安全条件を弱めず修正した。関連276/86/80/100件と後続70件が成功した。影響主要6領域は6665件成功・3SDK skip、最後1件のCLI欠如優先順位を上述70件で再確認した。無変更領域は直前の一式成功結果を再利用する。
