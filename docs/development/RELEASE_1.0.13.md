## 2. コマンドの契約

新しい統一入口はローカル実装済みで、install/update/setup/doctorの合成回帰を検証した。
実機へのインストール・サービス適用は未実施。既存の実行可能な入口を保持し、
`doctor`は`mcs_setup.py doctor`の診断を再利用する。

| 統一入口 | 再利用する実装 | 境界 |
|---|---|---|
| `mcs install` | `install.sh` | インストール後の初期設定とは分離。初回はlauncher未導入なのでrepo内のbootstrap入口も提供 |
| `mcs update plan` / `mcs update apply` | `scripts/mcs_upgrade.py`・`mcs_update.py` | planは読取り専用。apply/reinstallで停止・backup・更新・rollback。外部standalone applyの未対応を隠さない |
| `mcs setup` | `mcs_setup.py init`・`services` | initが行う最終チェックを重複させない。秘密入力は本人端末、既存設定は保持 |
| `mcs doctor` | `mcs_setup.py doctor`・`check` | 通常はローカル読取り専用。実サービスprobeは明示した範囲だけ。修復・再起動・既読化・送信は行わない |

installerが実行可能launcherをPATH上に配置する。repo直下の`mcs/`はソースディレクトリなので
同名ファイルで上書きしない。coreに外部依存を追加しない。
診断は人向け要約と安全な機械可読結果を返し、秘密値・本文・患者/利用者ID・生応答を含めない。
終了コードは正常/警告0、阻害1、引数不正2を基本とし、既存入口との互換を確認する。
診断で判明した問題の修復はplan・人承認・receiptの既存経路へ分ける。

共有スキーマ・統計REGISTRY・通知境界は同時に競合編集しない。
独立した実装は並列で進め、完了した担当へ次の着手可能タスクを継続投入する。
統合失敗や依存変更で計画の前提が変わった場合は、その箇所をレビュー・再設計し、
担当範囲と受入条件へ反映して実装を続ける。全員終了待ちの一括バリアは置かない。
不足した前提がある項目を別版へ送るときはユーザーの範囲変更が必要。
実API前提が取れない場合は不明と阻害条件を残す。既定offだけで完成とはしない。
