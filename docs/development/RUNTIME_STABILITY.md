# 稼働ログから見つかった改善項目の対応

2026-11-03の調査で挙げた22項目と、過去の障害記録4群を追跡します。
この文書はコードと合成テストの対応表です。本番での解消や性能改善を示すものではありません。

## 今回の実装

- クラウドワーカーの総数をメモリに応じて計算し、処理結果の精算後に余剰ワーカーを終了します。進行中の処理を外から強制終了しません。
- クラウドの処理段階、時刻、経過時間、固定の延期理由を記録します。精算に失敗した場合は再試行間隔を延ばします。
- 抽出準備で止まる理由を分類します。未確定課金のある対象を保護する既存のclaimと選択処理を維持します。
- 通知の証跡を5分ごとに照合します。現在のワーカーが所有する未終了処理は対象外です。不明な送信を自動再送しません。
- ルール抽出、LLM、薬剤照合、集計、シグナルへ時間を配分します。薬剤照合は同じ回のLLM抽出後に行います。
- 通知診断を重い全体集計より先に行い、収集終了時の処理時間を分けて記録します。
- 収集結果の更新が遅れている間も空きディスクを観測し、容量低下と回復を判定します。

## 全項目の対応

「既存」は今回の候補に含まれる既存コードを指します。本番で読み込まれたことを意味しません。

| 調査ID | 項目 | コード側の対応と残る確認 |
|---|---|---|
| 01 | クラウド抽出の未送信反復 | 既存の固定未送信分類・有限claim・選択位置の更新を使用。今回は準備段階の分類を追加。配備後に進捗を確認する |
| 02 | 生存しているが進捗が分からない | 処理段階の開始と進行中の経過を追加。時刻とPIDを記録する |
| 03 | 課金結果の未確定 | 既存の確定証跡保全と再送拒否を維持。外部の結果が不明な記録は照合が必要 |
| 04 | 通知の長期保留 | 稼働中の定期receipt照合を追加。既存の人承認による解決経路も維持 |
| 05 | カード更新失敗・送信部分の不明 | 定期照合と通知診断の優先実行を追加。実際の対象投稿の照合は別途必要 |
| 06 | semantic/QCの長期滞留 | 既存の優先度・巡回選択・有限claimを維持。処理待ちの理由を追加し、配備後の減少傾向を確認する |
| 07 | 現行抽出の適用率不足 | 現行契約の検証を維持して再抽出を進める。古い結果を現行扱いする緩和はしない |
| 08 | ディスク不足 | ヘルス監視が最新容量を独立して確認する。既存ファイルの削除や保存先変更は行わない |
| 09 | 抽出準備の拒否理由が粗い | 期限、ソース変更、クラウド無効、プロファイル、薬剤参照、コンテキスト、DB読取りに分類 |
| 10 | チェックポイント・コミット拒否 | 既存のチェックポイントとソース検証を維持。確認できない結果は公開せず、既存の固定理由を記録する |
| 11 | semantic延期理由が不明 | 候補に含まれる準備段階と送信前拒否の固定分類を使用 |
| 12 | writer lockの競合 | 既存のHTTP中のロック解放を維持。新しい進行ログで待機段階を確認できるようにする |
| 13 | 集計・シグナルの延期 | 前の処理に時間の上限を設け、集計の後にもシグナルの時間を残す |
| 14 | 収集終了処理の時間が長い | コマンド排出とsnapshotの計測を分離。検証を省略せず、遅い段階を特定する |
| 15 | 薬剤照合の途中終了 | 時間を確保し、未照合と検査済み不一致を区別する既存UIの回帰を追加 |
| 16 | 取得・メタデータ更新の遅れ | 既存の巡回・取得上限・延期理由を維持。取得間隔やサーバーへの負荷は増やさず、実運用で最古更新時刻を確認する |
| 17 | 通知診断の観測制限 | 同じ30秒の全体枠内で、通知診断を先行し各読取りを制限する。期限切れはunknownのまま報告する |
| 18 | 常駐数・メモリ使用 | 総目標数と増減の猶予を導入し、精算後の待機境界で縮小。実メモリ使用量の低下は配備後に測定する |
| 19 | 改善コードが本番へ未反映 | 専用ブランチで既存修正と今回の追加を一緒に検証。merge・配備は今回行わない |
| 20 | semanticのshadow設定 | 比較評価の設定を維持。結果の公開方式の切替は別の要件判断であり、自動変更しない |
| 21 | バックアップの方式・容量 | ローカル検証と保存クラス別の既存診断を維持。保存先や保持方針を決めずに削除・外部保存を有効化しない |
| 22 | 時刻・処理段階が不足するログ | 抽出とクラウドのイベントへ時刻・PIDを追加し、固定理由を記録。設定値や投稿本文を出力しない |

## 過去の障害記録

| 障害群 | 対応 |
|---|---|
| carryの精算失敗反復 | 再試行間隔を最大60秒まで延ばし、確定済み証跡を保持する |
| specの未対応キー | 候補に含まれる許可キーと拒否コードの修正を使用する |
| Slackの文字数拒否 | 既存のUTF-8・エスケープ後の分割と、送信されなかったことが確定した拒否だけの再計画を使用する。バイト上限なしの場合の数値比較を修正する |
| 添付編集の事前検証保留 | 既存の参照・サイズ検証を維持。保留を成功へ変えず、照合と既存の解決操作を使う |

## 適用と評価

更新後は、抽出・収集・ヘルス監視を所有する常駐サービスと、使用中の通知アダプターを再起動する必要があります。
Hermes接続ではgateway、LINE WORKSの独立接続では独立アダプターへの反映が必要です。

配備後は、同じ時間幅で完了数、延期理由、最古待機時間、通知の未確定数、メモリと空き容量を比較します。
結果不明の実送信、薬剤辞書の承認、shadowの公開方式、バックアップ保存先は、自動変更の対象に含めません。


## 検証結果

- 収集・ヘルス監視・共通通知・Slack・抽出の関連一括検証は1,730件中1,721件が通過しました。失敗した9件は、旧CLI終了コードのテストとSlackの同じ上限比較に起因する8件で、修正後の対象テストは通過しています。
- 修正箇所と追加した時刻情報の関連検証は219件を実行しました。時刻スタブの不足による1件を補正し、再検証は通過しています。
- 起動時のロック・復元保護35件、初期の追加回帰、静的検査、安全ゲート10項目、生成文書の整合を確認しました。全体suiteと実SDKのCIは実行していません。
- 独立した担当が差分をレビューし、終了待ち・薬剤照合の順序・ディスク回復・現在の送信claim保護の指摘を修正して再確認しました。Devinへも公式agmsgでレビューを依頼していますが、この記録時点では返答を受け取っていません。
