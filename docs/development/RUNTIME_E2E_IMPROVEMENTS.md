# 追加改善6項目の実装と適用範囲

対象は`ceed71e3`以後の追加改善です。前回の22項目と、実送信の結果が不明な記録を自動的に解決したとは扱いません。
この記録には患者データ・実投稿・秘密値を含めません。入力例は完全合成です。

## 1. 薬剤抽出の精度

現行の検証関数へ合成入力を渡し、次の状態を再現しました。

- 「本人のキラナ5mgは継続です。服用量は記載されていません。」に対する`dose=5mg`が、不確実扱いにもならず残ります。
- 「本人はキラナを1回2錠、1日2回服用しています。」で頻度が欠落した出力は、不確実扱いのまま残ります。
- 家族の服用と本人の非服用が同居する文では、対象者の欠落した出力が不確実扱いのまま残ります。

規格・服用量・頻度・服用者・否定・予定の根拠を、薬剤に結び付いた本文から検証します。既存の修正依頼と呼出回数の上限を使い、欠落を修正依頼へ確実に伝えます。曖昧な項目を推測で確定したり、家族の薬を本人の薬として表示したりしません。
受入では、正しい既存出力を維持し、明示された用量未記載との矛盾を拒否し、明示された頻度と服用者を持つ正解出力が保存・表示まで通ることを確認します。

## 2. 保存・表示までの評価

既存の`operational_progress.pipeline_progress`と`semantic_metrics`を再利用します。
ジョブ完了、現在有効な保存結果、公開snapshot、カード本体の配送、本文・添付を含む全体配送を分けます。
旧設定、ソース変更、不完全結果を有効完了へ含めません。並行したLLM時間の合計を、実経過時間として報告しません。
観測時刻と測定区間を持たせ、取得不能や区間の結合ができない場合は理由を明示します。

## 3. 長期保留の解決支援

`notify_scope.health_cards`の既存の上限付き一覧へ、部分の種類、状態、固定の理由、経過時間、必要証拠、既存の次操作を追加します。
カード本体は既存のカード解決操作へ、本文・添付は既存のpart planへ案内します。
承認用payloadの形式は変えず、説明を別の表示用情報として保持します。実送信の成否不明を自動解除しません。

## 4. 会計集計の重複処理

完全合成のSQLiteで、前月予約に対する当月結果400件と無関係な履歴1000件を使った場合、`_tally`は808回のSQLを実行しました。既に一括化されている`usage_report`は同条件で5回でした。
新規の予約IDを既存の一括取得経路へ渡し、重複・不正JSON・時刻・保持期限・予約との対応の検証を維持します。
また、新規会計行がない場合の同一snapshot内の末尾再hashを避けます。最初の完全な整合検証は維持し、件数や最大IDだけで改変検査を代替しません。
受入は合成DBのSQL回数・走査回数と、不正・削除・同時変更・rollback・月境界の既存回帰で確認します。

## 5. snapshotの負荷

既存の変更検知と再利用は機能しています。合成DBの単発計測では、1回の公開にcopyとquick_checkは各1回でした。
本番で観測した長時間処理の内訳は未確定です。copy・verifyに加え、署名、marker、公開時のfsync・replaceと全体時間を既存の計測へ追加します。
検証を省略せず、未測定の高速化を主張しません。並行呼出しの重複公開は合成スケジュールで再現できますが、通常の収集は既存run.lockで直列化されるため、本番の原因とは区別します。

## 6. 新着と過去分の処理保証

既存のarrival/backfill/QC別の巡回・処理率・条件付きETAを使用します。
現在の世代と設定に結び付いたジョブの最終完了、取得からの待ち時間、最終巡回時刻を既存statusへ出します。
古い投稿日時を待機開始とせず、今回の取得時刻と区別します。未定義の時間目標を新たな保証値にせず、目標未定義と観測不足を明示します。
