# 添付OCRの処理経路と残る制約

対象は1.1.2向けの開発候補です。本番反映・実データ変更・実サービスへの送信は、このレビューには含めません。

| 範囲 | 対応と条件 |
| --- | --- |
| 導入・更新 | 専用Python環境と必要なモデルを任意導入し、既定は無効。コアに外部依存を追加しない |
| OCR実行 | 通信を禁止した別プロセスで画像・PDFを処理。容量・ページ数・画素・出力・時間を制限し、停止時に子プロセスを回収する |
| 表の読取り | 行と列区切りを残し、複数の見出しが混在する欄を一つの医療項目として確定しない |
| 原資料 | 添付・患者・ページ・原文のhashを持つ独立した資料。投稿本文や投稿者の発言へ置き換えない |
| 同一性と失効 | 同じ添付の親本文編集や実体の通常pruneでは解析を再送しない。削除・撤回・所属違い・別内容は現行資料から除外する |
| ローカル解析 | 共通の抽出・引用検証・品質検査・実行枠を使用。途中のchunkを保存し、次回に再開する |
| クラウド解析 | ローカル結果の保存後に、既存の患者範囲・履歴承認・予算・共有枠で追加解析する。承認範囲の変化と原文の変化を区別する |
| 課金と復旧 | 受信した有料応答を私有journalへ保存してから会計へ反映。成果を採用できない場合も応答を保持し、再開時に同じPOSTを重ねない |
| 結果不明 | 予約しか残らない送信はunknownとして閉鎖する。未送信と推測して再送しない |
| 保存期間 | 保存済みOCR推論が参照する会計証明と未採用応答を、通常の会計削除から保護する |
| チャット | 原文の下に文字起こしを分け、長文は既存の本文表示で開く。カードは文字起こしと🖥・☁の進捗を短く表示する |
| 添付配送 | 元のファイルと既存の配送計画を再利用する。OCR更新を理由にファイルの再アップロードや別のメインチャット投稿を追加しない |
| 患者コンテキスト | 未処理・失敗・解析保留の資料を完了扱いにしない。画像だけの投稿と空ページにも明示的な完了条件を持たせる |
| 出典表示 | 添付原本のsource keyを統合・表示まで保持し、親投稿・添付・ページを示す。別資料の同文をmessage ID 0としてまとめない |
| 医療情報 | 引用・対象者・否定・明示日付を保持する。投稿日時を資料内の診療日時に転記せず、薬剤規格やPCA値から投与量を推測しない |
| 監視 | OCRの失敗・保留・監視記録の欠落を区別する。backoff中の失敗を正常0に戻さない |
| 外部export | OCR資料を外部exportへ追加しない。既存の読取り権限とチャットの配送先を維持する |

関連する合成テストでは、実際の抽出・CloudUnit・会計処理を使い、モデル応答とHTTPをスタブへ置き換えます。
実モデルの精度や実チャットの描画を確認した証拠とは区別します。

## 未対応・未検証の範囲

- 薬剤言及履歴・服薬管理の専用表示・測定値の時系列は、必要な解析と原文照合が完了したOCR資料を採用します。保留・失効・対象者や日時が不明な資料を、一覧の網羅性として扱いません。
- 薬剤・症状は既存の出典付きfact変換を使い、検査・バイタルは共通検証から観測値を渡します。記載条件が不足する資料は未確認に残ります。
- OCRは医療専用に追加学習したモデルではありません。実資料の正解付けによる臨床精度、手書き、チェック欄、機器画面の精度は、この合成テストでは評価できません。
- モデルの公開コードは固定commitですが、モデルキャッシュのrevisionを全て固定する仕組みはありません。厳密な精度比較では、使用したweightのrevisionも別途記録する必要があります。
- OCR監視は最大256件を調べます。それ以上のキューは全件正常と断定せず、未観測を残します。
- 実Slack・Discord・LINE WORKSの画面、本番の処理速度・メモリー使用量・全体suiteは未検証です。

## 責務分離と表形式の更新

`attachment_inference`は実行と書込みの制御、`attachment_extraction`は原資料に対応する結果の検証・保存・読取り、
`attachment_inference_checkpoints`は途中結果の再開、`extraction_provenance`は推論元の証拠検証を担当します。
実行中のソースhashは実ファイルの値を維持します。固定した互換性定義は、レビューした責務分離だけを旧OCR推論の識別値へ対応させます。
未知の変更やモデル・版の変更を、旧結果の再利用許可へ広げません。

表の列位置修正は挙動の変更なので、互換性定義では旧hashに置き換えません。OCR処理形式を更新し、旧資料は現行の原資料から除外します。
元ファイルが残る資料だけを新形式で読み直します。課金済み応答の精算と臨床結果の採用は別に判定します。
通常チャットの保留記録やsemanticの候補識別にも実ソース変更が反映されるため、既存の再評価条件を維持します。

## 再点検で修正した連携

| 範囲 | 修正と条件 |
| --- | --- |
| 単一原資料取得 | source keyから対象資料だけを取得する共通経路へ変更。一覧取得と項目の検証・解析状態の付与を共有する。別患者・失効・不正キーは採用しない |
| 検査・バイタル | 保存済み`labs`・`vitals`を共通検証で観測値seedへ変換。原文の本人・実施済み・日付・単位・引用を照合し、文書作成日・生年月日・予約日等を測定日にしない |
| PCA | 紹介状と同じ読取りスナップショット・現行性・全ページ解析完了の検証を使って、未確認候補を経過へ表示。続きページの文脈を補わず、推奨値・投与量・終了時刻を算出しない |
| OCR誤り報告 | 薬剤詳細のページ別ボタンから、人承認・理由・receiptを通して現行の原資料・解析を指定。対象ページだけを再解析し、原文・旧解析・課金証拠は上書きしない |

共通読取りは`ocr_document_reader`、資料別投影は`referral_reader`・`pump_reader`、
測定値の受渡しは`attachment_observation_seeds`、OCRの訂正境界は`attachment_feedback`が担当します。
新しいDB形式や追加の外部依存は導入しません。

測定値seedの採用後も、既存の系列化条件を満たさない複数段落資料は未確認として残ります。
同じ引用に測定日と別用途の日付が混在する場合も保留します。正確な対応を推測して確定しません。
OCR誤り報告は文字起こし原文の編集ではなく解析の再実行です。画像認識そのものの誤りを自動で訂正する機能ではありません。

今回の変更は振る舞いが変わるため、旧責務分離の互換証拠には追加しません。
新しいsource hashで旧解析を再評価し得ます。人の報告を含む再解析は、実際の訂正理由を既存のfeedback経路へ渡し、
送信制御・予算・unknown時の再送禁止は維持します。旧会計・応答・journalを消したり、未送信と偽って再送したりしません。

配送側では、手動OCR後のチャット反映は次回の更新処理を待ちます。LINE WORKSの追記回数制限、
配送計画の256部品上限も維持します。受理可能なOCR原文でも、長さや添付数によって全量を配送できるとは限りません。
クラウド追加解析には患者範囲の履歴承認と、新規・編集後の待機時間を含む既存条件が必要です。

## ローカル・クラウド連動の修正

| 指摘 | 対応 |
| --- | --- |
| 契約更新後に旧クラウド応答を復旧できない | ローカル結果の採用証拠とクラウド要求の識別を分離。旧保存証拠、現在の原資料と範囲、実際の送信内容、確定会計の一致だけを再利用する |
| 同文の別ページが再送防止で相互に止まる | 両方の原資料と所有証拠を検証した場合にだけ、別の資料として照合。帰属不明は保留を維持する |
| クラウド復旧失敗でローカルも停止 | ローカルは継続し、クラウド側の送信は閉じる。復旧待ちを監視に表示する |
| OCR例外で通常クラウド抽出へ譲らない | OCR試行の前に交代を記録し、例外があっても次回は通常抽出へ譲る |
| OCRが新着枠を使い、メモリーを確認しない | ローカルは背景枠と共通のGPU順番待ちを使用。OCR本体も起動前にメモリーを確認する |
| 対応外添付を未解析に数える | 対象外の状態定義を共有し、除外件数と保留件数を分離する |
| 薬剤0件のページを報告できない | 本文表示から解析済みOCRページを開き、既存の人承認・理由・receiptを使って報告する |
| 収集成功時の1添付・1ページだけでは進まない | 独立した毎分ジョブで、単一起動・総予算900秒の範囲内で待ち行列を処理する |

ローカル・クラウドの完了と、OCR原文が保存できたことは別々に判定します。
処理量の固定上限を外しても、モデルの応答速度や実機の処理件数を保証するものではありません。
詳細な照合条件と状態遷移は[OCR処理の連動仕様](../specs/ocr-processing.md)を参照してください。
