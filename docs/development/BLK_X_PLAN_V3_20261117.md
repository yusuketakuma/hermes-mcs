## 0. 要点

1. **上げる版は5つ。** `LLM_EXTRACT_VERSION` 11→12、`RULE_VERSION` 29→30、`PATIENT_CONTEXT_VERSION` 4→5、
   `semantic_projection.PROJECTION_VERSION` 7→8、`semantic_jev.REGISTRY_VERSION` を X9 の commit の日付へ（O8 の label_ja 日本語化のため。上げるのは O-10 の確認の後）。
   あわせて走査入力の署名の印 `patient-context-scan-items/1`→`/2`、`clinical_allergies.FIELD_GENERATION = 12` を置く。
   `CURRENT_VERSION='1.0'`（O1）、`PLAN_VERSION=2`、意味解析の5つのプロンプト、`SCHEMA_VERSION`、`POLICY_VERSION`、`HOLD_EPOCH`、走査契約の `CONTRACT`・`"facts": 2`、
   `SUMMARY_CONTRACT` は変えない。版の数値・pin・基準値・文書・`changes/` は統合ブロック X9 だけが書く。
2. **O8 は決定済みとして実装する。** QC の独立化（`semantic_qc._qc_questions` の緊急度の質問から「（抽出側の分類: …）」を外す）と、
   P 系の `label_ja` の日本語化を今回入れる。コードでは `label_ja` は Jev へ送られず（Jev の要求は `instructions` と `criteria` だけ）、
   ローカルの要約プロンプト（`semantic_llm._verdicts_brief`）と `semantic_fact_stages` の集計にだけ入る。成果物を失効させる鍵は `REGISTRY_VERSION`（`bundle_fingerprint` に入る）なので、上げると
   **意味解析の要約と Jev の判定が全件やり直し**（区分 C2＋C3）になる。ただし**上げるだけでは job が投入し直されない**（C2）ので、X10 で `execution_generation` に `REGISTRY_VERSION` を入れる。
   要約は患者コンテキストの走査が読む補助要約なので、**配備前の投稿の意味解析を S3 の前に終える**（N_sem＝0 が S3 の条件。§3.4）。
   「全件やり直し」は所有者が O8 を決めたときの前提（「label_ja で Jev が失効する」）と事実が違うので、上げる前に所有者に見せる（O-10）。
3. **「作り直しは1回だけ」を5つの仕組みで守る。** (a) G1b の後にコードを凍結し、凍結時の digest を記録・照合するツール（X12）。
   (b) 過去の世代を作り直す処理（投稿の LLM 再抽出、保留の解除、ルールの再実行、添付の頁の再推論、クラウドの追随）を、すべて1つの `extract.upgrade_scope` で絞る。

   (d) 後から編集すると添付・走査・要約・保留・昇格証跡を再び失効させるファイルの一覧（§3.3）を、作り直し後の作業の受入条件にする。

### 3.2 `extract.upgrade_scope`（X11a）

- 値:
  - **無い（未設定）→ 制限なし（今の動き）。** 配布された導入先が何も設定せずにこの版へ上げると、今までの世代の更新と同じく全件が作り直される。
  - `"all"` → 制限なし（未設定と同じ。明示したいとき用）。
  - `"none"` → **閉じる**（過去の世代は作り直さない）。
  - `{"project_ids": [正の整数, …]}`（重複なし・1件以上）→ その患者だけ開く。範囲外は閉じる。
  - それ以外（空の dict、未知のキー、`"ALL"`、真偽値、負の数、文字列の id など）→ **閉じる**として扱い、`mcs_config.validate_config` がエラー `extract.upgrade_scope: …` を出す。
    エラーは `mcs_setup.py check`（doctor）に出るほか、更新の事前検査（`update_preflight.precheck_local`）・`mcs jobs`・`ops.cloud_resume`・設定の保存（`config_edit`）を止める（今の `validate_config` のエラーと同じ扱い。収集の定期処理は止めない）。
  - 閉じていても、新着・本文の編集・同じ世代の QC 指摘・薄さの再試行・人の指摘は止めない。
- **案 a を選んだ理由**: 今の既定の動きを変えないので、配布された導入先で黙って止まることがなく、既定値・導入手順・新規導入の設定例（`deployment/`、`config_edit.py`、`UPGRADE_AGENT.md`・`INSTALLATION.md`）を変える必要が無い。
  危険になり得る点を3つ確かめた。(1) 旧コードがこの子キーを嫌うか: 旧 `validate_config` は `extract` の未知の子キーを見ないので、エラーにも警告にもならない。
  (2) 書いた瞬間から配備までの間に旧コードが動くと何が起きるか: 旧 `candidate_fingerprint` は `cfg['extract']` を丸ごと hash するので、canonical の環境では書いた瞬間に昇格証跡が外れ、ローカル抽出の受付が閉じる。
  配備で loaded source が変わり証跡はどちらにしても外れるので、損は「書いてから配備までの数分」だけ。§9-3 で writer を止めてから書くことでこれも無くす。
  (3) この Mac で書き忘れたら: 配備の直後から全件の作り直しが始まる（今までの世代の更新と同じ動き）。§9-3 の手順と、配備前の確認（`mcs_setup.py check` に「範囲を絞っています」の警告が出ていること）で防ぐ。
  以上から案 a は安全側に倒せないものを持ち込まない。
- 「過去の世代の成果物」の判定（`mcs/extract/upgrade_scope.py` が SQL の断片を作り、全経路が使う）:
  - 投稿の LLM: 本文の hash が今と同じ `extract_llm` の現行行があり、その `extract_version` が `EXTRACT_VERSION` 未満で、目標世代の行が無い。保留（`held_prior`）の投稿もこれに当たる。
  - クラウドの追随（`cloud_only`）: 同じ。
  - ルール: 本文の hash が今と同じ `extract_v1` があり、`rule_version` が `RULE_VERSION` 未満。
  - 添付の頁: 現行の契約の結果が無く、同じ `attachment_ocr:<id>:<page>` に別の契約の `attachment_extract_v1` がある（ローカル・クラウドの両段）。

## 4. アレルギー・副作用の検証器（X2、`mcs/extract/clinical/clinical_allergies.py`）

### 4.1 方針

- 出力の形は v1 §3.1（Blk-EVAL の仮の形と同じ。`extract_bench_assertions.units` は変えない）。
- 検証は「本文から軸を決める → モデルの値と比べる」の2段。決める段 `resolve(body, evidence, allergen, reaction)` は軸の値に依存しないので、
  `(body, evidence, allergen, reaction)` で memo し、軸の比較は `resolve` の外に置く。全組合せの門（§4.3）を数秒で回せるようにする。
- 本文に無い引用・手がかり語の無い主張は**落とす**（保存しない）。主体・時制・否定・確からしさの食い違いは `unverified`（候補）。
  直すのは「より弱い方向」だけ: モデルの `suspected` を本文が `confirmed` と読んでも `suspected` のまま残す。本人・確定・現在の方向へは決して直さない。
- **計算した主体が `unknown` なら、モデルの値によらず `unverified`**（モデルが `patient` でも `unknown` でも確定に残さない。採点器では主体を開けたままの確定は本人のものとして読まれる誤断定に当たるため）。
  計算した時制が `unknown` のときも同じ（R4）。
- `clinical_scope.py` は編集しない。専用の語彙は確定を弱める方向にだけ働き、誤検出しても候補に落ちるだけで、誤断定を増やさない。
- 単位: 「文」＝ `。！？!?\n` で区切った範囲。見出しの行は「見出しの語＋同じ行の値」。

## 6. ブロック

### 6.1 共通の決まり

- **統合ブランチ（V4・C5・C6）**: Blk-X は実装グループ `group/blk-x`（`origin/main` から作る）にまとめる。各ブロックは `group/blk-x` から切った作業ブランチ（`work/blkx-<id>`）を
  別の git worktree（クラウドは clone の外 `../hermes-mcs-wt/blkx-<id>`、Mac は `~/.mcs-wt/blkx-<id>`）で書き、`group/blk-x` 向けの PR にする。
  作業 PR は CI が通れば担当エージェントが `group/blk-x` へマージしてよい（所有者 2026-11-17）。
  **X1〜X12 は `group/blk-x` にだけ入れ、X9 が入るまで main へ入れない・リリースしない・配備しない。**
  理由: X9 より前の版には版上げも `changes/` も無いのに、添付の契約・保留・走査・意味解析の鍵を変えるファイルが入っている。これが通常の更新で実機に入ると、計画した1回より前に失効が起き（X8 は有料の全走査を1回余分に起こす）、
  CLAUDE.md の「実行時の挙動を変えたら同じ作業内で `changes/` を作る」にも反する。
  **main へ先に入れてよいのは、実行時の挙動を変えない X1（評価専用の `mcs/extract/eval/` と評価資料）・X12（`scripts/development/` の新しいツール）・X2（新しいモジュール。X3 が `_LOADED_SOURCE_PATHS`・`_HOLD_SOURCES` に登録するまでどの契約にも入らず、実行時のコードから import されない）だけ。**
  X5 は未配線でも `patient_context.py`（添付の契約と `_HOLD_SOURCES` の両方に入る）を変えるので main へ先に入れない。X4（`clinical_values.py`）も同じ。
  新しい規約の「グループは1週間か約2,000行・10作業で途中でも main へ入れる。未完成の機能は既定を無効にして挙動を変えない形にする」は、Blk-X ではファイルの digest そのものが契約なので満たせない。
  例外にするかを所有者に尋ねる（O-12、§12 Q1）。答えが出るまで、`group/blk-x` の main 向け PR は開いてよいが main へは入れない。
- 各ブロックは表の「所有ファイル」以外は編集しない。所有に無い既存テストを直す必要が出たら、その場で止めて親に戻す（親が所有を割り当て直す。同時には編集しない）。
- **単独で緑**: 既存の pin・golden・基準値が固定している経路の出力を変える変更は、未配線の関数と単体テストで渡し、配線は X9 が版上げと同じ commit で行う。
  固定されていない新しい経路（新しい欄など）はそのブロックで配線してよい。各ブロックの完了条件は「自分の新しいテストが変更前に落ち、変更後に通る」かつ「`scripts/run_tests.sh` 一式と CI と同じ範囲の ruff が緑」。
- テストは完全合成・一時 DB・スタブだけ。実 MCS・ローカル LLM・Jev・クラウドに触れない。テストの実行は Haiku（effort low）のサブエージェント、
  クラウドの実行環境では並列に走らせてよい。失敗の原因調査と修正は担当のモデル。
- 差分レビューは**書き手と別のモデル**（Sonnet か Fable、high、読取り専用）。Opus・Sonnet が書いたものは Fable high。Fable が書いたもの（X2 で規則の判断を Fable に回した部分、X8 の設計）は Sonnet high。
- 版の数値・pin・基準値・文書・`changes/` は X9 だけ。`docs/development/DEVELOPMENT.md` の生成表はどのブロックも PR に入れない（main への合流後に `main-sync.yml` が作り直す）。

## 9. 実機の手順（各段で所有者の承認）

1. 見積り（O-5、新しい checkout から、バックアップを読取り専用で）。
2. 保管用のバックアップ（O-2）。
3. 配備の作業の中で（gateway・LINE WORKS の独立アダプター・standalone の writer を止めてから）設定を書く: `extract.patient_context.enabled=false`、`cloud-llm stop`、**`extract.upgrade_scope="none"`**、reextract 経路（O-6）。
   止めてから書くのは、旧コードの `candidate_fingerprint` が `cfg['extract']` を丸ごと hash し、canonical の環境では書いた瞬間に抽出の受付が閉じるため。
4. 凍結点 F を配備し、gateway・LINE WORKS の独立アダプター・standalone を再起動する。再起動の後、`mcs_setup.py check` に「過去世代の更新を絞っています」の警告と件数が出ていることを確かめる（出ていなければ `upgrade_scope` が効いていない）。
   **legacy の環境では、この時点から意味解析の全件再処理が始まる**（`execution_generation` が変わり、`reprocess_step` が全 job を投入し直す。Jev の要求とローカル LLM の背景枠を使う。O-10）。
5. canonical の環境: G6 の再評価と再承認（O-1）。承認までは意味解析が `mode=off` で、承認の後に全件再処理が始まる。`reproject_stale` が古い版の投影を0にするのを `census` で確かめてから次へ。
6. G2: `upgrade_scope={"project_ids": […]}` を設定して測る（範囲外の置き換え 0 件を含む）。
7. `"all"`（または削除）にして B3。
8. G3（抽出の残り 0、意味解析の N_sem 0、ほか §7）。
9. S3（消去は `--confirm-human`＋`reason`＋receipt。拒否理由は抽出の残りと N_sem）→ `enabled=true` → 作り直し（O-3 のモデル）。
10. 定常: `upgrade_scope` は未設定か `"all"`。作り直しの後の作業は §3.1 の決まりで入れる。

## 12. 所有者への質問（前提知識のない人が決められるように）

各質問は「何を決めるか」「選んだら何が起きるか」「推奨」「いつまでに」の順。

**Q1（O-12）Blk-X の作業を、実装グループの「1週間・約2,000行・10作業で途中でも main へ入れる」という上限の例外にしますか。**
- 背景: 今回の変更は、プログラムのファイルの中身そのものが「作り直しの合図」になっています。途中の版が main に入り、通常の更新でこの Mac に入ると、添付の全頁・保留中の投稿・患者コンテキストの全走査（有料）が、計画した1回より前に作り直されます。設定で機能を無効にしても防げません。
- 例外にする: Blk-X は `group/blk-x` に全部がそろう（統合ブロック X9 まで）まで main に入れません。期間は上限を超える見込みで、その間は毎日 main を取り込んで衝突を小さく保ちます。挙動を変えない3つ（評価資産 X1・新しい検証器 X2・凍結ツール X12）だけは先に main へ入れられます。
- 例外にしない: 上限で途中の版を main へ入れることになり、その版を配備しないように別の歯止め（リリースから外す運用など）が要ります。歯止めを外すと作り直しが2回以上起き、有料の走査と Jev の要求が余分にかかります。
- 推奨: **例外にする。** いつまでに: `group/blk-x` を作る前。

**Q2（O-13）新しい設定 `extract.upgrade_scope`（過去の投稿を作り直す範囲）を書いていないとき、今までどおり「全部作り直す」でよいですか。**
- 背景: 今回、過去の投稿の作り直しを患者ごとに絞れる設定を足します。この Mac では絞って少しずつ進めますが、ほかの導入先はこの設定を知りません。
- 今までどおり（推奨の案 a）: 書いていなければ全部作り直します（今までの版上げと同じ）。この Mac では配備の作業の中で `"none"`（止める）を書き、カナリアの患者だけ開けてから全体を開けます。書き忘れると、この Mac でも配備の直後から全部の作り直しが始まります（配備後の確認で気付けるよう警告を出します）。
- 書いていなければ止める（案 b）: 設定しない導入先では、過去の投稿の更新が黙って止まったままになります。新規導入の設定例・更新手順の文書・診断を別に作る必要があります。
- 推奨: **今までどおり（案 a）。** いつまでに: 今の計画は案 a で進めます。変えるなら X11a の着手の前。

**Q3（O-11）「昇格の承認」が有効であり続ける条件から、作り直しの範囲（`upgrade_scope`）と患者コンテキストの有効・公開の設定を外してよいですか。**
- 背景: 意味解析の新しい方式（canonical）は、所有者が承認した証跡と、設定の中身が一致しているときだけ動きます。今は抽出の設定（`extract`）を丸ごと照合するので、作り直しの範囲を変えたり患者コンテキストを一時停止したりするだけで承認が外れ、ローカルの抽出が止まります。この2つは意味の解釈には使いません。
- 外す: 範囲の変更や一時停止で承認が外れなくなります。解釈に使う設定（`patient_state_context` など）は今までどおり照合します。人の承認の条件が変わるので、変更記録の「承認条件」に書きます。
- 外さない: canonical の環境では、カナリアから全体へ広げるたび、患者コンテキストを止めるたびに、Jev を使った再評価と再承認が要ります（本番が canonical かは O-1 で確かめます）。
- 推奨: **外す（承認する）。** いつまでに: 統合（X9）の前。

**Q4（O-10）意味解析（要約と Jev の判定）を全件やり直す変更を、このまま入れますか。始まる時期は配備の直後でよいですか。**
- 背景: 以前の決定（O8）は「命題の日本語名（label_ja）を変えると Jev の判定が全部無効になるので、作り直しと同じ回にまとめる」という前提でした。調べると、日本語名は Jev には送られず、ローカルの要約にだけ使われていました。全件のやり直しは、日本語名の変更に合わせて登録版（`REGISTRY_VERSION`）を上げる、という選択の結果です。また、登録版を上げるだけでは作り直しが始まらない不具合を見つけたので、合わせて直します。
- 入れる: 配備の直後から、過去の全投稿の要約（ローカル LLM）と Jev の判定（1日 10,000 要求の上限の中）がやり直されます。抽出の作り直しとローカル LLM の背景の枠を分け合うので、抽出の作り直しが遅くなります。日数は本番 DB の見積り（O-5）で出します。要約が新しい日本語名で揃い、患者コンテキストの作り直しの前に済ませるので、作り直しは1回で済みます。
- 入れない: 日本語名の変更と登録版の更新を外します。QC の独立化だけが入ります。要約は英語の名前のままで、あとで日本語名に変えるときにもう一度全件のやり直し（と患者コンテキストの作り直し）が要ります。
- 時期を遅らせる: 意味解析の対象患者（`semantic.project_ids`）を配備時に絞ると遅らせられますが、患者コンテキストの作り直し（S3）はその分遅れます。
- 推奨: **入れる。時期は配備の直後のまま。** いつまでに: 統合（X9）の前（見積りは配備の前）。

**Q5（O-1）本番の意味解析は、旧方式（legacy）と新方式（canonical）のどちらで動いていますか。**
- 背景: canonical なら、配備した瞬間に承認が外れ、再評価と再承認が終わるまでローカルの抽出と意味解析が止まります。legacy なら止まりません。
- 推奨: **設定を読んで確かめる**（実データには触れません）。canonical なら、再承認の段取りと、その間の「抽出停止中」の知らせ方を決めます。いつまでに: 配備の前。

**Q6（O-2）作り直しの前の結果（世代11）を、どうやって一定期間残しますか。**

- 推奨: **バックアップで残す。** いつまでに: カナリア（G2）の前。
