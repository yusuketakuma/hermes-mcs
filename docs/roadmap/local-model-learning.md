# ローカル解析の改善・学習計画

状態: **将来の検討計画**（2026-10-29）。1.1では学習機能を実装せず、学習処理も実行しない。実装する版や実データの利用は決まっていない。本書の作成は、患者データの学習利用、クラウドへの追加送信、モデルの変更、本番適用の承認ではない。

目的は、ローカル解析の誤りや漏れを減らすことである。クラウドの解析結果と原文を照合し、誤りの種類を把握する。改善方法は、既存の検証や合成評価を拡張して比較する。クラウドの回答を無条件で正解としたり、結果を自動で重みへ反映したりしない。

## 現状と前提

- 抽出・患者コンテキストには原文との対応、推論版、品質確認、保存前の再確認がある。新しい改善方法でもこれらを維持する。詳細は[推論エンジンの仕様](../specs/inference-engine-v1.md)を参照する。
- `cloud_compare_v1` は、ローカルとクラウドの事実数や一致数を記録する。現在の比較記録だけでは、個別の原文と人が確認した正解を結び付けた学習データにはならない。
- 合成評価は[抽出ベンチマーク](../../mcs/extract/eval/extract_bench.py)と `evaluation/` の架空ケースを使う。ベンチマークは承認済みの完全架空ケースを検査し、実投稿の匿名化例を合成ケースとして扱わない。
- 現行コードのローカルモデル既定は `Qwen3.5-9B`、実行経路は llama.cpp である。設定による変更はあり得る。このMacのメモリは16 GiBだが、対象モデルの追加学習、変換、稼働中の推論との共存は測定していない。
- [評価資産とG6基準](../../evaluation/README.md)は、合成試験と人手評価、本番の受入を区別する。G6 v2の候補昇格では[封印候補評価](../specs/SEALED_CANDIDATE_EVALUATION.md)を優先する。

## 比較する改善候補

| 候補 | 方法 | 評価する内容 |
|---|---|---|
| 例示・ルールの改善 | 完全合成の例を使い、既存のプロンプト、抽出ルール、検証を調整する | 重みを変えずに誤りが減るか、他の抽出項目を損なわないか |
| LoRAによる追加学習 | 元モデルを固定し、少数の追加パラメータを学習する | 同じ合成評価での品質、学習と推論の時間、メモリ、既存実行形式との互換性 |
| 限定用途の分類器 | 誤りの種類や要確認候補を識別する小さなモデルを比較する | 対象を狭めた検出が既存処理より有用か、漏れや過剰な保留が増えないか |

この順に比較し、改善が確認できなければ採用しない。分類器は生成モデルや人の判断を置き換えず、対象の発見を助ける候補とする。MLX LMはLoRAとQLoRAを提供するが、今回のモデルでの学習やllama.cppへの受け渡しを確認したものではない。[MLX LM公式手順](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/LORA.md)

## 進め方

### 1. 原文・結果・評価を分けて比較する

同じ対象について、入力の出現回と版、ローカルとクラウドの結果、それぞれのモデル・抽出契約・生成時刻・品質状態を対応付ける。比較の対象は必要な範囲に限定し、差が出た理由を分類する。

- 原文にある内容の漏れ、原文にない内容の追加。
- 否定・条件・時点・対象人物の取り違え。
- 薬剤、用量、単位、検査値、依頼や返信の関係の誤り。
- 本文未取得、処理失敗、保留、品質未確認など、比較できない状態。

両者の一致は正しさの証明ではない。クラウドだけが正しい、ローカルだけが正しい、両方とも誤っている、判定できない場合を分ける。既存の集計は改善対象の探索に使い、人手の正解ラベルとして使わない。

### 2. 完全合成データで試す

架空の原文と正解だけを作る。実記録を元にした匿名化例は使わない。薬剤・症状・バイタル・否定・家族・予定・訂正・返信・長文・分割境界の正例と負例を用意し、原文にない内容を答えない例も含める。候補ごとに同じ固定ケースと評価器を使い、現行版との差を分母・件数・失敗例の分類とともに記録する。

重みを変えない候補で改善できるか先に調べ、必要な場合にLoRAを試す。合成データによる成功は、実記録での有効性や臨床品質を示さない。生成例だけを繰り返し学習へ戻す方法は、誤りや珍しい事例の欠落を増幅し得るため採用しない。[生成データの反復利用に関する研究](https://www.nature.com/articles/s41586-024-07566-y)

### 3. 許可済みデータと教師を準備する

実データを使う場合は、利用目的、データ範囲、保存先、利用者、保持期間、削除・撤回時の扱い、外部提供者との契約を事前に確認する。患者情報をリポジトリ、通常のCI、共有ログ、外部の実験管理サービスへ入れない。原文、解析結果、評価票、モデル重み、LoRA、checkpointも許可された私有領域で管理する。

教師候補には対象の原文・文脈・版、両方式の出力、原文の根拠、人による判定と訂正、判定者・理由、データ利用許可を結び付ける。数量、否定、対象人物など重要な項目は独立した確認と不一致の裁定を行う。クラウド出力だけで人手の正解や承認を作らない。取得できない原文や権利を確認できない候補は学習対象にしない。

Anthropicの[公式案内](https://support.claude.com/en/articles/12326764-can-i-use-my-outputs-to-train-an-ai-model)は専門的な情報抽出を許可例として挙げる一方、学習対象や競合モデルへの制限、書面許可にも言及する。OpenAIの[事業者向け契約](https://openai.com/policies/services-agreement/)にも競合モデルに関する制限と限定的な例外がある。利用する契約と用途の適用可否を確認するまで、各社の出力を生成モデルの教師に使わない。モデル本体や利用データのライセンスも別に確認する。

### 4. 候補を評価する

開発・学習、調整、最終評価の集合を分ける。患者・スレッド・原文とその派生例が別々の集合に入らないようにし、最終評価の集合を事前に固定する。候補の比較では同じ入力と判定基準を使い、できる範囲で方式を伏せて確認する。

測定項目は、重要な事実の漏れ、誤断定、否定・時点・主体・用量・単位、根拠、依頼と返信、適切な保留、処理時間と資源使用量とする。分母が足りない項目は未評価とし、全件を保留して誤断定だけを減らす候補を合格にしない。希少な重大事例は別に件数と結果を示す。

採用判断に使うモデル本体・追加重み・プロンプト・ルール・schema・検証条件・データ集合を版とハッシュで固定する。既存の候補指紋はモデルIDなどを束ねるが、同じIDの重み差替えは検知対象外である。追加学習候補ではモデル本体と追加重みのハッシュを別途結び付ける必要がある。

### 5. 影運転と採用

評価を通った候補を、現行の結果や通知を変えない影運転で比較する。新着の収集・通知を優先し、学習や評価が通常処理の資源を圧迫しない条件を測る。実データでの影運転は対象・費用・権限を別途確認する。

候補の採用は、評価結果と版が一致し、必要な人の承認が得られた後に行う。配備・サービス再起動・本番設定の変更は別の明示指示で行う。旧版へ戻す手順を用意し、切替や復元で元データ、通知の配送記録、費用予約、承認履歴を巻き戻さない。入力の削除だけで学習済み重みからの情報除去が完了したとは扱わない。

## 調査の根拠と未確認事項

英語の臨床試験適格性判定の研究では、8Bモデルの平均balanced accuracyが追加学習前の84.0%から学習後の93.5%になった評価がある。ただし、研究対象と日本語の医療・介護チャットは異なり、そのまま本システムへの有効性を示すものではない。[研究本文](https://pmc.ncbi.nlm.nih.gov/articles/PMC12065832/)

別の臨床情報抽出研究では、人手ラベルによる学習とモデルのラベルによる学習に差があり、症状抽出では学習後モデルが教師を下回った。教師の出力を正解とみなさず、誤りの種類ごとに評価する必要がある。[研究本文](https://arxiv.org/html/2501.00031v1)

言語モデルから学習例を取り出せた研究があるため、追加重みやcheckpointも機密情報を含み得るものとして扱う。この研究は本システムの漏えい率を示すものではない。[研究本文](https://www.usenix.org/conference/usenixsecurity21/presentation/carlini-extracting)

未確認なのは、このMacでの学習と推論の資源使用量、モデル・形式の互換性、許可された評価データの準備、各提供者の契約における教師利用、実環境での精度と運用負荷である。これらは測定・確認した時点で記録し、未確認を成功や利用許可に読み替えない。
